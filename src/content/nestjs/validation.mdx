## 한눈에 보기

- Pipe는 핸들러 **직전에** 각 인자를 받아 **변환(transform)** 하거나 **검증(validate)** 한다. 실패하면 예외를 던져 핸들러가 실행되지 않는다.
- `ValidationPipe`는 내부적으로 `plainToInstance`(class-transformer) → `validate`(class-validator) 순서로 동작한다. 그래서 두 라이브러리의 데코레이터가 모두 의미가 있다.
- 실무 기본값은 `whitelist: true`, `forbidNonWhitelisted: true`, `transform: true`. 단 `enableImplicitConversion`은 boolean 변환 함정이 있다.
- 중첩 객체는 `@ValidateNested()` + `@Type(() => Dto)` 짝이 필수다. `@Type`이 없으면 중첩 검증이 동작하지 않는다.
- 수정용 DTO는 `PartialType` 등 Mapped types로 만들고, Swagger를 쓰면 `@nestjs/swagger`에서 import한다.

## Pipe의 두 역할

> **비유**: Pipe는 공장 라인의 **입고 검수대**다. 들어온 원자재를 규격에 맞게 다듬고(변환), 불량품은 반송한다(검증). 검수대를 통과한 자재만 조립 라인(핸들러)에 올라간다.

```ts
export interface PipeTransform<T = any, R = any> {
  transform(value: T, metadata: ArgumentMetadata): R;
}

export interface ArgumentMetadata {
  type: 'body' | 'query' | 'param' | 'custom';
  metatype?: Type<unknown>; // design:paramtypes에서 꺼낸 클래스
  data?: string; // @Param('id')의 'id'
}
```

| 역할 | 하는 일 | 예시 |
| --- | --- | --- |
| 변환 | 입력 값을 원하는 형태로 바꿔 반환 | `'42'` → `42`, plain object → DTO 인스턴스 |
| 검증 | 조건에 맞으면 그대로, 아니면 예외 | 이메일 형식이 아니면 `BadRequestException` |

> **포인트**: Pipe는 **반환값이 곧 핸들러의 인자**가 된다. 검증만 하는 Pipe라도 값을 그대로 `return`해야 한다.

Pipe가 Guard, Interceptor 이후, 핸들러 직전에 실행된다는 전체 순서는 Request Lifecycle 문서를 참고하자.

## 내장 Pipe

> **비유**: 공구함에 기본으로 들어 있는 **규격 게이지**들이다. 숫자 게이지, UUID 게이지, 목록 게이지가 따로 있고, 필요한 칸에 끼워 쓰면 된다.

| Pipe | 역할 | 실패 시 |
| --- | --- | --- |
| `ParseIntPipe` | 정수로 변환 | 400 |
| `ParseFloatPipe` | 실수로 변환 | 400 |
| `ParseBoolPipe` | `'true'`/`'false'` → boolean | 400 |
| `ParseUUIDPipe` | UUID 형식 검증(버전 지정 가능) | 400 |
| `ParseEnumPipe` | enum 값인지 검증 | 400 |
| `ParseArrayPipe` | 구분자로 분리 + 항목 검증 | 400 |
| `DefaultValuePipe` | `undefined`/`null`일 때 기본값 | 실패 없음 |
| `ParseFilePipe` | 업로드 파일 검증(크기, 타입) | 400 또는 지정 코드 |
| `ParseDatePipe` | 날짜로 변환(v11) | 400 |
| `ValidationPipe` | class-validator 기반 DTO 검증 | 400 |

```ts
@Controller('orders')
export class OrdersController {
  @Get()
  list(
    @Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number,
    @Query('status', new ParseEnumPipe(OrderStatus, { optional: true })) status?: OrderStatus,
    @Query('ids', new ParseArrayPipe({ items: Number, separator: ',', optional: true })) ids?: number[],
  ) {
    return this.ordersService.list({ page, status, ids });
  }

  @Get(':id')
  findOne(@Param('id', new ParseUUIDPipe({ version: '4' })) id: string) {
    return this.ordersService.findOne(id);
  }

  @Delete(':id')
  remove(
    @Param('id', new ParseIntPipe({ errorHttpStatusCode: HttpStatus.NOT_ACCEPTABLE })) id: number,
  ) {
    return this.ordersService.remove(id);
  }
}
```

> **주의**: 한 파라미터에 여러 Pipe를 걸면 **왼쪽에서 오른쪽** 순서로 실행된다. `DefaultValuePipe`는 반드시 `ParseIntPipe` **앞에** 둬야 한다. 순서를 바꾸면 `undefined`가 `ParseIntPipe`에서 먼저 실패한다.

### ParseFilePipe

```ts
@Post('avatar')
@UseInterceptors(FileInterceptor('file'))
uploadAvatar(
  @UploadedFile(
    new ParseFilePipe({
      validators: [
        new MaxFileSizeValidator({ maxSize: 2 * 1024 * 1024 }),
        new FileTypeValidator({ fileType: /^image\/(png|jpeg)$/ }),
      ],
      errorHttpStatusCode: HttpStatus.UNPROCESSABLE_ENTITY,
    }),
  )
  file: Express.Multer.File,
) {
  return this.usersService.saveAvatar(file);
}
```

빌더 스타일도 있다.

```ts
new ParseFilePipeBuilder()
  .addFileTypeValidator({ fileType: 'image/png' })
  .addMaxSizeValidator({ maxSize: 1_000_000 })
  .build({ errorHttpStatusCode: HttpStatus.UNPROCESSABLE_ENTITY });
```

> **주의**: `FileTypeValidator`는 최근 버전에서 확장자/mimetype 헤더가 아니라 **파일 내용(magic number)** 을 확인하도록 강화되었다. 클라이언트가 보낸 `Content-Type`만 믿는 검증은 우회 가능하다는 점을 기억하자.

## 바인딩 위치

> **비유**: 검수대를 **어디에 설치하느냐**의 문제다. 특정 부품 칸(파라미터)에만, 특정 라인(메서드)에만, 공장 한 동(컨트롤러)에만, 혹은 공장 정문(전역)에 설치할 수 있다.

| 위치 | 문법 | 적용 범위 | DI 가능 |
| --- | --- | --- | --- |
| 파라미터 | `@Body(ValidationPipe)` | 해당 인자 하나 | 클래스로 넘기면 O |
| 메서드 | `@UsePipes(...)` | 메서드의 모든 인자 | 클래스로 넘기면 O |
| 컨트롤러 | 클래스에 `@UsePipes(...)` | 컨트롤러 전체 | 클래스로 넘기면 O |
| 전역(인스턴스) | `app.useGlobalPipes(new ...)` | 앱 전체 | X |
| 전역(provider) | `APP_PIPE` | 앱 전체 | O |

```ts
// 1) 전역: main.ts (DI 불가, 하이브리드 앱의 microservice/gateway에는 미적용)
app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));

// 2) 전역: provider 방식 (DI 가능, 어느 모듈에서 선언해도 전역)
@Module({
  providers: [
    {
      provide: APP_PIPE,
      useFactory: () => new ValidationPipe({ whitelist: true, transform: true }),
    },
  ],
})
export class AppModule {}
```

> **포인트**: `@UsePipes(ValidationPipe)`처럼 **클래스**를 넘기면 Nest가 인스턴스를 만들고 DI도 해 준다. `new ValidationPipe()`처럼 **인스턴스**를 넘기면 옵션은 줄 수 있지만 DI는 받을 수 없다.

> **주의**: e2e 테스트에서 `Test.createTestingModule`로 앱을 만들면 `main.ts`의 `useGlobalPipes`는 실행되지 않는다. 테스트와 실제 앱의 동작을 맞추려면 `APP_PIPE`로 등록하거나 테스트 셋업에서도 같은 설정을 호출해야 한다.

## ValidationPipe 내부 동작

> **비유**: 택배 상자(JSON)를 받으면 먼저 **견본 틀(DTO class)에 내용물을 옮겨 담고**(plainToInstance), 그 다음 틀에 붙은 **검사 항목표**(class-validator 데코레이터)대로 하나씩 확인한다(validate). 틀에 옮겨 담지 않으면 검사표를 붙일 곳이 없다.

```ts
export class CreateUserDto {
  @IsEmail()
  email!: string;

  @IsString()
  @Length(8, 64)
  password!: string;

  @IsOptional()
  @IsInt()
  @Min(0)
  age?: number;
}
```

### 단계별 흐름

1. Nest가 `transform(value, metadata)`를 호출한다. `metadata.metatype`은 `CreateUserDto`.
2. `metatype`이 없거나 `String`, `Number`, `Boolean`, `Array`, `Object` 같은 기본 타입이면 검증을 건너뛴다(`transform: true`면 `param`/`query`의 원시 타입 변환만 수행).
3. `plainToInstance(CreateUserDto, value, transformOptions)`로 **DTO 인스턴스**를 만든다. 이때 `@Type`, `@Transform`이 적용된다.
4. `validate(instance, validatorOptions)`로 class-validator 메타데이터를 검사한다. `whitelist`, `forbidNonWhitelisted`도 여기서 처리된다.
5. 에러가 있으면 `exceptionFactory(errors)`가 만든 예외(기본은 `BadRequestException`)를 던진다.
6. 성공하면 `transform: true`일 때 **DTO 인스턴스**를, 아니면 원본 값(또는 whitelist가 적용된 plain object)을 반환한다.

```ts
// 개념적으로 단순화한 ValidationPipe
async transform(value: unknown, { metatype, type }: ArgumentMetadata) {
  if (!metatype || isPrimitiveType(metatype)) {
    return this.transformEnabled ? transformPrimitive(value, metatype, type) : value;
  }
  const entity = plainToInstance(metatype, value, this.transformOptions);
  const errors = await validate(entity, this.validatorOptions);
  if (errors.length > 0) {
    throw this.exceptionFactory(errors);
  }
  return this.transformEnabled ? entity : value;
}
```

> **포인트**: `transform: false`여도 **내부적으로는 항상 `plainToInstance`를 한다**. 검증은 인스턴스에만 걸 수 있기 때문이다. `transform` 옵션은 "그 인스턴스를 핸들러에 넘길지"를 결정할 뿐이다.

> **주의**: `ValidationPipe`는 `class-validator`와 `class-transformer`를 **peer dependency**로 쓴다. 설치하지 않으면 런타임에 패키지를 찾을 수 없다는 에러가 난다.

## ValidationPipe 옵션

| 옵션 | 기본값 | 효과 |
| --- | --- | --- |
| `whitelist` | `false` | 데코레이터가 하나도 없는 프로퍼티를 **제거** |
| `forbidNonWhitelisted` | `false` | 제거 대신 **400 에러**(whitelist와 함께 사용) |
| `transform` | `false` | 핸들러에 DTO 인스턴스 전달, `param`/`query` 원시 타입 변환 |
| `transformOptions.enableImplicitConversion` | `false` | TS 타입 정보(`design:type`)로 자동 형 변환 |
| `stopAtFirstError` | `false` | 프로퍼티별 첫 번째 에러에서 중단 |
| `skipMissingProperties` | `false` | `null`/`undefined` 프로퍼티 검증 건너뜀 |
| `disableErrorMessages` | `false` | 에러 상세 숨김(운영 환경용) |
| `errorHttpStatusCode` | 400 | 실패 시 상태 코드 |
| `exceptionFactory` | 기본 팩토리 | `ValidationError[]`로 원하는 예외 생성 |
| `validateCustomDecorators` | `false` | 커스텀 파라미터 데코레이터도 검증 |
| `expectedType` | 없음 | `metatype` 대신 강제로 쓸 타입 |

### whitelist와 forbidNonWhitelisted

```ts
// 요청 바디
// { "email": "a@b.com", "password": "secret123", "isAdmin": true }

// whitelist: true → isAdmin이 조용히 제거됨
// whitelist: true + forbidNonWhitelisted: true → 400 "property isAdmin should not exist"
```

> **포인트**: `whitelist`는 **mass assignment 공격**(요청에 `isAdmin`, `role` 같은 필드를 몰래 끼워 넣기)을 막는 1차 방어선이다. DTO에 선언되지 않은 필드는 서비스 계층까지 오지 못한다.

> **주의**: whitelist는 "데코레이터가 붙은 프로퍼티"를 기준으로 한다. 검증이 필요 없는 필드라도 남기고 싶다면 `@Allow()`나 `@IsOptional()` 같은 데코레이터를 하나는 붙여야 한다.

### exceptionFactory로 에러 형식 통일

```ts
new ValidationPipe({
  whitelist: true,
  transform: true,
  exceptionFactory: (errors: ValidationError[]) => {
    const flatten = (errs: ValidationError[], parent = ''): { field: string; messages: string[] }[] =>
      errs.flatMap((e) => {
        const path = parent ? `${parent}.${e.property}` : e.property;
        const self = e.constraints ? [{ field: path, messages: Object.values(e.constraints) }] : [];
        return [...self, ...flatten(e.children ?? [], path)];
      });

    return new UnprocessableEntityException({
      code: 'VALIDATION_FAILED',
      errors: flatten(errors),
    });
  },
});
```

중첩 DTO 에러는 `children`에 재귀적으로 들어 있으므로 평탄화해 두면 프론트엔드가 다루기 쉽다.

## 쿼리 스트링 타입 변환 함정

> **비유**: 쿼리 스트링은 **모든 값을 글자로 적은 쪽지**다. `?page=2&active=false`라고 써도 받는 쪽에서는 `'2'`와 `'false'`라는 글자일 뿐이다. 글자를 숫자나 참/거짓으로 읽는 방법을 정확히 정해 줘야 한다.

```ts
export class ListProductsQueryDto {
  @IsOptional()
  @IsInt()
  @Min(1)
  page?: number;

  @IsOptional()
  @IsBoolean()
  active?: boolean;
}
```

| 설정 | `page=2` | `active=false` |
| --- | --- | --- |
| 아무 변환 없음 | `'2'` → `@IsInt` 실패 | `'false'` → `@IsBoolean` 실패 |
| `enableImplicitConversion: true` | `2` O | `Boolean('false')` → **`true`** X |
| `@Type(() => Number)` | `2` O | (해당 없음) |
| 명시적 `@Transform` | O | `false` O |

`enableImplicitConversion`은 `design:type`을 보고 `Number(value)`, `Boolean(value)`를 호출한다. JS에서 비어 있지 않은 문자열은 모두 truthy이므로 `'false'`도 `true`가 된다.

```ts
export class ListProductsQueryDto {
  @IsOptional()
  @Type(() => Number)
  @IsInt()
  @Min(1)
  page?: number = 1;

  @IsOptional()
  @Transform(({ obj, key }) => {
    const raw = obj[key];
    if (raw === 'true' || raw === true) return true;
    if (raw === 'false' || raw === false) return false;
    return raw; // 그대로 두면 @IsBoolean이 실패시킴
  })
  @IsBoolean()
  active?: boolean;

  @IsOptional()
  @Transform(({ value }) => (Array.isArray(value) ? value : String(value).split(',')))
  @IsString({ each: true })
  tags?: string[];
}
```

> **주의**: `enableImplicitConversion`이 켜져 있으면 `@Transform`의 `value`는 이미 `Boolean()`으로 변환된 값일 수 있다. 위 예처럼 `obj[key]`로 **원본 값**을 읽는 것이 안전하다.

> **포인트**: `?tags=a`처럼 값이 하나면 문자열, `?tags=a&tags=b`면 배열로 들어온다(Express 기본 쿼리 파서 기준). 배열 필드는 항상 두 경우를 모두 처리하자.

## 중첩 DTO와 배열 검증

> **비유**: 큰 상자 안에 작은 상자가 들어 있는 **이중 포장**이다. 겉 상자 검수표에 "안쪽 상자도 검수할 것"(`@ValidateNested`)과 "안쪽 상자는 이 규격"(`@Type`)을 둘 다 적어야 안쪽까지 검사한다.

```ts
export class AddressDto {
  @IsString()
  @IsNotEmpty()
  street!: string;

  @IsPostalCode('KR')
  zipCode!: string;
}

export class OrderItemDto {
  @IsUUID()
  productId!: string;

  @IsInt()
  @Min(1)
  quantity!: number;
}

export class CreateOrderDto {
  @ValidateNested()
  @Type(() => AddressDto)
  shippingAddress!: AddressDto;

  @IsArray()
  @ArrayMinSize(1)
  @ArrayMaxSize(50)
  @ValidateNested({ each: true })
  @Type(() => OrderItemDto)
  items!: OrderItemDto[];
}
```

### 왜 @Type이 필요한가

1. JSON 파싱 결과의 `shippingAddress`는 plain object다.
2. class-validator는 **인스턴스의 클래스에 등록된 메타데이터**로 검증한다.
3. TS의 `design:type`만으로는 배열 요소 타입(`OrderItemDto[]`의 `OrderItemDto`)을 알 수 없다. 배열은 그냥 `Array`로 기록된다.
4. 그래서 `@Type(() => OrderItemDto)`로 class-transformer에게 "이 필드는 이 클래스로 변환하라"고 알려 줘야 한다.
5. 변환되지 않은 plain object에 `@ValidateNested`를 걸면 검증할 메타데이터가 없어 **에러 없이 통과**하거나 "nested property must be either object or array" 에러가 난다.

> **주의**: `@ValidateNested()`만 있고 `@Type()`이 없는 것이 가장 흔한 실수다. 테스트에서 잘못된 중첩 값을 넣어 실제로 400이 나는지 꼭 확인하자.

### 최상위 배열 바디

`@Body() dtos: CreateUserDto[]`처럼 **바디 자체가 배열**이면 `design:paramtypes`에는 `Array`만 남아 `ValidationPipe`가 요소 타입을 모른다.

```ts
@Post('bulk')
createBulk(
  @Body(new ParseArrayPipe({ items: CreateUserDto, whitelist: true }))
  dtos: CreateUserDto[],
) {
  return this.usersService.createMany(dtos);
}
```

또는 `{ users: CreateUserDto[] }` 형태의 래퍼 DTO를 만들어 `@ValidateNested({ each: true })`로 검증하는 방법이 확장성 면에서 더 낫다.

## 조건부 검증: @ValidateIf

```ts
export class CreateCustomerDto {
  @IsEnum(CustomerType)
  type!: CustomerType; // 'PERSONAL' | 'COMPANY'

  @ValidateIf((o: CreateCustomerDto) => o.type === CustomerType.COMPANY)
  @IsString()
  @Length(10, 10)
  businessNumber?: string;

  @ValidateIf((o: CreateCustomerDto) => o.type === CustomerType.PERSONAL)
  @IsDateString()
  birthDate?: string;
}
```

`@ValidateIf`의 조건이 `false`면 그 프로퍼티의 **다른 모든 검증 데코레이터가 무시**된다.

| 데코레이터 | 건너뛰는 조건 |
| --- | --- |
| `@IsOptional()` | 값이 `null` 또는 `undefined` |
| `@ValidateIf(fn)` | `fn(object, value)`가 `false` |

## 커스텀 Validator

> **비유**: 기본 게이지로는 잴 수 없는 규격(예: "종료일은 시작일 이후")을 위해 **전용 게이지를 직접 제작**하는 것이다.

### registerDecorator: 동기 규칙

```ts
import { registerDecorator, ValidationArguments, ValidationOptions } from 'class-validator';

export function IsAfter(property: string, options?: ValidationOptions) {
  return (object: object, propertyName: string) => {
    registerDecorator({
      name: 'isAfter',
      target: object.constructor,
      propertyName,
      constraints: [property],
      options,
      validator: {
        validate(value: unknown, args: ValidationArguments) {
          const [relatedKey] = args.constraints;
          const related = (args.object as Record<string, unknown>)[relatedKey];
          return (
            typeof value === 'string' &&
            typeof related === 'string' &&
            new Date(value).getTime() > new Date(related).getTime()
          );
        },
        defaultMessage(args: ValidationArguments) {
          return `${args.property} must be after ${args.constraints[0]}`;
        },
      },
    });
  };
}

export class CreateEventDto {
  @IsDateString()
  startsAt!: string;

  @IsDateString()
  @IsAfter('startsAt')
  endsAt!: string;
}
```

### ValidatorConstraint + DI: DB 조회가 필요한 규칙

```ts
@ValidatorConstraint({ name: 'isEmailUnique', async: true })
@Injectable()
export class IsEmailUniqueConstraint implements ValidatorConstraintInterface {
  constructor(private readonly usersRepository: UsersRepository) {}

  async validate(email: string): Promise<boolean> {
    return !(await this.usersRepository.existsByEmail(email));
  }

  defaultMessage(): string {
    return 'email already exists';
  }
}

export function IsEmailUnique(options?: ValidationOptions) {
  return (object: object, propertyName: string) =>
    registerDecorator({
      target: object.constructor,
      propertyName,
      options,
      validator: IsEmailUniqueConstraint,
    });
}
```

class-validator는 기본적으로 constraint 클래스를 **자기 손으로 `new`** 한다. Nest 컨테이너의 인스턴스를 쓰게 하려면 `useContainer`로 연결해야 한다.

```ts
// main.ts
const app = await NestFactory.create(AppModule);
useContainer(app.select(AppModule), { fallbackOnErrors: true });

// users.module.ts
@Module({
  providers: [UsersRepository, IsEmailUniqueConstraint], // provider 등록 필수
})
export class UsersModule {}
```

1. `useContainer`가 class-validator의 인스턴스 생성기를 Nest 컨테이너 조회로 바꾼다.
2. 검증 시 class-validator가 `IsEmailUniqueConstraint`를 요청한다.
3. Nest가 DI로 만든 싱글톤 인스턴스를 돌려준다.
4. `fallbackOnErrors: true`는 컨테이너에서 못 찾으면 class-validator 기본 방식으로 fallback한다.

> **주의**: 중복 검사를 validator에서 하면 **검증과 저장 사이 경쟁 조건**이 남는다. UX용 조기 검증으로만 쓰고, 최종 보장은 DB unique 제약과 예외 처리로 해야 한다.

> **주의**: `useContainer`는 `main.ts`에서 호출되므로 `Test.createTestingModule` 기반 테스트에서는 따로 호출해 줘야 한다.

## Mapped types

> **비유**: 기존 DTO를 **복사기로 변형 복사**하는 기능이다. "전부 선택 사항으로"(Partial), "이 칸만"(Pick), "이 칸 빼고"(Omit), "두 장 합치기"(Intersection). 원본에 붙은 검수 스티커(검증 데코레이터)도 함께 복사된다.

```ts
import { IntersectionType, OmitType, PartialType, PickType } from '@nestjs/swagger';

export class CreateUserDto {
  @IsEmail() email!: string;
  @IsString() @Length(8, 64) password!: string;
  @IsString() name!: string;
}

export class UpdateUserDto extends PartialType(OmitType(CreateUserDto, ['password'] as const)) {}

export class LoginDto extends PickType(CreateUserDto, ['email', 'password'] as const) {}

export class AuditDto {
  @IsOptional() @IsString() reason?: string;
}

export class AdminUpdateUserDto extends IntersectionType(UpdateUserDto, AuditDto) {}
```

| 함수 | 결과 | 검증 메타데이터 |
| --- | --- | --- |
| `PartialType(A)` | 모든 필드 optional | 복사 + `@IsOptional` 효과 추가 |
| `PickType(A, keys)` | 지정 필드만 | 해당 필드만 복사 |
| `OmitType(A, keys)` | 지정 필드 제외 | 나머지 복사 |
| `IntersectionType(A, B, ...)` | 필드 합집합 | 양쪽 모두 복사 |

### 어디서 import할까

| 패키지 | 복사하는 메타데이터 | 사용 시점 |
| --- | --- | --- |
| `@nestjs/mapped-types` | class-validator, class-transformer | Swagger 미사용 |
| `@nestjs/swagger` | 위 + `@ApiProperty` 스키마 | Swagger 사용 |
| `@nestjs/graphql` | 위 + GraphQL 타입 메타데이터 | GraphQL InputType |

> **주의**: Swagger를 쓰면서 `@nestjs/mapped-types`에서 `PartialType`을 import하면 **검증은 되지만 문서에서 필드가 사라진다**. 반대로 섞어 쓰면 메타데이터가 일부만 복사되니 한 프로젝트에서 import 경로를 통일하자.

> **포인트**: `as const`를 붙이면 키 배열이 리터럴 튜플로 추론되어 결과 타입이 정확해진다.

## 커스텀 Pipe 작성

```ts
@Injectable()
export class ParseSortPipe implements PipeTransform<string | undefined, SortSpec[]> {
  constructor(private readonly allowed: readonly string[]) {}

  transform(value: string | undefined, metadata: ArgumentMetadata): SortSpec[] {
    if (!value) return [];

    return value.split(',').map((token) => {
      const desc = token.startsWith('-');
      const field = desc ? token.slice(1) : token;
      if (!this.allowed.includes(field)) {
        throw new BadRequestException(`${metadata.data ?? 'sort'}: unknown field "${field}"`);
      }
      return { field, direction: desc ? 'DESC' : 'ASC' };
    });
  }
}

@Get()
list(@Query('sort', new ParseSortPipe(['createdAt', 'price', 'name'])) sort: SortSpec[]) {
  return this.productsService.list({ sort });
}
```

DI가 필요한 Pipe(예: ID로 엔티티를 로드하는 Pipe)는 인스턴스 대신 **클래스**를 넘겨 Nest가 만들게 한다.

```ts
@Injectable()
export class ProductByIdPipe implements PipeTransform<string, Promise<Product>> {
  constructor(private readonly products: ProductsRepository) {}

  async transform(id: string): Promise<Product> {
    const product = await this.products.findById(id);
    if (!product) throw new NotFoundException(`Product ${id} not found`);
    return product;
  }
}

@Get(':id')
findOne(@Param('id', ParseUUIDPipe, ProductByIdPipe) product: Product) {
  return product;
}
```

> **포인트**: `ArgumentMetadata.type`과 `metatype`을 보면 하나의 Pipe가 body/query/param을 구분해 다르게 동작하게 만들 수 있다. `ValidationPipe`도 이 정보로 동작을 분기한다.

## zod 기반 Pipe 대안

> **비유**: class-validator가 **견본 틀에 스티커를 붙이는 방식**이라면, zod는 **규격서를 별도 문서로 작성**하는 방식이다. 규격서에서 타입도 뽑아낼 수 있다.

```ts
import { z, ZodSchema } from 'zod';

export const createProductSchema = z.object({
  name: z.string().min(1).max(100),
  price: z.coerce.number().int().positive(),
  tags: z.array(z.string()).max(10).default([]),
});
export type CreateProductInput = z.infer<typeof createProductSchema>;

export class ZodValidationPipe implements PipeTransform {
  constructor(private readonly schema: ZodSchema) {}

  transform(value: unknown) {
    const result = this.schema.safeParse(value);
    if (!result.success) {
      throw new BadRequestException({
        code: 'VALIDATION_FAILED',
        errors: result.error.issues.map((i) => ({ field: i.path.join('.'), message: i.message })),
      });
    }
    return result.data; // 파싱된(변환된) 값 반환
  }
}

@Post()
create(@Body(new ZodValidationPipe(createProductSchema)) input: CreateProductInput) {
  return this.productsService.create(input);
}
```

| 비교 | class-validator | zod |
| --- | --- | --- |
| 스키마 정의 | 클래스 + 데코레이터 | 함수형 스키마 객체 |
| 타입 | 클래스 자체가 타입 | `z.infer`로 추론 |
| 메타데이터 의존 | O (`emitDecoratorMetadata`) | X |
| 프론트와 스키마 공유 | 어려움 | 쉬움 |
| Swagger 연동 | `@nestjs/swagger` 기본 지원 | 추가 라이브러리 필요(예: `nestjs-zod`) |
| 전역 Pipe 자동 적용 | O (`metatype` 기반) | 파라미터마다 스키마 지정 필요 |

> **포인트**: zod Pipe는 `metatype`을 쓰지 않으므로 전역 `ValidationPipe`처럼 "타입만 선언하면 자동 검증"이 되지 않는다. `nestjs-zod`의 `createZodDto`처럼 스키마를 클래스로 감싸 metatype 기반 자동 적용을 흉내 내는 접근도 있다.

## 셀프 체크

**Q1. `transform: false`인데도 `@Type(() => Number)`가 검증 결과에 영향을 주는 이유는?**

**A.** `ValidationPipe`는 검증을 위해 `transform` 옵션과 무관하게 항상 `plainToInstance`로 인스턴스를 만든 뒤 `validate`를 실행한다. `@Type`은 이 변환 단계에서 적용되므로 검증 결과에 영향을 준다. `transform` 옵션은 그 인스턴스를 핸들러에 넘길지만 결정한다.

**Q2. `enableImplicitConversion: true` 상태에서 `?active=false`가 `true`로 들어오는 이유와 해결책은?**

**A.** 암시적 변환은 `design:type`이 `Boolean`이면 `Boolean(value)`를 호출하는데, `'false'`는 비어 있지 않은 문자열이라 `true`가 된다. `@Transform`에서 `obj[key]`의 원본 문자열을 읽어 `'true'`/`'false'`를 명시적으로 비교해 변환한다.

**Q3. 중첩 DTO 필드에 `@ValidateNested()`만 붙였더니 잘못된 값이 통과한다. 무엇이 빠졌는가?**

**A.** `@Type(() => NestedDto)`가 빠졌다. class-transformer가 중첩 plain object를 해당 클래스 인스턴스로 바꾸지 않으면 class-validator가 읽을 검증 메타데이터가 없다. 특히 배열은 `design:type`이 `Array`라 요소 타입을 알 수 없으므로 `@Type`이 필수다.

**Q4. DB를 조회하는 커스텀 constraint에서 주입받은 repository가 `undefined`다. 원인은?**

**A.** class-validator가 constraint 클래스를 직접 `new`로 생성했기 때문이다. `main.ts`에서 `useContainer(app.select(AppModule), { fallbackOnErrors: true })`를 호출하고, constraint 클래스를 `@Injectable()`과 함께 모듈의 provider로 등록해야 Nest DI 인스턴스가 사용된다.

**Q5. `app.useGlobalPipes()`와 `APP_PIPE` 등록의 차이는?**

**A.** `useGlobalPipes`는 모듈 밖에서 직접 만든 인스턴스를 등록하므로 DI를 받을 수 없고, 하이브리드 앱의 gateway/microservice에는 적용되지 않으며, `main.ts`를 거치지 않는 테스트 앱에도 빠진다. `APP_PIPE`는 provider로 등록되어 DI가 가능하고 모듈 그래프 안에서 전역으로 적용된다.

## 핵심 정리

- Pipe는 핸들러 직전에 인자를 변환하거나 검증하며, 반환값이 그대로 핸들러 인자가 된다. 실패 시 예외로 핸들러 실행을 막는다.
- 내장 Pipe는 파라미터 단위로 조합하며 왼쪽부터 실행된다. `DefaultValuePipe`는 파싱 Pipe 앞에 둔다.
- `ValidationPipe`는 `metatype`(메서드의 `design:paramtypes`)을 기준으로 `plainToInstance` → `validate` 순서로 동작한다. interface나 원시 타입은 검증 대상이 아니다.
- `whitelist` + `forbidNonWhitelisted`로 mass assignment를 막고, `transform`으로 DTO 인스턴스를 받는다. 쿼리 boolean은 암시적 변환 대신 명시적 `@Transform`으로 처리한다.
- 중첩/배열은 `@ValidateNested` + `@Type` 짝, 조건부는 `@ValidateIf`, 커스텀 규칙은 `registerDecorator`나 `ValidatorConstraint` + `useContainer`로 만든다.
- 파생 DTO는 Mapped types로 만들고 Swagger 사용 여부에 따라 `@nestjs/swagger` 또는 `@nestjs/mapped-types`로 import 경로를 통일한다.
- 전역 Pipe는 DI와 테스트 일관성을 위해 `APP_PIPE`로 등록하는 편이 낫고, 스키마 공유가 중요하면 zod 기반 Pipe가 대안이다.

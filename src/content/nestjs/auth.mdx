## 한눈에 보기

- **인증(Authentication)** 은 "누구인가", **인가(Authorization)** 는 "무엇을 할 수 있는가"다. Nest에서는 둘 다 주로 **Guard**로 구현한다.
- Guard는 `canActivate()`가 `true`면 통과, `false`면 `ForbiddenException`(403), 직접 throw하면 그 예외가 응답된다.
- `@nestjs/passport`는 `PassportStrategy`로 전략을 감싸고, `validate()`의 반환값을 `request.user`에 넣어준다. `AuthGuard('jwt')`가 그 전략을 실행한다.
- 실무 표준 패턴은 **전역 JWT guard + `@Public()` 메타데이터 예외 처리 + `RolesGuard`** 조합이다.
- 리소스 소유권(내 글인지)은 guard보다 **서비스 계층**에서 확인하는 것이 대부분 안전하고 단순하다.

## Guard 원리

> **비유**: 건물 출입 게이트다. 카드를 찍으면 문이 열리거나(true), 빨간 불이 켜지거나(false), 경비원이 직접 "출입 금지 구역입니다"라고 안내한다(throw).

Guard는 `CanActivate` 인터페이스를 구현한 provider다. 요청 파이프라인에서 Middleware 다음, Interceptor 이전에 실행된다(순서 상세는 lifecycle 문서).

```ts
import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';
import { Observable } from 'rxjs';

@Injectable()
export class ApiKeyGuard implements CanActivate {
  canActivate(
    context: ExecutionContext,
  ): boolean | Promise<boolean> | Observable<boolean> {
    const req = context.switchToHttp().getRequest();
    return req.headers['x-api-key'] === process.env.API_KEY;
  }
}
```

| 반환 / 동작 | 결과 응답 | 언제 쓰나 |
| --- | --- | --- |
| `true` | 다음 단계로 진행 | 통과 |
| `false` | `403 Forbidden resource` | 권한 없음(기본 메시지로 충분할 때) |
| `throw new UnauthorizedException()` | 401 | 인증 정보가 없거나 잘못됨 |
| `throw new ForbiddenException('...')` | 403 + 커스텀 메시지 | 권한 없음을 구체적으로 알릴 때 |

> **포인트**: Middleware도 인증을 할 수 있지만 "다음에 어떤 핸들러가 실행될지" 모른다. Guard는 `ExecutionContext`로 `getHandler()`, `getClass()`에 접근할 수 있어서 **핸들러에 붙은 메타데이터(`@Roles`, `@Public`)를 읽을 수 있다**. 이것이 Guard가 인가에 적합한 이유다.

> **주의**: `false`는 항상 403이다. 토큰이 없을 때도 `false`를 반환하면 클라이언트는 401이 아니라 403을 받는다. 인증 실패는 `UnauthorizedException`을 직접 throw하자.

## @nestjs/passport 구조

> **비유**: 여러 나라 여권을 심사하는 출입국 사무소다. Passport는 사무소 건물이고, 각 전략(Local, JWT, Google)은 나라별 심사관이다. `@nestjs/passport`는 이 사무소를 Nest 건물 안으로 옮겨온 어댑터다.

구성 요소는 세 가지다.

| 구성 요소 | 역할 |
| --- | --- |
| `PassportStrategy(Strategy, name?)` | passport 전략을 Nest provider로 감싸는 mixin. DI 가능 |
| `validate(...)` | 전략이 자격 증명을 검증한 뒤 호출. 반환값이 `request.user`가 됨 |
| `AuthGuard(name)` | 이름으로 전략을 찾아 실행하는 Guard 팩토리 |

흐름을 단계별로 보면 다음과 같다.

1. 요청이 `@UseGuards(AuthGuard('jwt'))`가 붙은 라우트로 들어온다.
2. `AuthGuard`가 내부적으로 `passport.authenticate('jwt', ...)`를 호출한다.
3. passport-jwt가 헤더에서 토큰을 추출하고 서명/만료를 검증한다.
4. 검증 성공 시 디코딩된 payload로 우리가 작성한 `validate(payload)`를 호출한다.
5. `validate()`가 객체를 반환하면 그 값이 `request.user`에 할당되고 `canActivate`가 `true`가 된다.
6. `validate()`가 `null`/`false`를 반환하거나 throw하면 401이 응답된다.

```bash
npm i @nestjs/passport passport passport-local passport-jwt @nestjs/jwt
npm i -D @types/passport-local @types/passport-jwt
```

> **포인트**: `validate()`의 반환값 설계가 핵심이다. 여기서 반환한 객체 모양이 앱 전체에서 `req.user`의 타입이 된다. DB 엔티티 전체를 넣지 말고 `{ id, email, roles }`처럼 최소한만 담자.

## Local 전략: 로그인

> **비유**: 매표소 창구에서 신분증과 예매번호를 확인하고 입장권(토큰)을 발급하는 단계다.

```ts
// auth/strategies/local.strategy.ts
import { Injectable, UnauthorizedException } from '@nestjs/common';
import { PassportStrategy } from '@nestjs/passport';
import { Strategy } from 'passport-local';

@Injectable()
export class LocalStrategy extends PassportStrategy(Strategy) {
  constructor(private readonly authService: AuthService) {
    super({ usernameField: 'email' }); // 기본값은 username
  }

  async validate(email: string, password: string): Promise<AuthUser> {
    const user = await this.authService.validateUser(email, password);
    if (!user) throw new UnauthorizedException('Invalid credentials');
    return user; // → req.user
  }
}
```

```ts
// auth/auth.service.ts
@Injectable()
export class AuthService {
  constructor(
    private readonly users: UsersService,
    private readonly jwt: JwtService,
  ) {}

  async validateUser(email: string, password: string): Promise<AuthUser | null> {
    const user = await this.users.findByEmail(email);
    if (!user) return null;
    const ok = await bcrypt.compare(password, user.passwordHash);
    return ok ? { id: user.id, email: user.email, roles: user.roles } : null;
  }

  async login(user: AuthUser) {
    const payload = { sub: user.id, email: user.email, roles: user.roles };
    return { accessToken: await this.jwt.signAsync(payload) };
  }
}
```

```ts
// auth/auth.controller.ts
@Controller('auth')
export class AuthController {
  constructor(private readonly authService: AuthService) {}

  @Public()
  @UseGuards(AuthGuard('local'))
  @Post('login')
  @HttpCode(200)
  login(@Req() req: Request & { user: AuthUser }) {
    return this.authService.login(req.user);
  }
}
```

> **주의**: 이메일이 없을 때와 비밀번호가 틀렸을 때 다른 메시지를 주면 계정 존재 여부가 노출된다(user enumeration). 둘 다 같은 401 메시지로 응답하자.

## JWT 전략: 이후 요청 인증

> **비유**: 입장권에 찍힌 홀로그램(서명)만 확인하고 들여보내는 검표원이다. 매번 매표소(DB)에 전화하지 않는다.

```ts
// auth/strategies/jwt.strategy.ts
import { ExtractJwt, Strategy } from 'passport-jwt';

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy, 'jwt') {
  constructor(config: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: config.getOrThrow<string>('JWT_ACCESS_SECRET'),
    });
  }

  // 서명/만료 검증이 끝난 payload가 들어온다
  async validate(payload: JwtPayload): Promise<AuthUser> {
    return { id: payload.sub, email: payload.email, roles: payload.roles };
  }
}
```

```ts
// auth/auth.module.ts
@Module({
  imports: [
    UsersModule,
    PassportModule,
    JwtModule.registerAsync({
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        secret: config.getOrThrow('JWT_ACCESS_SECRET'),
        signOptions: { expiresIn: '15m' },
      }),
    }),
  ],
  providers: [AuthService, LocalStrategy, JwtStrategy],
  controllers: [AuthController],
})
export class AuthModule {}
```

> **포인트**: 전략 클래스는 반드시 `providers`에 등록해야 한다. 생성자에서 `super()`가 호출될 때 passport에 전략이 등록되므로, provider로 인스턴스화되지 않으면 `Unknown authentication strategy "jwt"` 에러가 난다.

### validate()에서 DB를 조회할까

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| payload만 그대로 반환 | 빠름, stateless | 탈퇴/권한 변경이 토큰 만료까지 반영 안 됨 |
| `validate()`에서 DB/캐시 조회 | 즉시 차단 가능 | 매 요청마다 조회 비용 |

짧은 access token(5~15분) + refresh token 조합이면 대개 payload만으로 충분하다. 즉시 차단이 중요한 서비스면 Redis 같은 캐시에서 차단 목록만 확인하는 절충안을 쓴다.

## JwtService 직접 사용

> **비유**: 도장 찍는 기계다. 전략 없이도 필요할 때 토큰을 찍거나(sign) 진위를 확인(verify)할 수 있다.

`@nestjs/jwt`의 `JwtService`는 `jsonwebtoken`을 감싼 provider다.

| 메서드 | 설명 |
| --- | --- |
| `sign(payload, options?)` / `signAsync(...)` | 토큰 발급. options로 `secret`, `expiresIn` 개별 지정 가능 |
| `verify(token, options?)` / `verifyAsync(...)` | 서명/만료 검증 후 payload 반환. 실패 시 throw |
| `decode(token)` | 검증 없이 디코딩만. 신뢰하면 안 됨 |

```ts
// access와 refresh를 다른 secret으로 발급
const accessToken = await this.jwt.signAsync(payload); // 모듈 기본 secret
const refreshToken = await this.jwt.signAsync(
  { sub: user.id, jti: randomUUID() },
  { secret: this.config.getOrThrow('JWT_REFRESH_SECRET'), expiresIn: '14d' },
);
```

## 전역 Guard + @Public() 패턴

> **비유**: 건물 전체에 출입 통제를 걸고, 로비와 화장실처럼 공개 구역에만 "누구나 출입 가능" 스티커를 붙이는 방식이다. 새 방을 만들면 기본으로 잠겨 있으니 실수로 열어둘 일이 없다.

라우트마다 `@UseGuards(JwtAuthGuard)`를 붙이면 하나쯤 빼먹기 쉽다. **기본 잠금(secure by default)** 으로 뒤집자.

### 1단계: 메타데이터 데코레이터

```ts
// auth/decorators/public.decorator.ts
import { SetMetadata } from '@nestjs/common';

export const IS_PUBLIC_KEY = 'isPublic';
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);
```

### 2단계: AuthGuard 확장

```ts
// auth/guards/jwt-auth.guard.ts
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private readonly reflector: Reflector) {
    super();
  }

  canActivate(context: ExecutionContext) {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(), // 메서드 메타데이터 우선
      context.getClass(),   // 없으면 클래스 메타데이터
    ]);
    if (isPublic) return true;
    return super.canActivate(context);
  }

  // 에러 메시지/형태를 바꾸고 싶을 때 오버라이드
  handleRequest<TUser = AuthUser>(err: unknown, user: TUser, info: unknown): TUser {
    if (err || !user) {
      throw err instanceof Error ? err : new UnauthorizedException('Invalid or expired token');
    }
    return user;
  }
}
```

### 3단계: APP_GUARD로 전역 등록

```ts
@Module({
  providers: [
    { provide: APP_GUARD, useClass: JwtAuthGuard },
    { provide: APP_GUARD, useClass: RolesGuard },
  ],
})
export class AppModule {}
```

> **포인트**: `APP_GUARD`로 등록하면 Guard가 DI 컨테이너에서 생성되므로 `Reflector`, `ConfigService` 주입이 된다. `app.useGlobalGuards(new JwtAuthGuard(...))`는 의존성을 직접 넘겨야 해서 불편하다.

`Reflector` 메서드 선택 기준은 다음과 같다(메타데이터 상세는 decorators-metadata 문서).

| 메서드 | 동작 | 용도 |
| --- | --- | --- |
| `get(key, target)` | 단일 대상에서 조회 | 한 곳만 볼 때 |
| `getAllAndOverride(key, targets)` | 첫 번째로 값이 있는 대상 반환 | `@Public`, `@Roles` 덮어쓰기 |
| `getAllAndMerge(key, targets)` | 배열/객체를 병합 | 클래스 + 메서드 권한 합치기 |

## RBAC: RolesGuard + @Roles

> **비유**: 사원증 색깔별로 들어갈 수 있는 층이 정해진 건물이다. 문 앞의 리더기는 사원증 색만 보고 판단한다.

```ts
// auth/decorators/roles.decorator.ts
export enum Role {
  User = 'user',
  Admin = 'admin',
}

export const ROLES_KEY = 'roles';
export const Roles = (...roles: Role[]) => SetMetadata(ROLES_KEY, roles);
```

Nest v10 이상에서는 `Reflector.createDecorator`로 타입 안전한 데코레이터를 만들 수도 있다.

```ts
export const Roles = Reflector.createDecorator<Role[]>();
// guard에서: this.reflector.get(Roles, context.getHandler())
```

```ts
// auth/guards/roles.guard.ts
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<Role[]>(ROLES_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (!required || required.length === 0) return true; // 역할 제한 없음

    const { user } = context.switchToHttp().getRequest();
    if (!user) return false;
    return required.some((role) => user.roles?.includes(role));
  }
}
```

```ts
@Controller('admin/users')
@Roles(Role.Admin)
export class AdminUsersController {
  @Get()
  list() { /* admin만 */ }

  @Get('stats')
  @Roles(Role.Admin, Role.User) // getAllAndOverride라 메서드 값이 우선
  stats() { /* admin 또는 user */ }
}
```

> **주의**: `RolesGuard`는 `request.user`가 이미 채워져 있다고 가정한다. 반드시 JWT guard **뒤에** 실행되어야 한다. 순서는 아래 절에서 다룬다.

## 리소스 소유권 체크는 어디서

> **비유**: 사원증으로 "3층 출입 가능"은 게이트에서 확인하지만, "3층 312호 서랍이 네 것인가"는 서랍을 열어 봐야 안다.

"자기 글만 수정 가능" 같은 규칙은 리소스를 조회해야 판단할 수 있다.

| 위치 | 장점 | 단점 |
| --- | --- | --- |
| Guard | 선언적, 핸들러 진입 전 차단 | 리소스를 guard에서 한 번, 서비스에서 또 한 번 조회. 파라미터 파싱 중복 |
| Service | 조회 한 번으로 검증 + 처리, 트랜잭션 안에서 일관성 | 각 서비스 메서드에 명시적으로 작성 |
| Repository 쿼리 조건 | `where: { id, authorId }`로 원천 차단 | 403과 404 구분이 어려움 |

```ts
@Injectable()
export class PostService {
  async update(postId: string, actor: AuthUser, dto: UpdatePostDto) {
    const post = await this.posts.findById(postId);
    if (!post) throw new NotFoundException();
    if (post.authorId !== actor.id && !actor.roles.includes(Role.Admin)) {
      throw new ForbiddenException('Not the owner');
    }
    return this.posts.save(Object.assign(post, dto));
  }
}
```

> **포인트**: 역할(role)처럼 요청만 보고 판단 가능한 것은 Guard, 데이터를 봐야 판단 가능한 것은 Service. 이 구분이 가장 실용적이다. 규칙이 복잡해지면 아래 CASL을 고려한다.

## Access/Refresh 토큰 회전 전략

> **비유**: 놀이공원 1일 입장 팔찌(access)와 재입장권(refresh)이다. 팔찌는 짧게 유효하고, 재입장권은 한 번 쓰면 회수되고 새 재입장권이 발급된다. 누군가 이미 회수된 재입장권을 내밀면 도난으로 판단한다.

| 토큰 | 수명 | 저장 위치(웹) | 서버 상태 |
| --- | --- | --- | --- |
| Access | 5~15분 | 메모리 | stateless |
| Refresh | 7~30일 | `HttpOnly`, `Secure`, `SameSite` 쿠키 | DB/Redis에 해시 저장 |

회전(rotation) 흐름은 다음과 같다.

1. 로그인 시 access + refresh를 발급하고 refresh의 해시와 `jti`, `familyId`를 저장한다.
2. access 만료 → 클라이언트가 `/auth/refresh`에 refresh 토큰을 보낸다.
3. 서버는 서명을 검증하고, 저장된 해시와 비교한다.
4. 일치하면 기존 refresh를 폐기하고 **새 access + 새 refresh**를 발급한다.
5. 이미 폐기된 refresh가 들어오면 탈취로 간주하고 같은 `familyId`의 토큰을 전부 폐기한다(reuse detection).

```ts
@Injectable()
export class JwtRefreshStrategy extends PassportStrategy(Strategy, 'jwt-refresh') {
  constructor(config: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromExtractors([(req: Request) => req?.cookies?.refresh_token]),
      secretOrKey: config.getOrThrow('JWT_REFRESH_SECRET'),
      passReqToCallback: true, // validate에 req 전달
    });
  }

  validate(req: Request, payload: RefreshPayload) {
    return { id: payload.sub, jti: payload.jti, familyId: payload.fid, raw: req.cookies.refresh_token };
  }
}
```

```ts
@Public()
@UseGuards(AuthGuard('jwt-refresh'))
@Post('refresh')
async refresh(@Req() req, @Res({ passthrough: true }) res: Response) {
  const { accessToken, refreshToken } = await this.authService.rotate(req.user);
  res.cookie('refresh_token', refreshToken, {
    httpOnly: true, secure: true, sameSite: 'strict', path: '/auth/refresh',
  });
  return { accessToken };
}
```

```ts
async rotate(user: RefreshUser) {
  const stored = await this.tokens.findByJti(user.jti);
  if (!stored || stored.revokedAt) {
    await this.tokens.revokeFamily(user.familyId); // 재사용 감지
    throw new UnauthorizedException('Refresh token reused');
  }
  if (!(await bcrypt.compare(user.raw, stored.hash))) throw new UnauthorizedException();

  await this.tokens.revoke(user.jti);
  return this.issueTokens(user.id, user.familyId);
}
```

> **주의**: `@Public()`을 빼먹으면 전역 JWT guard가 만료된 access token 때문에 refresh 요청 자체를 막는다. refresh 엔드포인트는 전역 guard를 우회하고 refresh 전략 guard만 걸어야 한다.

## Guard 순서와 여러 Guard 조합

> **비유**: 공항에서 여권 심사(인증) 다음에 탑승권 등급 확인(인가)을 한다. 순서가 바뀌면 신원도 모르는 사람의 등급을 확인하는 꼴이다.

실행 순서 규칙은 다음과 같다.

1. 전역 guard → controller guard → method guard 순.
2. 같은 레벨 안에서는 **배열/등록 순서대로** 실행된다.
3. 하나라도 `false`이거나 throw하면 즉시 중단되고 이후 guard는 실행되지 않는다(AND 조건).

```ts
// 전역: 등록 순서 = 실행 순서
providers: [
  { provide: APP_GUARD, useClass: JwtAuthGuard }, // 1
  { provide: APP_GUARD, useClass: RolesGuard },   // 2
]

// 라우트 레벨: 왼쪽부터
@UseGuards(ThrottlerGuard, FeatureFlagGuard)
```

OR 조건(예: API key 또는 JWT 중 하나)은 기본 제공되지 않는다. `AuthGuard`는 여러 전략 이름을 배열로 받으면 순서대로 시도하다가 하나가 성공하면 통과시킨다.

```ts
@UseGuards(AuthGuard(['jwt', 'api-key'])) // 둘 중 하나 성공 시 통과
```

> **포인트**: 커스텀 guard끼리의 OR이 필요하면 guard 하나를 만들어 내부에서 다른 guard 인스턴스들을 순서대로 호출하는 composite guard로 구현한다.

## Passport 없이 직접 구현

> **비유**: 출입국 사무소(passport)를 쓰지 않고 직접 검표원을 고용하는 것이다. 규칙이 하나뿐이면 오히려 간단하다.

```ts
@Injectable()
export class SimpleJwtGuard implements CanActivate {
  constructor(private readonly jwt: JwtService, private readonly reflector: Reflector) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(), context.getClass(),
    ]);
    if (isPublic) return true;

    const req = context.switchToHttp().getRequest();
    const [type, token] = req.headers.authorization?.split(' ') ?? [];
    if (type !== 'Bearer' || !token) throw new UnauthorizedException();

    try {
      const payload = await this.jwt.verifyAsync<JwtPayload>(token);
      req.user = { id: payload.sub, email: payload.email, roles: payload.roles };
      return true;
    } catch {
      throw new UnauthorizedException('Invalid or expired token');
    }
  }
}
```

| 항목 | `@nestjs/passport` | 직접 구현 Guard |
| --- | --- | --- |
| 의존성 | passport + 전략 패키지 | `@nestjs/jwt`만 |
| OAuth(Google, GitHub 등) | 전략 패키지로 즉시 사용 | 직접 구현 부담 큼 |
| 코드 추적 | mixin, 콜백 구조로 다소 간접적 | 한 파일에서 전부 보임 |
| 다중 전략 OR | `AuthGuard([...])` 지원 | 직접 작성 |
| 추천 상황 | 소셜 로그인, 다양한 전략 | JWT 하나만 쓰는 API |

## WebSocket/GraphQL 컨텍스트에서의 Guard

> **비유**: 같은 검표원이 기차역(HTTP), 지하철(WebSocket), 버스(GraphQL)에 배치된다. 표를 꺼내는 주머니 위치만 다르다.

`AuthGuard`는 내부적으로 `getRequest(context)`를 호출해 request 객체를 얻는다. 기본 구현은 `context.switchToHttp().getRequest()`이므로 다른 컨텍스트에서는 오버라이드해야 한다.

### GraphQL

```ts
import { GqlExecutionContext } from '@nestjs/graphql';

@Injectable()
export class GqlAuthGuard extends AuthGuard('jwt') {
  getRequest(context: ExecutionContext) {
    const ctx = GqlExecutionContext.create(context);
    return ctx.getContext().req; // GraphQLModule context에 req를 넣어둬야 함
  }
}
```

```ts
GraphQLModule.forRoot<ApolloDriverConfig>({
  driver: ApolloDriver,
  context: ({ req }) => ({ req }),
});
```

현재 사용자 추출 데코레이터도 컨텍스트 분기가 필요하다.

```ts
export const CurrentUser = createParamDecorator((_: unknown, context: ExecutionContext) => {
  if (context.getType<GqlContextType>() === 'graphql') {
    return GqlExecutionContext.create(context).getContext().req.user;
  }
  return context.switchToHttp().getRequest().user;
});
```

### WebSocket

WebSocket은 연결 후 메시지마다 HTTP 헤더가 없다. 보통 **핸드셰이크 시점에 한 번 인증**하고, 메시지 핸들러의 guard는 소켓에 저장된 사용자를 확인한다.

```ts
@Injectable()
export class WsJwtGuard implements CanActivate {
  constructor(private readonly jwt: JwtService) {}

  canActivate(context: ExecutionContext): boolean {
    const client = context.switchToWs().getClient<Socket>();
    const token = client.handshake.auth?.token;
    try {
      client.data.user = this.jwt.verify(token);
      return true;
    } catch {
      throw new WsException('Unauthorized'); // HttpException이 아니라 WsException
    }
  }
}
```

> **주의**: 전역 `APP_GUARD`는 gateway에도 적용된다. HTTP 전용 guard가 `switchToHttp()`를 무조건 호출하면 WebSocket 이벤트에서 깨지므로 `context.getType()`으로 분기하거나 HTTP가 아니면 통과시키는 처리가 필요하다.

## CASL 간단 소개

> **비유**: 역할별 출입 층 목록(RBAC) 대신, "본인이 작성하고 아직 게시되지 않은 문서는 수정 가능" 같은 문장형 규정집을 두는 것이다.

RBAC은 "admin은 모든 것"처럼 역할 단위다. 조건이 필드 값에 따라 달라지면 **ABAC(속성 기반)** 이 필요하고, CASL(`@casl/ability`)이 Nest 문서에서도 소개하는 대표 라이브러리다.

```ts
@Injectable()
export class CaslAbilityFactory {
  createForUser(user: AuthUser) {
    const { can, cannot, build } = new AbilityBuilder(createMongoAbility);

    if (user.roles.includes(Role.Admin)) {
      can('manage', 'all');
    } else {
      can('read', 'Post');
      can('update', 'Post', { authorId: user.id, published: false });
      cannot('delete', 'Post');
    }
    return build();
  }
}
```

```ts
// 서비스에서 리소스 조회 후 판단
const ability = this.caslFactory.createForUser(actor);
if (ability.cannot('update', subject('Post', post))) throw new ForbiddenException();
```

> **포인트**: CASL도 결국 "리소스를 봐야 판단"하는 규칙이 대부분이라 서비스 계층에서 쓰는 경우가 많다. Guard에서는 "이 사용자가 Post를 update할 가능성이 있는가" 정도의 1차 필터만 하는 policy guard 패턴을 쓴다.

## 셀프 체크

**Q1. 토큰이 없는 요청에 대해 Guard가 `false`를 반환하면 어떤 상태 코드가 나가며, 무엇이 더 적절한가?**

**A.** `false`는 항상 403 `ForbiddenException`이 된다. 인증 정보가 없는 경우는 401이 의미상 맞으므로 `UnauthorizedException`을 직접 throw해야 한다.

**Q2. `JwtStrategy.validate()`가 반환한 값은 어디로 가는가?**

**A.** passport가 그 값을 `request.user`에 할당한다. 이후 컨트롤러의 `@Req()`나 커스텀 `@CurrentUser()` 데코레이터, 다음 순서의 `RolesGuard`가 이 값을 사용한다.

**Q3. 전역 JWT guard를 쓰면서 로그인 엔드포인트를 열어두려면 어떻게 하나?**

**A.** `SetMetadata(IS_PUBLIC_KEY, true)`로 `@Public()` 데코레이터를 만들고, 전역 guard에서 `Reflector.getAllAndOverride`로 handler와 class 메타데이터를 확인해 `true`면 바로 통과시킨다.

**Q4. GraphQL resolver에 `AuthGuard('jwt')`를 그대로 붙이면 왜 동작하지 않는가?**

**A.** `AuthGuard`는 기본적으로 `switchToHttp().getRequest()`로 request를 찾는데, GraphQL 실행 컨텍스트에서는 request가 GraphQL context 안에 있다. `getRequest()`를 오버라이드해 `GqlExecutionContext.create(context).getContext().req`를 반환해야 한다.

**Q5. refresh token 회전에서 이미 폐기된 refresh token이 들어오면 어떻게 처리해야 하는가?**

**A.** 토큰 탈취 가능성으로 보고 해당 토큰 family 전체를 폐기한 뒤 401을 반환한다. 정상 사용자도 다시 로그인해야 하지만 공격자의 세션도 함께 끊긴다.

## 핵심 정리

- Guard는 `canActivate`로 true/false/throw를 결정하며, `ExecutionContext`로 핸들러 메타데이터를 읽을 수 있어 인가에 적합하다.
- `@nestjs/passport`는 `PassportStrategy` mixin으로 전략을 provider화하고, `validate()` 반환값을 `request.user`에 넣는다.
- Local 전략으로 로그인 → `JwtService`로 토큰 발급 → JWT 전략으로 이후 요청 인증이 기본 흐름이다.
- 전역 `APP_GUARD` + `@Public()` 메타데이터로 secure by default를 만든다.
- `RolesGuard`는 JWT guard 뒤에 실행되어야 하며, 같은 레벨에서는 등록 순서대로 AND로 동작한다.
- 리소스 소유권 같은 데이터 기반 판단은 서비스 계층에서 하는 것이 실용적이다.
- Access는 짧게, Refresh는 HttpOnly 쿠키 + 회전 + 재사용 감지로 관리한다.
- GraphQL은 `getRequest()` 오버라이드, WebSocket은 핸드셰이크 인증 + `WsException`.

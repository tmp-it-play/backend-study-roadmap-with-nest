## 한눈에 보기

- Nest에는 **내장 exception layer**가 있어서, 어디서 throw하든 처리되지 않은 예외는 결국 JSON 에러 응답으로 바뀐다.
- `HttpException`은 `response`(본문), `status`, `options.cause`, `options.description`으로 구성된다. 내장 하위 클래스(`NotFoundException` 등)를 쓰면 대부분 해결된다.
- 서비스 계층은 **도메인 예외**만 던지고, HTTP로의 변환은 **ExceptionFilter**가 담당하게 분리하는 것이 깔끔하다.
- Filter는 `@Catch()`로 잡을 타입을 고르고, `ArgumentsHost`로 컨텍스트(HTTP/RPC/WS)를 꺼낸다. 전역 등록은 DI가 되는 `APP_FILTER`를 선호한다.
- 운영에서는 응답 포맷을 통일하고, 5xx는 로깅하되 스택은 클라이언트에 노출하지 않는다.

## 내장 exception layer

> **비유**: 건물 1층에 있는 종합 안내 데스크다. 어느 층에서 문제가 생기든 처리되지 않은 민원은 결국 1층 데스크로 내려오고, 데스크는 정해진 양식의 답변서를 돌려준다.

Nest는 요청 처리 중 발생한 예외를 잡아 응답으로 바꿔주는 전역 필터를 기본 내장하고 있다. 별도 설정이 없어도 다음처럼 동작한다.

1. 컨트롤러/서비스/가드/파이프 등 어디서든 예외가 throw된다.
2. 가장 가까운 ExceptionFilter를 찾는다. 사용자 필터가 없으면 내장 global filter(`BaseExceptionFilter`)가 처리한다.
3. 예외가 `HttpException`(또는 그 하위 클래스)이면 `getStatus()`와 `getResponse()`로 응답을 만든다.
4. 그 외의 예외(`Error`, `TypeError` 등)는 **알 수 없는 예외**로 보고 500을 응답한다.

```json
{
  "statusCode": 500,
  "message": "Internal server error"
}
```

> **포인트**: 인식되지 않는 예외는 메시지를 숨기고 무조건 `Internal server error`로 응답한다. 내부 에러 메시지가 실수로 클라이언트에 새어 나가지 않도록 기본값이 안전하게 설계되어 있다.

> **주의**: `http-errors` 라이브러리의 에러처럼 `statusCode`와 `message` 속성을 가진 객체도 내장 필터가 부분적으로 인식한다. 의도치 않게 그런 모양의 객체를 throw하면 상태 코드가 예상과 달라질 수 있다.

## HttpException 구조

> **비유**: 택배 반송 전표다. 반송 사유(본문), 반송 코드(status), 내부 추적용 원인(cause), 사유 요약(description)이 한 장에 적혀 있다.

```ts
new HttpException(response, status, options?)
```

| 구성 요소 | 타입 | 역할 |
| --- | --- | --- |
| `response` | `string \| object` | 응답 본문. 문자열이면 `message`로 들어가고, 객체면 그대로 직렬화된다 |
| `status` | `number` | HTTP 상태 코드. `HttpStatus` enum 사용 권장 |
| `options.cause` | `unknown` | 원인 에러. 응답에는 안 나가고 로깅/디버깅용 |
| `options.description` | `string` | 내장 하위 클래스에서 `error` 필드로 들어가는 짧은 설명 |

```ts
import { HttpException, HttpStatus } from '@nestjs/common';

// 1) 문자열 response
throw new HttpException('Forbidden', HttpStatus.FORBIDDEN);
// → { "statusCode": 403, "message": "Forbidden" }

// 2) 객체 response: 본문 전체를 직접 제어
throw new HttpException(
  { status: HttpStatus.FORBIDDEN, error: 'custom message', code: 'NO_PERMISSION' },
  HttpStatus.FORBIDDEN,
  { cause: originalError },
);
```

`response`가 객체면 Nest는 그 객체를 **그대로** 응답 본문으로 쓴다. `statusCode` 필드를 자동으로 넣어주지 않으므로 필요하면 직접 포함해야 한다.

```ts
try {
  await this.paymentGateway.charge(dto);
} catch (error) {
  throw new HttpException('Payment failed', HttpStatus.BAD_GATEWAY, {
    cause: error, // 원인 체인 보존
  });
}
```

> **포인트**: `cause`는 응답에 직렬화되지 않는다. 필터에서 `exception.cause`를 꺼내 로그로 남기는 용도다. 원인 체인을 잃지 않는 것이 운영 디버깅에서 큰 차이를 만든다.

## 내장 예외 클래스

> **비유**: 자주 쓰는 반송 사유를 미리 인쇄해 둔 도장 세트다. 매번 손으로 쓰지 않고 맞는 도장을 찍으면 된다.

`@nestjs/common`이 제공하는 `HttpException` 하위 클래스들이다.

| 클래스 | status | 주 사용처 |
| --- | --- | --- |
| `BadRequestException` | 400 | 입력값 오류, ValidationPipe 실패 |
| `UnauthorizedException` | 401 | 인증 실패(토큰 없음/만료) |
| `ForbiddenException` | 403 | 인증은 됐지만 권한 없음. Guard가 false 반환 시 기본값 |
| `NotFoundException` | 404 | 리소스 없음 |
| `MethodNotAllowedException` | 405 | 허용되지 않은 메서드 |
| `NotAcceptableException` | 406 | 협상 불가한 응답 형식 |
| `RequestTimeoutException` | 408 | 처리 시간 초과 |
| `ConflictException` | 409 | 중복 키, 상태 충돌 |
| `GoneException` | 410 | 영구 삭제된 리소스 |
| `PayloadTooLargeException` | 413 | 업로드 용량 초과 |
| `UnsupportedMediaTypeException` | 415 | Content-Type 미지원 |
| `UnprocessableEntityException` | 422 | 형식은 맞지만 의미상 처리 불가 |
| `InternalServerErrorException` | 500 | 서버 내부 오류 |
| `NotImplementedException` | 501 | 미구현 |
| `BadGatewayException` | 502 | 외부 의존 서비스 오류 |
| `ServiceUnavailableException` | 503 | 점검, 과부하 |
| `GatewayTimeoutException` | 504 | 외부 의존 서비스 타임아웃 |

하위 클래스는 첫 인자로 메시지(또는 객체), 두 번째 인자로 `cause`/`description` 옵션을 받는다.

```ts
throw new NotFoundException('Order not found', {
  cause: new Error('row missing'),
  description: 'ORDER_NOT_FOUND',
});
// → { "message": "Order not found", "error": "ORDER_NOT_FOUND", "statusCode": 404 }
```

## 커스텀 도메인 예외 설계

> **비유**: 주방(서비스)은 "재료 소진"이라고만 말하고, 홀 직원(필터)이 손님에게 "죄송합니다, 품절입니다"라고 번역해서 전달한다. 주방이 손님 응대 매너까지 알 필요는 없다.

서비스 계층에서 `NotFoundException`을 직접 던지면 편하지만, 서비스가 HTTP에 묶인다. 같은 서비스를 마이크로서비스 핸들러, 배치 작업, CLI에서 재사용하면 HTTP 예외가 어색해진다.

### 1단계: 도메인 예외 계층 정의

```ts
// domain/errors/domain.error.ts
export abstract class DomainError extends Error {
  abstract readonly code: string;

  constructor(message: string, readonly details?: Record<string, unknown>) {
    super(message);
    this.name = new.target.name;
  }
}

export class EntityNotFoundError extends DomainError {
  readonly code = 'ENTITY_NOT_FOUND';
  constructor(entity: string, id: string | number) {
    super(`${entity} ${id} not found`, { entity, id });
  }
}

export class BusinessRuleViolationError extends DomainError {
  readonly code = 'BUSINESS_RULE_VIOLATION';
}

export class InsufficientStockError extends BusinessRuleViolationError {
  readonly code = 'INSUFFICIENT_STOCK';
}
```

### 2단계: 서비스는 도메인 예외만 던진다

```ts
@Injectable()
export class OrderService {
  constructor(private readonly orders: OrderRepository) {}

  async cancel(orderId: string) {
    const order = await this.orders.findById(orderId);
    if (!order) throw new EntityNotFoundError('Order', orderId);
    if (order.status === 'SHIPPED') {
      throw new BusinessRuleViolationError('Shipped order cannot be cancelled');
    }
    order.cancel();
    await this.orders.save(order);
  }
}
```

### 3단계: 필터에서 HTTP로 매핑

```ts
const DOMAIN_STATUS_MAP = new Map<Function, number>([
  [EntityNotFoundError, HttpStatus.NOT_FOUND],
  [InsufficientStockError, HttpStatus.CONFLICT],
  [BusinessRuleViolationError, HttpStatus.UNPROCESSABLE_ENTITY],
]);

@Catch(DomainError)
export class DomainExceptionFilter implements ExceptionFilter {
  catch(exception: DomainError, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse<Response>();
    const status = this.resolveStatus(exception);

    res.status(status).json({
      statusCode: status,
      code: exception.code,
      message: exception.message,
      details: exception.details,
    });
  }

  private resolveStatus(exception: DomainError): number {
    // 프로토타입 체인을 따라 올라가며 가장 구체적인 매핑을 찾는다
    let proto = Object.getPrototypeOf(exception);
    while (proto && proto !== Error.prototype) {
      const status = DOMAIN_STATUS_MAP.get(proto.constructor);
      if (status) return status;
      proto = Object.getPrototypeOf(proto);
    }
    return HttpStatus.BAD_REQUEST;
  }
}
```

> **포인트**: 도메인 예외 → HTTP 매핑 표가 한 파일에 모이면, "이 에러는 몇 번 코드로 나가지?"라는 질문에 한 곳만 보면 된다. 서비스 테스트도 HTTP 개념 없이 작성할 수 있다.

| 접근 | 장점 | 단점 |
| --- | --- | --- |
| 서비스에서 `HttpException` 직접 throw | 빠르고 단순 | 서비스가 HTTP에 결합, RPC/배치 재사용 어려움 |
| 도메인 예외 + 필터 매핑 | 계층 분리, 매핑 일원화 | 클래스와 매핑 표 관리 비용 |

작은 CRUD 앱이면 첫 번째로 충분하다. 도메인 로직이 두꺼워지거나 여러 transport를 쓰면 두 번째로 넘어가자.

## ExceptionFilter 기본

> **비유**: 특정 종류의 민원만 받는 전담 창구다. `@Catch()`에 적힌 민원 종류만 이 창구로 온다.

```ts
import { ArgumentsHost, Catch, ExceptionFilter, HttpException } from '@nestjs/common';
import type { Request, Response } from 'express';

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const res = ctx.getResponse<Response>();
    const req = ctx.getRequest<Request>();
    const status = exception.getStatus();

    res.status(status).json({
      statusCode: status,
      path: req.url,
      timestamp: new Date().toISOString(),
      message: exception.getResponse(),
    });
  }
}
```

동작 순서를 정리하면 다음과 같다.

1. 예외가 throw되면 Nest는 해당 라우트에 바인딩된 필터를 **route → controller → global** 순으로 찾는다.
2. 각 필터의 `@Catch()` 메타데이터와 예외 타입을 `instanceof`로 비교한다.
3. 처음 매칭되는 필터 **하나만** 실행된다. 필터끼리 체이닝되지 않는다.
4. 필터는 응답을 직접 써야 한다. 아무것도 안 쓰면 요청이 hang된다.

`ArgumentsHost`는 transport 독립적인 인자 래퍼다.

| 메서드 | 반환 | 용도 |
| --- | --- | --- |
| `host.getType()` | `'http' \| 'rpc' \| 'ws'` (GraphQL은 `'graphql'`) | 현재 컨텍스트 판별 |
| `host.switchToHttp()` | `HttpArgumentsHost` | `getRequest()`, `getResponse()`, `getNext()` |
| `host.switchToRpc()` | `RpcArgumentsHost` | `getData()`, `getContext()` |
| `host.switchToWs()` | `WsArgumentsHost` | `getClient()`, `getData()` |

> **주의**: `@Catch(A, B)`처럼 여러 타입을 나열할 수 있다. 하지만 필터 클래스 하나에 너무 많은 분기를 넣으면 결국 거대한 switch 문이 된다. 관심사별로 필터를 나누는 편이 낫다.

## catch-all 필터

> **비유**: 어떤 전담 창구에도 해당하지 않는 민원을 받는 "기타 민원" 창구다.

`@Catch()`를 인자 없이 쓰면 모든 예외를 잡는다.

```ts
@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger(AllExceptionsFilter.name);

  catch(exception: unknown, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse<Response>();
    const status =
      exception instanceof HttpException
        ? exception.getStatus()
        : HttpStatus.INTERNAL_SERVER_ERROR;

    if (status >= 500) {
      this.logger.error(exception, (exception as Error)?.stack);
    }

    res.status(status).json({
      statusCode: status,
      message: status >= 500 ? 'Internal server error' : (exception as HttpException).message,
    });
  }
}
```

> **주의**: catch-all 필터가 위 코드처럼 `switchToHttp()`를 무조건 호출하면, 같은 앱에 마이크로서비스나 WebSocket 핸들러가 섞여 있을 때 깨진다. `host.getType()`으로 분기하거나 다음 절의 `HttpAdapterHost` 방식을 쓰자.

## BaseExceptionFilter 상속

> **비유**: 기본 응대 매뉴얼은 그대로 따르되, 특정 상황에서만 한 줄을 덧붙이는 직원이다.

기본 동작은 유지하면서 로깅이나 일부 예외만 바꾸고 싶다면 `BaseExceptionFilter`를 상속하고 `super.catch()`를 호출한다.

```ts
import { BaseExceptionFilter } from '@nestjs/core';

@Catch()
export class SentryExceptionFilter extends BaseExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    if (!(exception instanceof HttpException) || exception.getStatus() >= 500) {
      Sentry.captureException(exception);
    }
    super.catch(exception, host); // 기본 응답 로직 위임
  }
}
```

등록 방식에 따라 `httpAdapter` 주입 방법이 다르다.

```ts
// main.ts에서 직접 생성하는 경우: httpAdapter를 넘겨야 한다
const { httpAdapter } = app.get(HttpAdapterHost);
app.useGlobalFilters(new SentryExceptionFilter(httpAdapter));
```

```ts
// APP_FILTER로 등록하면 Nest가 알아서 주입한다
@Module({
  providers: [{ provide: APP_FILTER, useClass: SentryExceptionFilter }],
})
export class AppModule {}
```

> **주의**: `BaseExceptionFilter`를 상속한 필터를 컨트롤러/메서드 레벨에서 `new`로 생성해서 붙이면 안 된다. 클래스 참조(`@UseFilters(SentryExceptionFilter)`)로 넘겨 프레임워크가 인스턴스를 만들게 하자.

## HttpAdapterHost로 플랫폼 독립 필터

> **비유**: 어느 나라 우체국을 쓰든 동일한 송장 양식을 쓰는 국제 택배 회사다. Express든 Fastify든 응답을 보내는 방법을 추상화한다.

`res.status().json()`은 Express API다. Fastify에서는 `reply.code().send()`를 쓴다. `HttpAdapterHost`를 쓰면 이 차이를 숨길 수 있다.

```ts
@Catch()
export class GlobalExceptionFilter implements ExceptionFilter {
  constructor(private readonly adapterHost: HttpAdapterHost) {}

  catch(exception: unknown, host: ArgumentsHost) {
    // 생성자 시점에는 httpAdapter가 아직 없을 수 있어서 catch 안에서 꺼낸다
    const { httpAdapter } = this.adapterHost;
    const ctx = host.switchToHttp();

    const status =
      exception instanceof HttpException
        ? exception.getStatus()
        : HttpStatus.INTERNAL_SERVER_ERROR;

    const body = {
      statusCode: status,
      path: httpAdapter.getRequestUrl(ctx.getRequest()),
      timestamp: new Date().toISOString(),
    };

    httpAdapter.reply(ctx.getResponse(), body, status);
  }
}
```

> **포인트**: Fastify 전환 가능성이 있거나 라이브러리처럼 재사용할 필터라면 처음부터 `httpAdapter.reply()`로 작성하자. Fastify 전환 자체는 tips 문서를 참고.

## 바인딩 범위와 우선순위

> **비유**: 민원은 가장 가까운 창구(해당 층)부터 찾고, 없으면 상위 층, 마지막에 1층 종합 데스크로 간다. 한 번 처리되면 다른 창구로 넘어가지 않는다.

| 범위 | 방법 | DI | 우선순위 |
| --- | --- | --- | --- |
| Method | `@UseFilters(XFilter)` on handler | O | 가장 높음 |
| Controller | `@UseFilters(XFilter)` on class | O | 중간 |
| Global (provider) | `{ provide: APP_FILTER, useClass: XFilter }` | O | 낮음 |
| Global (main.ts) | `app.useGlobalFilters(new XFilter())` | X | 낮음 |
| 내장 | `BaseExceptionFilter` | - | 최후 |

```ts
@Controller('orders')
@UseFilters(DomainExceptionFilter) // controller 범위
export class OrderController {
  @Post(':id/cancel')
  @UseFilters(PaymentExceptionFilter) // method 범위, 먼저 검사됨
  cancel(@Param('id') id: string) {
    return this.orderService.cancel(id);
  }
}
```

### 여러 전역 필터를 등록할 때

`APP_FILTER`를 여러 개 등록하면 **나중에 등록된 것이 먼저** 검사된다. 그래서 catch-all을 먼저, 구체적인 필터를 나중에 등록해야 의도대로 동작한다.

```ts
@Module({
  providers: [
    { provide: APP_FILTER, useClass: AllExceptionsFilter },   // 마지막에 검사
    { provide: APP_FILTER, useClass: DomainExceptionFilter }, // 먼저 검사
  ],
})
export class AppModule {}
```

> **주의**: 순서를 반대로 하면 catch-all이 모든 예외를 먼저 가져가서 `DomainExceptionFilter`는 영영 호출되지 않는다. 헷갈리면 필터를 하나로 합치고 내부에서 분기하는 것도 방법이다.

### APP_FILTER vs useGlobalFilters

| 항목 | `APP_FILTER` | `app.useGlobalFilters()` |
| --- | --- | --- |
| 생성자 주입 | O (`Logger`, `ConfigService` 등) | X (직접 `new`) |
| hybrid app(마이크로서비스 연결) | 적용됨 | 기본적으로 gateway/microservice에 미적용 |
| e2e 테스트 앱 | 모듈 import만 하면 자동 적용 | 테스트에서 다시 호출해야 함 |

> **포인트**: 대부분 `APP_FILTER`가 정답이다. 어느 모듈에 등록하든 전역으로 적용되므로, 관례상 `AppModule`이나 `CoreModule`에 둔다.

## 비동기 에러와 Observable 에러

> **비유**: 우편으로 늦게 도착한 민원도 같은 데스크가 처리한다. 단, 우편이 아예 다른 주소로 가면 데스크는 모른다.

Nest는 핸들러가 반환한 Promise의 rejection과 Observable의 error 알림을 모두 예외 레이어로 연결한다.

```ts
@Get(':id')
async findOne(@Param('id') id: string) {
  // async 함수 안에서 throw → rejected Promise → 필터가 잡음
  const user = await this.users.findById(id);
  if (!user) throw new NotFoundException();
  return user;
}

@Get('stream')
stream(): Observable<Item> {
  // Observable의 error도 필터로 전달됨
  return this.items$.pipe(
    map((item) => {
      if (!item.valid) throw new BadRequestException('invalid item');
      return item;
    }),
  );
}
```

필터가 잡지 **못하는** 경우를 기억하자.

1. `await` 하지 않은 Promise(fire-and-forget)에서 발생한 rejection
2. `setTimeout`, 이벤트 리스너 콜백 안에서 throw
3. 응답이 이미 전송된 뒤 발생한 예외
4. Middleware에서 `next(err)` 대신 비동기 콜백 안에서 throw한 경우

```ts
@Post()
create(@Body() dto: CreateDto) {
  // X: await 없음. 실패해도 필터는 모르고 unhandledRejection이 된다
  this.mailer.sendWelcome(dto.email);

  // O: 의도적으로 백그라운드라면 직접 catch해서 로깅
  this.mailer.sendWelcome(dto.email).catch((e) => this.logger.warn(e));
}
```

> **주의**: 백그라운드 작업 실패를 확실히 추적해야 한다면 fire-and-forget 대신 큐(background 문서 참고)를 쓰자.

## 인터셉터 catchError와의 역할 구분

> **비유**: 인터셉터의 `catchError`는 현장에서 바로 수습하는 팀장이고, 필터는 최종 민원 처리 부서다. 팀장이 수습하면 민원 부서까지 가지 않는다.

인터셉터는 `next.handle()`이 반환하는 Observable에 `catchError`를 걸 수 있다.

```ts
@Injectable()
export class FallbackInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    return next.handle().pipe(
      catchError((err) => {
        if (err instanceof ExternalApiTimeoutError) {
          return of({ items: [], degraded: true }); // 복구: 정상 응답으로 전환
        }
        return throwError(() => err); // 나머지는 필터로 넘김
      }),
    );
  }
}
```

| 구분 | Interceptor `catchError` | ExceptionFilter |
| --- | --- | --- |
| 실행 위치 | 핸들러 바로 바깥 | 파이프라인 가장 바깥 |
| 잡을 수 있는 범위 | `next.handle()` 내부(안쪽 인터셉터, Pipe, Handler) | Guard, Pipe, Interceptor, Handler 전부 |
| Guard 예외 | X (Guard는 인터셉터보다 먼저 실행) | O |
| 주 용도 | 에러 변환, 재시도(`retry`), 폴백 값 반환 | 최종 응답 포맷 결정, 로깅 |
| 결과 | 정상 스트림으로 복구 가능 | 반드시 에러 응답을 써야 함 |

> **포인트**: "복구하거나 다른 에러로 바꾸고 싶다"면 인터셉터, "에러를 어떻게 응답할지 정한다"면 필터다. 응답 포맷을 두 곳에서 만들기 시작하면 일관성이 깨진다.

## 에러 응답 포맷 통일

> **비유**: 회사 모든 부서가 같은 공문 양식을 쓰는 것이다. 프론트엔드 입장에서는 양식 하나만 파싱하면 된다.

ValidationPipe의 400, 도메인 예외의 409, 알 수 없는 500이 각각 다른 모양으로 나가면 클라이언트가 고생한다. 하나의 포맷을 정하자.

```ts
export interface ErrorResponse {
  statusCode: number;
  code: string;          // 기계가 읽는 에러 코드
  message: string;       // 사람이 읽는 메시지
  details?: unknown;     // 검증 에러 목록 등
  path: string;
  timestamp: string;
  traceId?: string;
}
```

```ts
@Catch()
export class UnifiedExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger('Exception');

  constructor(
    private readonly adapterHost: HttpAdapterHost,
    private readonly config: ConfigService,
  ) {}

  catch(exception: unknown, host: ArgumentsHost) {
    if (host.getType() !== 'http') throw exception; // 다른 transport는 건드리지 않음

    const { httpAdapter } = this.adapterHost;
    const ctx = host.switchToHttp();
    const req = ctx.getRequest();
    const body = this.toErrorResponse(exception, httpAdapter.getRequestUrl(req));

    this.log(exception, body, req);
    httpAdapter.reply(ctx.getResponse(), body, body.statusCode);
  }

  private toErrorResponse(exception: unknown, path: string): ErrorResponse {
    const base = { path, timestamp: new Date().toISOString() };

    if (exception instanceof DomainError) {
      return { ...base, statusCode: mapDomainStatus(exception), code: exception.code,
        message: exception.message, details: exception.details };
    }

    if (exception instanceof HttpException) {
      const res = exception.getResponse();
      const message = typeof res === 'string' ? res : (res as any).message;
      return {
        ...base,
        statusCode: exception.getStatus(),
        code: exception.constructor.name.replace(/Exception$/, '').toUpperCase(),
        message: Array.isArray(message) ? 'Validation failed' : message,
        details: Array.isArray(message) ? message : undefined,
      };
    }

    return { ...base, statusCode: 500, code: 'INTERNAL', message: 'Internal server error' };
  }

  private log(exception: unknown, body: ErrorResponse, req: any) {
    const meta = `${req.method} ${body.path} ${body.statusCode}`;
    if (body.statusCode >= 500) {
      this.logger.error(meta, (exception as Error)?.stack);
    } else {
      this.logger.warn(`${meta} ${body.code}`);
    }
  }
}
```

ValidationPipe의 에러 모양도 맞추고 싶다면 `exceptionFactory`로 처음부터 원하는 형태의 예외를 만들 수 있다(validation 문서 참고).

## 로깅 전략

> **비유**: 응급실 트리아지다. 경미한 환자(4xx)는 대기표만 기록하고, 중증 환자(5xx)는 상세 차트를 남긴다.

| 상태 | 로그 레벨 | 스택 기록 | 알림 |
| --- | --- | --- | --- |
| 4xx (클라이언트 실수) | `warn` 또는 `debug` | X | X |
| 401/403 급증 | `warn` | X | 임계치 초과 시 O |
| 5xx | `error` | O | O (Sentry 등) |
| 도메인 규칙 위반 | `info`/`warn` | X | X |

1. 필터에서 request id(trace id)를 함께 기록해 요청 단위로 추적한다.
2. `cause` 체인이 있으면 원인 스택까지 남긴다.
3. 요청 바디 전체를 로그로 남기지 않는다. 비밀번호/토큰 같은 민감 정보가 섞인다.

```ts
const cause = (exception as any)?.cause;
this.logger.error(
  { msg: 'Unhandled exception', traceId, path, cause: cause?.message },
  (exception as Error).stack,
);
```

## 운영에서 스택 숨기기

> **비유**: 고객에게는 "시스템 점검 중입니다"라고 안내하고, 서버실 화이트보드에만 자세한 장애 내용을 적는다.

내장 필터는 알 수 없는 예외의 메시지를 이미 숨기지만, 커스텀 필터를 만들면서 실수로 `exception.message`나 `stack`을 응답에 넣는 경우가 많다.

```ts
const isProd = this.config.get('NODE_ENV') === 'production';

const body = {
  statusCode: 500,
  code: 'INTERNAL',
  message: 'Internal server error',
  ...(isProd ? {} : { debug: { message: (exception as Error).message, stack: (exception as Error).stack } }),
};
```

> **주의**: ORM 에러 메시지에는 테이블명, 컬럼명, 심지어 쿼리 값이 들어 있다. `QueryFailedError` 같은 DB 에러를 그대로 응답에 담으면 스키마가 노출된다. 5xx는 무조건 일반 메시지로 바꾸고, 필요하면 `traceId`만 돌려주자.

> **포인트**: 클라이언트에는 `traceId`, 로그에는 같은 `traceId` + 스택. 고객 문의가 오면 `traceId`로 로그를 찾는 흐름이 운영 표준이다.

## 셀프 체크

**Q1. `throw new Error('db down')`을 서비스에서 던졌을 때 사용자 정의 필터가 없다면 클라이언트는 어떤 응답을 받는가?**

**A.** 내장 exception layer가 `HttpException`이 아닌 예외로 판단해 `statusCode: 500`, `message: 'Internal server error'`를 응답한다. 원래 메시지 `db down`은 노출되지 않는다.

**Q2. `APP_FILTER`로 `AllExceptionsFilter`와 `DomainExceptionFilter`를 이 순서로 등록했다. 도메인 예외는 어느 필터가 처리하는가?**

**A.** 전역 필터는 나중에 등록된 것이 먼저 검사되므로 `DomainExceptionFilter`가 처리한다. 순서를 뒤집으면 catch-all이 먼저 가져간다.

**Q3. `BaseExceptionFilter`를 상속한 필터를 `main.ts`에서 `useGlobalFilters`로 등록할 때 주의할 점은?**

**A.** 생성자에 `HttpAdapterHost`에서 꺼낸 `httpAdapter`를 넘겨야 한다. `APP_FILTER`로 등록하면 Nest가 자동 주입하므로 이 문제가 없다.

**Q4. 외부 API 타임아웃 시 빈 목록으로 대체 응답하고 싶다. 필터와 인터셉터 중 어디에 구현해야 하는가?**

**A.** 인터셉터의 `catchError`에서 `of(fallback)`을 반환해 정상 스트림으로 복구하는 것이 맞다. 필터는 에러 응답을 결정하는 곳이지 정상 응답으로 복구하는 곳이 아니다.

**Q5. 서비스에서 `NotFoundException` 대신 도메인 예외를 던지는 설계의 이점은?**

**A.** 서비스가 HTTP에 결합되지 않아 RPC 핸들러, 배치, CLI에서도 재사용할 수 있고, 도메인 에러 → HTTP 상태 매핑이 필터 한 곳에 모여 관리와 테스트가 쉬워진다.

## 핵심 정리

- 처리되지 않은 예외는 내장 `BaseExceptionFilter`가 받아 `HttpException`이면 그 상태로, 아니면 500으로 응답한다.
- `HttpException`은 `response`, `status`, `cause`, `description`으로 구성되고, `cause`는 로깅용으로만 쓰인다.
- 서비스는 도메인 예외를 던지고, 필터가 HTTP 상태로 매핑하는 구조가 계층 분리에 유리하다.
- 필터는 route → controller → global 순으로 하나만 매칭되며, 전역 필터 여러 개는 나중 등록이 먼저 검사된다.
- `APP_FILTER` + `HttpAdapterHost`로 DI 가능하고 플랫폼 독립적인 전역 필터를 만든다.
- await되지 않은 Promise, 타이머 콜백의 에러는 필터가 잡지 못한다.
- 복구/변환은 인터셉터 `catchError`, 최종 응답 결정은 필터.
- 응답 포맷은 하나로 통일하고, 5xx는 스택을 로그에만 남기며 클라이언트에는 `traceId`만 준다.

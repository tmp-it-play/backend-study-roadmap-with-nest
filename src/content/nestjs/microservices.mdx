## 한눈에 보기

- `@nestjs/microservices`는 HTTP 대신 **Transport**(TCP, Redis, NATS, Kafka, RabbitMQ, gRPC 등) 위에서 Controller 스타일 핸들러를 돌리는 계층이다. 같은 Guard/Pipe/Interceptor/Filter 모델을 그대로 쓴다.
- `@MessagePattern`은 요청-응답(응답을 기다림), `@EventPattern`은 fire-and-forget 이벤트(응답 없음)다.
- `ClientProxy.send()`는 **cold Observable**이라 구독(`firstValueFrom` 등)하지 않으면 메시지가 아예 나가지 않는다. `emit()`은 호출 즉시 발행되지만, 에러를 잡으려면 역시 기다려야 한다.
- WebSocket은 `@WebSocketGateway` + `@SubscribeMessage`로 만들고, 핸들러 반환값이 클라이언트 ack가 된다. 인스턴스가 여러 대면 Redis adapter가 필수다.
- 서버 → 클라이언트 단방향 스트림이면 WebSocket보다 SSE가 단순하다.

## @nestjs/microservices 큰 그림

> **비유**: HTTP 서버가 **손님이 직접 와서 주문하는 매장**이라면, 마이크로서비스는 **주방끼리 주고받는 사내 주문 시스템**이다. 주문서 양식(pattern)과 전달 수단(Transport: 무전기, 컨베이어 벨트, 우편함)만 다를 뿐, 주방(핸들러)이 일하는 방식은 매장과 같다.

Nest 마이크로서비스의 핵심 아이디어는 **Transport 추상화**다.

- 서버 쪽은 `Server` 구현체(`ServerTCP`, `ServerRedis`, `ServerKafka`, `ServerRMQ`, `ServerNats`, `ServerGrpc` 등)가 메시지를 받아 pattern에 맞는 핸들러를 찾아 호출한다.
- 클라이언트 쪽은 `ClientProxy` 구현체(`ClientTCP`, `ClientKafka` 등)가 메시지를 직렬화해서 보낸다.
- 핸들러는 HTTP Controller와 똑같이 `@Controller()` 클래스 안에 두고, Guard/Interceptor/Pipe/Filter가 그대로 적용된다(단, `ExecutionContext.getType()`이 `'rpc'`).

| Transport | 특징 | 요청-응답 | 이벤트 | 대표 용도 |
| --- | --- | --- | --- | --- |
| TCP | 기본값, 추가 의존성 없음 | O | O | 내부 서비스 간 단순 RPC |
| Redis | pub/sub 기반, 영속성 없음 | O | O | 가벼운 이벤트 브로드캐스트 |
| NATS | 빠른 메시징, queue group | O | O | 저지연 서비스 메시 |
| Kafka | 로그 기반, 파티션, offset | O(설정 필요) | O | 이벤트 스트리밍, 재처리 |
| RabbitMQ | 큐, ack, DLX | O | O | 작업 큐, 신뢰성 있는 전달 |
| gRPC | protobuf, HTTP/2, 스트리밍 | O | X | 강한 스키마의 서비스 간 API |

> **포인트**: Transport를 바꿔도 핸들러 코드는 거의 그대로다. 다만 **전달 보장(at-most-once / at-least-once), 순서, 재처리** 같은 성질은 Transport마다 완전히 다르므로 "코드가 같다"를 "동작이 같다"로 착각하면 안 된다.

## createMicroservice vs hybrid app

> **비유**: `createMicroservice`는 **배달 전용 주방**(홀 없음), hybrid app은 **홀 영업도 하면서 배달 주문도 받는 식당**이다.

### 순수 마이크로서비스

```ts
// main.ts (orders-service)
import { NestFactory } from '@nestjs/core';
import { MicroserviceOptions, Transport } from '@nestjs/microservices';

async function bootstrap() {
  const app = await NestFactory.createMicroservice<MicroserviceOptions>(AppModule, {
    transport: Transport.TCP,
    options: { host: '0.0.0.0', port: 4001 },
  });
  await app.listen();
}
bootstrap();
```

### Hybrid app

```ts
async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.connectMicroservice<MicroserviceOptions>(
    {
      transport: Transport.RMQ,
      options: { urls: [process.env.RMQ_URL!], queue: 'orders', queueOptions: { durable: true }, noAck: false },
    },
    { inheritAppConfig: true }, // HTTP 앱의 global pipe/guard/filter를 마이크로서비스에도 적용
  );

  await app.startAllMicroservices();
  await app.listen(3000);
}
```

| 항목 | `createMicroservice` | hybrid (`connectMicroservice`) |
| --- | --- | --- |
| HTTP 서버 | X | O |
| Transport 개수 | 1개 | 여러 개 연결 가능 |
| 시작 방법 | `app.listen()` | `startAllMicroservices()` 후 `listen()` |
| global enhancer | `app.useGlobalPipes` 등 직접 | 기본은 별도, `inheritAppConfig: true`로 공유 |
| 용도 | 순수 워커/내부 서비스 | 헬스체크, 관리 API가 필요한 서비스 |

> **주의**: hybrid app에서 `app.useGlobalPipes(new ValidationPipe())`만 하면 마이크로서비스 핸들러에는 적용되지 않는다. `inheritAppConfig: true`를 주거나, `APP_PIPE` 같은 모듈 레벨 global provider로 등록해야 양쪽에 다 걸린다.

## @MessagePattern vs @EventPattern

> **비유**: `@MessagePattern`은 **전화**다. 걸고 나서 상대가 받아 대답할 때까지 기다린다. `@EventPattern`은 **단체 문자**다. 보내면 끝이고, 누가 읽었는지 답장을 기다리지 않는다.

```ts
@Controller()
export class OrdersController {
  constructor(private readonly orders: OrdersService) {}

  @MessagePattern({ cmd: 'get_order' })
  getOrder(@Payload() data: { id: string }) {
    return this.orders.findById(data.id); // 반환값(혹은 Promise/Observable)이 응답
  }

  @EventPattern('user_created')
  async onUserCreated(@Payload() event: UserCreatedEvent, @Ctx() ctx: RmqContext) {
    await this.orders.createCartFor(event.userId); // 반환값은 무시됨
  }
}
```

| 항목 | `@MessagePattern` | `@EventPattern` |
| --- | --- | --- |
| 통신 모델 | request-response | event-based (fire-and-forget) |
| 클라이언트 메서드 | `client.send()` | `client.emit()` |
| 응답 | 핸들러 반환값이 응답으로 돌아감 | 응답 없음, 반환값 무시 |
| 같은 pattern 핸들러 수 | 1개 | 여러 개 가능 |
| 실패 전파 | 클라이언트 Observable에 에러로 전달 | 클라이언트는 알 수 없음 |
| Observable 반환 | 마지막 값(또는 스트림)을 응답 | 의미 없음 |
| 적합한 경우 | 조회, 즉시 결과가 필요한 명령 | 도메인 이벤트 알림, 비동기 후처리 |

pattern은 문자열 혹은 객체(`{ cmd: 'get_order' }`)다. 객체 pattern은 내부적으로 키를 정렬해 문자열로 직렬화되어 매칭되므로 키 순서는 상관없다.

## ClientsModule과 ClientProxy

### 등록

```ts
@Module({
  imports: [
    ClientsModule.registerAsync([
      {
        name: 'ORDERS_SERVICE',
        inject: [ConfigService],
        useFactory: (config: ConfigService) => ({
          transport: Transport.TCP,
          options: { host: config.get('ORDERS_HOST'), port: config.get<number>('ORDERS_PORT') },
        }),
      },
    ]),
  ],
  providers: [CheckoutService],
})
export class CheckoutModule {}
```

```ts
@Injectable()
export class CheckoutService {
  constructor(@Inject('ORDERS_SERVICE') private readonly ordersClient: ClientProxy) {}
}
```

`name`이 DI 토큰이 된다. 연결은 첫 호출 시 lazy하게 맺어지며, 기동 시점에 연결 실패를 드러내고 싶다면 `onApplicationBootstrap`에서 `await this.ordersClient.connect()`를 호출한다.

### 함정: send()는 cold Observable

> **비유**: `send()`가 돌려주는 것은 **아직 부치지 않은 편지 봉투**다. 봉투를 받아 들고 아무것도 안 하면(구독하지 않으면) 편지는 영원히 우체국에 가지 않는다.

```ts
// X 아무 일도 일어나지 않는다. 메시지가 전송되지 않음
this.ordersClient.send({ cmd: 'get_order' }, { id });

// O Promise로 변환해서 기다림
const order = await firstValueFrom(
  this.ordersClient.send<OrderDto>({ cmd: 'get_order' }, { id }).pipe(timeout(3000)),
);
```

- `send()`는 subscribe되는 시점에 연결 확인 → 메시지 발행 → 응답 대기를 시작한다. 구독할 때마다 메시지가 **다시** 나간다(cold).
- `toPromise()`는 RxJS 7에서 deprecated. `firstValueFrom` / `lastValueFrom`을 쓴다.
- 응답이 영영 안 오면 Observable도 영영 완료되지 않는다. **`timeout` 연산자는 사실상 필수**다.

`emit()`은 현재 구현에서 호출 즉시 발행을 시작하는 hot Observable을 반환한다. 그래서 구독하지 않아도 이벤트는 나가지만, 브로커 연결 실패 같은 에러를 잡으려면 `await lastValueFrom(client.emit(...))`처럼 기다리는 것이 안전하다.

> **주의**: Controller가 `send()`의 Observable을 그대로 `return`하면 Nest가 구독해 주므로 동작한다. 문제는 서비스 내부에서 결과를 쓰지 않고 호출만 할 때다. "로컬에서는 됐는데"의 대부분은 테스트 코드가 우연히 구독하고 있었던 경우다.

### @Payload와 @Ctx

- `@Payload()`는 메시지 본문(`data`)이다. `@Payload('id')`처럼 프로퍼티를 꺼낼 수도 있고, Pipe를 붙일 수도 있다.
- `@Ctx()`는 Transport별 컨텍스트 객체다: `TcpContext`, `RedisContext`, `NatsContext`, `KafkaContext`, `RmqContext`, `MqttContext`.

```ts
@EventPattern('order.paid')
handle(@Payload() data: OrderPaidEvent, @Ctx() ctx: KafkaContext) {
  const { offset } = ctx.getMessage();
  const partition = ctx.getPartition();
  const topic = ctx.getTopic();
}
```

## RpcException과 예외 필터

> **비유**: HTTP 예외는 **손님에게 보여주는 사과문**(status code)이 있지만, RPC 예외는 **주방 간 내부 메모**다. 상태 코드라는 공통 언어가 없으니 메모 양식(에러 객체 구조)을 팀이 정해야 한다.

```ts
@MessagePattern({ cmd: 'get_order' })
async getOrder(@Payload() { id }: { id: string }) {
  const order = await this.orders.findById(id);
  if (!order) throw new RpcException({ code: 'ORDER_NOT_FOUND', message: `order ${id} not found` });
  return order;
}
```

- 기본 `BaseRpcExceptionFilter`는 `RpcException`의 `getError()` 결과를 클라이언트에 에러로 전달한다. 그 외 예외는 `Internal server error` 형태로 감싼다.
- 클라이언트 쪽에서는 `send()` Observable이 에러로 끝나고, `firstValueFrom`이 reject된다. 받은 값은 Error 인스턴스가 아니라 **직렬화된 plain object**다.
- 마이크로서비스 핸들러에서 `HttpException`(예: `NotFoundException`)을 던지면 의미가 맞지 않는다. 서비스 계층 예외를 공용으로 쓰고 싶다면 필터에서 변환한다.

```ts
@Catch()
export class AllRpcExceptionsFilter implements RpcExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost): Observable<never> {
    if (exception instanceof RpcException) return throwError(() => exception.getError());
    if (exception instanceof HttpException) {
      return throwError(() => ({ code: exception.getStatus(), message: exception.message }));
    }
    return throwError(() => ({ code: 'INTERNAL', message: 'unexpected error' }));
  }
}
```

> **포인트**: RPC 예외 필터는 HTTP 필터와 달리 **Observable을 반환**해야 한다(`throwError`). 응답을 직접 write하는 HTTP 필터와 모양이 다르다.

> **주의**: 게이트웨이(BFF) 쪽에서 RPC 에러를 그대로 throw하면 HTTP 응답은 500이 된다. 받은 에러 코드를 HTTP 예외로 매핑하는 Interceptor나 필터를 게이트웨이에 두는 것이 일반적이다.

## 직렬화

- 기본은 JSON 직렬화다. 따라서 `Date`는 문자열, `Map`/`Set`은 빈 객체, 클래스 인스턴스는 prototype을 잃은 plain object가 된다.
- 받는 쪽에서 DTO 클래스 인스턴스가 필요하면 `ValidationPipe({ transform: true })`를 마이크로서비스에도 적용한다.
- Transport 옵션의 `serializer` / `deserializer`로 커스텀 직렬화를 꽂을 수 있다(예: 외부 시스템이 Nest 메시지 포맷이 아닌 raw JSON을 보낼 때).
- Nest 클라이언트가 보내는 메시지는 `{ pattern, data, id }` 형태(요청-응답이면 `id` 포함)로 감싸진다. Nest가 아닌 producer와 연동할 때 이 포맷 차이가 가장 흔한 장애 원인이다.

## Kafka / RabbitMQ의 ack 개념

> **비유**: ack는 **택배 수령 서명**이다. 서명하기 전에 기사가 떠나면(auto ack) 상자를 떨어뜨려도 책임질 사람이 없다. 서명을 받고 떠나면(manual ack) 처리 실패 시 다시 배달(redelivery)할 수 있다.

### RabbitMQ: manual ack

```ts
// 서버 옵션에 noAck: false
@EventPattern('order.created')
async handle(@Payload() data: OrderCreated, @Ctx() ctx: RmqContext) {
  const channel = ctx.getChannelRef();
  const msg = ctx.getMessage();
  try {
    await this.process(data);
    channel.ack(msg);
  } catch (e) {
    channel.nack(msg, false, false); // requeue=false → DLX로 보냄
  }
}
```

### Kafka: offset commit과 consumer group

- Kafka는 메시지를 지우지 않고 **consumer group별 offset**만 기록한다. 같은 group의 인스턴스들은 파티션을 나눠 갖는다.
- 기본은 kafkajs의 auto commit이다. 핸들러가 실패해도 offset이 넘어갈 수 있으므로, 중요한 처리라면 `run: { autoCommit: false }`로 두고 처리 후 `ctx.getConsumer().commitOffsets(...)`로 직접 commit한다.
- Kafka에서 `send()`(요청-응답)를 쓰려면 클라이언트가 응답 토픽을 구독해야 한다. `onModuleInit`에서 `client.subscribeToResponseOf('pattern')` 후 `await client.connect()`.

> **포인트**: at-least-once 전달에서는 **같은 메시지가 두 번 올 수 있다**. 핸들러는 멱등(idempotent)하게 만들고, 메시지 id로 중복 처리 테이블을 두는 것이 정석이다.

## gRPC 기본

> **비유**: JSON 기반 RPC가 **자유 양식 메모**라면, gRPC는 **정해진 서식의 공문서**다. proto 파일이라는 서식이 양쪽에 있어야 하고, 서식에 없는 칸은 쓸 수 없다.

```proto
// proto/hero.proto
syntax = "proto3";
package hero;

service HeroesService {
  rpc FindOne (HeroById) returns (Hero);
}
message HeroById { int32 id = 1; }
message Hero { int32 id = 1; string name = 2; }
```

```ts
// 서버
app.connectMicroservice<MicroserviceOptions>({
  transport: Transport.GRPC,
  options: { package: 'hero', protoPath: join(__dirname, 'proto/hero.proto'), url: '0.0.0.0:5000' },
});

@Controller()
export class HeroesController {
  @GrpcMethod('HeroesService', 'FindOne')
  findOne(data: HeroById, metadata: Metadata, call: ServerUnaryCall<any, any>): Hero {
    return { id: data.id, name: 'Nest' };
  }
}
```

```ts
// 클라이언트
interface HeroesService {
  findOne(data: HeroById): Observable<Hero>;
}

@Injectable()
export class HeroClient implements OnModuleInit {
  private heroes!: HeroesService;
  constructor(@Inject('HERO_PACKAGE') private readonly client: ClientGrpc) {}

  onModuleInit() {
    this.heroes = this.client.getService<HeroesService>('HeroesService');
  }

  get(id: number) {
    return firstValueFrom(this.heroes.findOne({ id }));
  }
}
```

- `@GrpcMethod`의 메서드 이름을 생략하면 핸들러 메서드명을 UpperCamelCase로 바꿔 매칭한다.
- 클라이언트 stub의 메서드는 lowerCamelCase(`findOne`)로 노출된다.
- 스트리밍은 `@GrpcStreamMethod`(Observable 기반) / `@GrpcStreamCall`(raw stream)로 다룬다.
- 에러는 `RpcException({ code: status.NOT_FOUND, message })`처럼 gRPC status code를 담아 던진다.

## WebSocket Gateway

> **비유**: HTTP Controller가 **민원 창구**(번호표 뽑고, 한 번 답 받고 끝)라면, Gateway는 **전화가 계속 연결된 상담실**이다. 연결된 동안 양쪽이 언제든 말을 걸 수 있고, 상담원은 여러 손님을 방(room)에 묶어 한꺼번에 안내할 수도 있다.

### 기본 구조

```ts
import {
  ConnectedSocket, MessageBody, OnGatewayConnection, OnGatewayDisconnect, OnGatewayInit,
  SubscribeMessage, WebSocketGateway, WebSocketServer, WsException,
} from '@nestjs/websockets';
import { Server, Socket } from 'socket.io';

@WebSocketGateway({ namespace: '/chat', cors: { origin: ['https://app.example.com'] } })
export class ChatGateway implements OnGatewayInit, OnGatewayConnection, OnGatewayDisconnect {
  @WebSocketServer() server!: Server; // namespace를 주면 해당 Namespace 객체

  constructor(private readonly chat: ChatService) {}

  afterInit(server: Server) {
    // 서버 생성 직후 1회
  }

  handleConnection(client: Socket) {
    // 클라이언트 연결마다
  }

  handleDisconnect(client: Socket) {
    // 연결 종료마다: presence 정리 등
  }

  @SubscribeMessage('join')
  async join(@MessageBody() roomId: string, @ConnectedSocket() client: Socket) {
    await client.join(roomId);
    return { ok: true }; // socket.io ack로 전달
  }

  @SubscribeMessage('message')
  async message(@MessageBody() dto: SendMessageDto, @ConnectedSocket() client: Socket) {
    if (!client.rooms.has(dto.roomId)) throw new WsException('not joined');
    const saved = await this.chat.save(dto);
    this.server.to(dto.roomId).emit('message', saved); // 방 전체에 브로드캐스트
    return saved.id;
  }
}
```

- Gateway도 provider다. 모듈의 `providers`에 넣어야 동작한다.
- 기본 플랫폼은 socket.io(`@nestjs/platform-socket.io`). 순수 `ws`를 쓰려면 `@nestjs/platform-ws`의 `WsAdapter`를 `app.useWebSocketAdapter`로 지정한다.
- 포트를 생략하면 HTTP 서버와 같은 포트를 공유한다.

### 반환값 = ack

핸들러 반환값의 의미는 다음과 같다.

| 반환 | 동작 |
| --- | --- |
| 일반 값 / Promise | 클라이언트가 ack 콜백을 넘겼다면 그 콜백의 인자로 전달 |
| `{ event, data }` 형태(`WsResponse`) | 해당 `event` 이름으로 보낸 클라이언트에게 emit |
| Observable | 방출되는 값마다 응답 |
| `undefined` | 아무것도 보내지 않음 |

```ts
// 클라이언트
socket.emit('join', 'room-1', (res) => console.log(res)); // { ok: true }
```

### WsException과 필터

`WsException`을 던지면 기본 `BaseWsExceptionFilter`가 클라이언트에 `exception` 이벤트로 `{ status: 'error', message }`를 보낸다. 그 외 예외는 `Internal server error`로 바뀐다. `ValidationPipe` 실패는 `BadRequestException`(HTTP 예외)이므로 그대로 두면 internal error로 보이는데, 이를 막으려면 `exceptionFactory`에서 `WsException`을 만들게 하거나 Gateway 전용 필터를 둔다.

> **주의**: `@UsePipes(new ValidationPipe())`를 Gateway에 걸 때 `exceptionFactory: (errors) => new WsException(errors)` 설정을 잊으면 클라이언트는 원인을 알 수 없는 에러만 받는다.

### 인증: handshake 시점에 막기

> **비유**: Guard는 **매 발언마다 신분증을 확인하는 사회자**고, handshake 인증은 **입장할 때 한 번 확인하는 문지기**다. 둘 다 필요할 수 있지만, 아무나 일단 방에 들어오게 두는 것은 위험하다.

Gateway에 `@UseGuards()`를 걸면 **메시지마다** 실행되고, 연결(`handleConnection`) 자체는 막지 못한다. 그래서 연결 단계 인증은 보통 socket.io 미들웨어로 처리한다.

```ts
@WebSocketGateway({ namespace: '/chat' })
export class ChatGateway implements OnGatewayInit {
  constructor(private readonly jwt: JwtService) {}

  afterInit(server: Namespace) {
    server.use(async (socket, next) => {
      try {
        const token = socket.handshake.auth?.token ?? socket.handshake.headers.authorization?.split(' ')[1];
        socket.data.user = await this.jwt.verifyAsync(token);
        next();
      } catch {
        next(new Error('unauthorized'));
      }
    });
  }
}

// 메시지 단위 권한은 Guard로
@Injectable()
export class WsRoomGuard implements CanActivate {
  canActivate(ctx: ExecutionContext) {
    const client = ctx.switchToWs().getClient<Socket>();
    const data = ctx.switchToWs().getData<{ roomId: string }>();
    return client.data.user?.rooms?.includes(data.roomId) ?? false;
  }
}
```

### 다중 인스턴스: Redis adapter

> **비유**: 상담실이 여러 층(인스턴스)에 있으면, 3층 상담원이 "이 방 사람들 모두에게 알려줘"라고 해도 5층 손님은 못 듣는다. Redis adapter는 **층마다 깔린 사내 방송 스피커**다.

```text
  client A ── instance 1 ─┐
                          ├── Redis pub/sub ── 모든 인스턴스가 room 브로드캐스트 공유
  client B ── instance 2 ─┘
```

```ts
// redis-io.adapter.ts
import { IoAdapter } from '@nestjs/platform-socket.io';
import { ServerOptions } from 'socket.io';
import { createAdapter } from '@socket.io/redis-adapter';
import { createClient } from 'redis';

export class RedisIoAdapter extends IoAdapter {
  private adapterConstructor!: ReturnType<typeof createAdapter>;

  async connectToRedis(url: string) {
    const pub = createClient({ url });
    const sub = pub.duplicate();
    await Promise.all([pub.connect(), sub.connect()]);
    this.adapterConstructor = createAdapter(pub, sub);
  }

  createIOServer(port: number, options?: ServerOptions) {
    const server = super.createIOServer(port, options);
    server.adapter(this.adapterConstructor);
    return server;
  }
}

// main.ts
const redisIoAdapter = new RedisIoAdapter(app);
await redisIoAdapter.connectToRedis(process.env.REDIS_URL!);
app.useWebSocketAdapter(redisIoAdapter);
```

> **주의**: socket.io의 HTTP long-polling fallback을 쓰면 로드밸런서에 **sticky session**이 필요하다. 사용하지 않는다면 클라이언트에서 `transports: ['websocket']`으로 고정한다.

## WebSocket vs SSE 선택 기준

> **비유**: WebSocket은 **양방향 무전기**, SSE는 **라디오 방송**이다. 듣기만 하면 되는데 무전기를 쓸 필요는 없다.

```ts
@Controller('jobs')
export class JobsController {
  @Sse(':id/progress')
  progress(@Param('id') id: string): Observable<MessageEvent> {
    return this.jobs.progress$(id).pipe(map((p) => ({ data: p }) as MessageEvent));
  }
}
```

| 항목 | WebSocket (Gateway) | SSE (`@Sse`) |
| --- | --- | --- |
| 방향 | 양방향 | 서버 → 클라이언트 단방향 |
| 프로토콜 | 별도 upgrade (ws) | 일반 HTTP 응답 스트림 |
| 자동 재연결 | 라이브러리 구현(socket.io는 O) | 브라우저 `EventSource` 내장 |
| 인증 | handshake 별도 처리 | 기존 HTTP Guard/쿠키 그대로 |
| Nest 파이프라인 | Gateway 컨텍스트(`ws`) | 일반 Controller 파이프라인 그대로 |
| 바이너리 | O | X(텍스트) |
| 확장 | Redis adapter 등 필요 | 인스턴스 간 이벤트 공유는 별도 pub/sub |
| 적합 | 채팅, 협업 편집, 게임 | 알림, 진행률, 로그 tail, LLM 토큰 스트림 |

> **포인트**: SSE 핸들러가 반환한 Observable은 클라이언트가 연결을 끊으면 구독 해제(teardown)된다. 반대로 서버 쪽 Observable이 완료되지 않으면 연결이 계속 열려 있으므로, interval이나 외부 구독을 쓰는 스트림은 teardown 로직을 반드시 넣어야 한다.

## 셀프 체크

**Q1. `@MessagePattern`과 `@EventPattern`의 차이를 응답, 핸들러 수, 실패 전파 관점에서 설명하라.**

**A.** `@MessagePattern`은 request-response라 핸들러 반환값이 클라이언트에 응답으로 가고, 같은 pattern에 핸들러는 하나이며, 예외는 클라이언트 Observable의 에러로 전파된다. `@EventPattern`은 fire-and-forget이라 반환값이 무시되고, 같은 이벤트에 여러 핸들러를 둘 수 있으며, 발행자는 처리 실패를 알 수 없다.

**Q2. 서비스 코드에서 `this.client.send(pattern, data)`만 호출했는데 상대 서비스 로그에 아무것도 찍히지 않는다. 원인과 해결책은?**

**A.** `send()`는 cold Observable이라 구독해야 비로소 메시지를 발행한다. `await firstValueFrom(this.client.send(...).pipe(timeout(3000)))`처럼 구독하고, 응답이 오지 않는 경우를 대비해 timeout도 건다.

**Q3. hybrid app에서 `app.useGlobalPipes(new ValidationPipe())`를 했는데 RabbitMQ 핸들러에는 검증이 적용되지 않는다. 왜이고 어떻게 고치는가?**

**A.** 연결된 마이크로서비스는 HTTP 앱의 global enhancer를 기본적으로 상속하지 않는다. `connectMicroservice(options, { inheritAppConfig: true })`로 상속시키거나, `APP_PIPE` provider로 모듈 레벨 global pipe를 등록한다.

**Q4. Gateway에 `@UseGuards(JwtWsGuard)`를 걸었는데 토큰 없는 클라이언트도 연결은 되는 이유와 대안은?**

**A.** Gateway의 Guard는 `@SubscribeMessage` 핸들러가 실행될 때마다 동작할 뿐, 연결 수립 자체에는 관여하지 않는다. `afterInit`에서 socket.io 미들웨어(`server.use`)로 handshake 토큰을 검증해 `next(new Error(...))`로 거부하거나, `handleConnection`에서 검증 실패 시 `client.disconnect()`한다.

**Q5. 인스턴스 3대로 늘렸더니 같은 room에 있는 사용자 일부가 메시지를 못 받는다. 원인과 해결책은?**

**A.** socket.io의 room과 브로드캐스트는 기본적으로 프로세스 메모리 안에서만 관리되어, 다른 인스턴스에 연결된 클라이언트에게 전달되지 않는다. `@socket.io/redis-adapter`를 적용한 커스텀 `IoAdapter`를 `app.useWebSocketAdapter`로 등록해 인스턴스 간 브로드캐스트를 공유하고, polling을 쓴다면 sticky session도 설정한다.

## 핵심 정리

- `@nestjs/microservices`는 Transport만 다른 Controller 모델이다. Guard/Pipe/Interceptor/Filter가 그대로 동작하고 컨텍스트 타입은 `rpc`.
- `createMicroservice`는 순수 워커, hybrid는 `connectMicroservice` + `startAllMicroservices`. global enhancer 공유는 `inheritAppConfig`.
- `@MessagePattern`/`send()`는 요청-응답, `@EventPattern`/`emit()`은 이벤트. `send()`는 cold라 반드시 구독하고 timeout을 건다.
- RPC 에러는 `RpcException` + Observable을 반환하는 필터. 받은 에러는 직렬화된 plain object다.
- 기본 직렬화는 JSON이라 클래스/Date 정보가 사라진다. Nest가 아닌 producer와는 메시지 포맷을 맞춘다.
- RabbitMQ는 `noAck: false` + `channel.ack`, Kafka는 consumer group과 offset commit. 핸들러는 멱등하게.
- WebSocket: `@WebSocketGateway`, `@SubscribeMessage`, 반환값이 ack, `WsException`, handshake 인증은 미들웨어, 다중 인스턴스는 Redis adapter.
- 단방향 스트림이면 SSE가 더 단순하고 기존 HTTP 파이프라인을 그대로 쓴다.

## 한눈에 보기

- **Fastify 어댑터**로 바꾸면 처리량이 올라가지만, Express 전용 미들웨어 호환성과 `listen(3000, '0.0.0.0')`을 꼭 챙겨야 한다.
- **LazyModuleLoader**는 서버리스 콜드스타트를 줄여주지만, lazy 모듈엔 컨트롤러/게이트웨이를 둘 수 없다.
- **압축**은 앱에서도 되지만 운영에선 nginx 같은 리버스 프록시에 맡기는 게 낫다.
- **Barrel export**(`index.ts`)는 import를 깔끔하게 하지만 순환 의존성 → `undefined` 주입의 주범이 된다.
- **Config 네임스페이스**(`registerAs` + `ConfigType`)로 설정을 타입 안전하게 주입하자.

## Fastify 어댑터

> **비유**: 같은 차체(NestJS)에 엔진만 바꿔 다는 것. 기본 엔진(Express)은 정비소(미들웨어 생태계)가 많아 어디서나 고칠 수 있고, 고성능 엔진(Fastify)은 더 빠르지만 부품 규격이 달라서 기존 부품을 그대로 끼울 수 없을 때가 있다.

### 개념

NestJS는 HTTP 계층을 **어댑터**로 추상화한다. 기본은 `@nestjs/platform-express`이고, `@nestjs/platform-fastify`로 바꾸면 내부 HTTP 서버가 Fastify가 된다. 컨트롤러, 가드, 파이프, 인터셉터 코드는 대부분 그대로 동작한다.

```bash
npm i @nestjs/platform-fastify
```

```ts
// main.ts
import { NestFactory } from '@nestjs/core';
import { FastifyAdapter, NestFastifyApplication } from '@nestjs/platform-fastify';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create<NestFastifyApplication>(
    AppModule,
    new FastifyAdapter({ logger: false, trustProxy: true }),
  );

  // Fastify는 기본적으로 localhost(127.0.0.1)에만 바인딩한다
  await app.listen(3000, '0.0.0.0');
}
bootstrap();
```

> **주의**: Docker/K8s에서 `app.listen(3000)`만 쓰면 컨테이너 내부 루프백에만 바인딩돼서 외부에서 접속이 안 된다. Fastify에서는 반드시 `'0.0.0.0'`을 명시하자. 최신 버전에서는 `app.listen({ port: 3000, host: '0.0.0.0' })` 형태도 쓸 수 있다.

### Express와의 차이

| 항목 | Express | Fastify |
| --- | --- | --- |
| 성능 | 무난 | JSON 직렬화/라우팅이 빨라 처리량이 더 높은 편 |
| 미들웨어 생태계 | 방대함 (`helmet`, `compression`, `multer` 등) | `@fastify/*` 플러그인 생태계를 써야 함 |
| 요청/응답 객체 | `req`, `res` (Express 타입) | `FastifyRequest`, `FastifyReply` |
| 파일 업로드 | `FileInterceptor` (multer 기반) 바로 사용 | `@fastify/multipart` 등 별도 구성 필요 |
| 응답 스키마 | 없음 | JSON Schema 기반 직렬화 최적화 지원 |

### 미들웨어 호환성

1. NestJS의 `MiddlewareConsumer`로 등록한 함수형 미들웨어는 Fastify에서도 동작한다(내부적으로 미들웨어 호환 계층을 쓴다).
2. 하지만 `res.send`, `res.locals`처럼 **Express 응답 객체 API에 의존하는 미들웨어**는 깨진다.
3. Express 전용 라이브러리(`helmet`, `compression`, `express-session`)는 `@fastify/helmet`, `@fastify/compress`, `@fastify/secure-session` 같은 Fastify 버전으로 교체한다.
4. 컨트롤러에서 `@Res()`로 `Response`(Express 타입)를 직접 다루던 코드는 `FastifyReply`로 바꿔야 한다.

```ts
import { FastifyReply, FastifyRequest } from 'fastify';

@Get('download')
download(@Req() req: FastifyRequest, @Res() reply: FastifyReply) {
  reply.header('Content-Type', 'text/csv').send('id,name\n1,foo');
}
```

```ts
// Fastify 플러그인 등록
import helmet from '@fastify/helmet';

await app.register(helmet);
```

> **포인트**: 성능 이득은 "프레임워크 오버헤드"에 한정된다. 실제 API 응답 시간 대부분이 DB 쿼리라면 체감 차이는 작다. 새 프로젝트에서 처음부터 고르는 건 좋지만, 기존 Express 프로젝트를 성능만 보고 옮기는 건 신중하게.

## Lazy Loading 모듈

> **비유**: 캠핑 갈 때 모든 장비를 차에 싣고 출발하는 대신, 자주 쓰는 것만 챙기고 무거운 장비(보트, 발전기)는 **필요할 때 택배로 받는** 것. 출발(콜드스타트)이 빨라진다.

### 문제 상황

서버리스(AWS Lambda 등)에서는 요청이 올 때 인스턴스가 새로 뜨는 콜드스타트가 발생한다. 앱 시작 시 PDF 생성, 리포트, 엑셀 export 같은 무거운 모듈까지 전부 초기화하면 첫 요청이 수 초 걸린다.

### 개념

`LazyModuleLoader`는 특정 모듈을 **실제로 필요할 때** 동적으로 로드하고 초기화한다. 한 번 로드된 모듈은 캐시되어 다음 호출부터는 즉시 반환된다.

```ts
// reports/reports.service.ts
import { Injectable } from '@nestjs/common';
import { LazyModuleLoader } from '@nestjs/core';

@Injectable()
export class ReportsService {
  constructor(private readonly lazyModuleLoader: LazyModuleLoader) {}

  async exportPdf(reportId: string) {
    // 1. 동적 import로 모듈 파일 자체를 늦게 로드
    const { PdfModule } = await import('../pdf/pdf.module');
    // 2. Nest가 모듈을 초기화 (최초 1회만, 이후엔 캐시)
    const moduleRef = await this.lazyModuleLoader.load(() => PdfModule);

    const { PdfService } = await import('../pdf/pdf.service');
    const pdfService = moduleRef.get(PdfService);
    return pdfService.render(reportId);
  }
}
```

흐름을 정리하면 이렇다.

1. 앱 부트스트랩 시 `PdfModule`은 `AppModule`의 imports에 **없다** → 초기화되지 않음.
2. 첫 `exportPdf()` 호출 → `import()`로 JS 파일 로드 → `lazyModuleLoader.load()`로 DI 그래프 구성.
3. 반환된 `ModuleRef`에서 `get()`으로 provider를 꺼내 사용.
4. 두 번째 호출부터는 캐시된 모듈 인스턴스를 바로 반환.

### 제약 사항

| 제약 | 이유 |
| --- | --- |
| 컨트롤러 등록 불가 | 라우트는 부트스트랩 시점에 HTTP 어댑터에 등록되므로 나중에 추가할 수 없다 |
| WebSocket 게이트웨이 / 마이크로서비스 핸들러 / GraphQL resolver 불가 | 같은 이유로 시작 시점 등록이 필요하다 |
| lifecycle hooks 일부만 호출 | lazy 모듈에서는 `onModuleInit` 같은 초기화 훅은 호출되지만, `onApplicationBootstrap`처럼 앱 전체 시작 시점 훅은 이미 지나서 호출되지 않는다 |
| 글로벌 enhancer 영향 | lazy 모듈에 선언한 글로벌 가드/인터셉터는 기대대로 동작하지 않는다 |

> **주의**: 일반 서버(항상 떠 있는 컨테이너)에서는 이득이 거의 없다. 오히려 첫 요청만 느려진다. **콜드스타트가 문제인 서버리스 환경**에서, 일부 엔드포인트만 쓰는 무거운 모듈에 적용하자.

> **포인트**: webpack 번들링을 하는 서버리스 빌드라면 동적 `import()`가 별도 chunk로 분리되어야 효과가 크다.

## 압축 (Compression)

> **비유**: 택배를 보낼 때 이불을 **압축팩**에 넣으면 운송비(네트워크 대역폭)는 줄지만, 압축하는 수고(CPU)가 든다. 그 수고를 매장 직원(앱)이 할지, 물류센터(nginx)가 전담할지의 문제다.

### Express

```bash
npm i compression
```

```ts
import compression from 'compression';

const app = await NestFactory.create(AppModule);
app.use(compression({ threshold: 1024 })); // 1KB 이상만 압축
```

### Fastify

```bash
npm i @fastify/compress
```

```ts
import compression from '@fastify/compress';

const app = await NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter());
await app.register(compression, { encodings: ['gzip', 'deflate'] });
```

### 운영에서는 리버스 프록시에 맡기자

Node.js는 싱글 스레드 이벤트 루프라서, gzip 같은 CPU 작업을 앱에서 하면 다른 요청 처리가 밀린다. nginx는 압축을 C로 효율적으로 처리하고, 정적 파일은 미리 압축된 파일(`gzip_static`)을 쓸 수도 있다.

```nginx
http {
  gzip on;
  gzip_comp_level 5;
  gzip_min_length 1024;
  gzip_proxied any;
  gzip_types application/json text/plain text/css application/javascript;

  server {
    listen 80;
    location / {
      proxy_pass http://nest_app:3000;
    }
  }
}
```

| 위치 | 장점 | 단점 |
| --- | --- | --- |
| 앱 (`compression`) | 설정 간단, 프록시 없는 환경에서도 동작 | 이벤트 루프 CPU 소모 |
| 리버스 프록시 (nginx, CDN) | 앱 부하 0, 효율적 | 인프라 설정 필요 |

> **주의**: nginx와 앱 양쪽에서 압축을 켜면 CPU만 낭비된다. 한 곳에서만 하자. 또 SSE(Server-Sent Events) 응답은 압축 미들웨어가 버퍼링해서 이벤트가 늦게 도착할 수 있다.

## Barrel Export

> **비유**: 건물 1층의 **통합 안내 데스크**. 각 층 사무실을 일일이 찾아가지 않고 안내 데스크(`index.ts`)에서 다 받을 수 있어 편하다. 하지만 안내 데스크가 모든 사무실과 연결되어 있다 보니, 어떤 사무실이 다른 사무실을 찾으러 안내 데스크로 가면 **빙빙 도는 동선**(순환 의존)이 생긴다.

### 개념

폴더마다 `index.ts`를 두고 하위 파일을 re-export하는 방식이다.

```ts
// users/index.ts
export * from './users.module';
export * from './users.service';
export * from './dto/create-user.dto';
export * from './entities/user.entity';
```

```ts
// 사용하는 쪽
import { UsersService, CreateUserDto } from '../users';
```

### 장단점

| 장점 | 단점 |
| --- | --- |
| import 경로가 짧고 깔끔 | 순환 의존성이 쉽게 생김 |
| 모듈의 public API를 명시적으로 관리 | 하나만 import해도 barrel 전체 파일이 평가됨 → 초기 로딩 비용 |
| 내부 파일 구조 변경이 외부에 영향 없음 | 번들러에 따라 트리셰이킹이 잘 안 됨(side effect 있는 모듈) |

### NestJS에서 터지는 사례: undefined 주입

```ts
// users/users.service.ts
import { OrdersService } from '../orders'; // orders/index.ts 경유

@Injectable()
export class UsersService {
  constructor(private readonly ordersService: OrdersService) {}
}

// orders/orders.service.ts
import { UsersService } from '../users'; // users/index.ts 경유

@Injectable()
export class OrdersService {
  constructor(private readonly usersService: UsersService) {}
}
```

무슨 일이 일어나는지 단계별로 보자.

1. `users/index.ts`가 평가되면서 `users.service.ts`를 로드한다.
2. `users.service.ts`는 `../orders`를 import → `orders/index.ts` → `orders.service.ts` 로드.
3. `orders.service.ts`는 `../users`를 import하는데, `users/index.ts`는 **아직 평가 중**이라 `UsersService`가 아직 `undefined`다.
4. TypeScript가 생성한 `design:paramtypes` 메타데이터에 `undefined`가 기록된다.
5. Nest 부트스트랩 시 에러가 난다.

```text
Nest can't resolve dependencies of the OrdersService (?).
Please make sure that the argument dependency at index [0] is available in the OrdersModule context.
```

혹은 "A circular dependency between modules" 경고나, 모듈 import 배열에 `undefined`가 들어갔다는 에러를 만난다.

### 해결 방법

1. **같은 기능 내부/서로를 참조하는 파일끼리는 barrel을 쓰지 말고 파일 경로로 직접 import**한다.

```ts
import { OrdersService } from '../orders/orders.service';
```

2. 진짜로 양방향 의존이 필요하면 `forwardRef`를 쓴다.

```ts
@Injectable()
export class UsersService {
  constructor(
    @Inject(forwardRef(() => OrdersService))
    private readonly ordersService: OrdersService,
  ) {}
}

@Module({
  imports: [forwardRef(() => OrdersModule)],
  providers: [UsersService],
  exports: [UsersService],
})
export class UsersModule {}
```

3. 근본적으로는 양방향 의존을 끊는다. 공통 로직을 별도 모듈로 빼거나, 한쪽을 이벤트(`@OnEvent`)로 바꾼다.

> **주의**: `forwardRef`는 "barrel 때문에 생긴 가짜 순환"을 덮는 용도로 쓰면 안 된다. 실제 설계상 순환이 아닌데 `forwardRef`가 필요해졌다면 barrel import부터 의심하자.

> **포인트**: barrel은 **라이브러리/모듈 경계의 public API**에만 쓰고, 앱 내부 기능 모듈끼리는 직접 경로 import를 쓰는 것이 안전한 절충안이다. ESLint `import/no-cycle` 규칙이나 `madge --circular`로 순환을 점검할 수 있다.

```bash
npx madge --circular --extensions ts src/
```

## Config 네임스페이스

> **비유**: 환경변수를 한 서랍에 다 넣으면 찾기 힘들다. **라벨 붙은 칸막이 서랍**(`database`, `redis`, `jwt`)으로 나누고, 각 칸에 무엇이 들어 있는지 목록(타입)까지 붙여두면 꺼내 쓸 때 실수가 없다.

### 문제 상황

`configService.get('DB_HOST')`를 곳곳에서 문자열 키로 호출한다. 오타가 나도 컴파일 에러가 안 나고, 반환 타입은 `any`이거나 직접 제네릭을 적어야 하며, 숫자여야 할 포트가 문자열로 들어온다.

### 1단계: registerAs로 네임스페이스 정의

```ts
// config/database.config.ts
import { registerAs } from '@nestjs/config';

export default registerAs('database', () => ({
  host: process.env.DB_HOST ?? 'localhost',
  port: parseInt(process.env.DB_PORT ?? '5432', 10),
  username: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  name: process.env.DB_NAME,
  ssl: process.env.DB_SSL === 'true',
}));
```

```ts
// config/jwt.config.ts
export default registerAs('jwt', () => ({
  secret: process.env.JWT_SECRET,
  expiresIn: process.env.JWT_EXPIRES_IN ?? '15m',
}));
```

### 2단계: ConfigModule.forRoot

```ts
import { ConfigModule } from '@nestjs/config';
import * as Joi from 'joi';
import databaseConfig from './config/database.config';
import jwtConfig from './config/jwt.config';

@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,              // 모든 모듈에서 import 없이 ConfigService 사용
      cache: true,                 // process.env 접근 결과 캐시
      envFilePath: ['.env.local', '.env'],
      load: [databaseConfig, jwtConfig],
      validationSchema: Joi.object({
        NODE_ENV: Joi.string().valid('development', 'production', 'test').default('development'),
        DB_HOST: Joi.string().required(),
        DB_PORT: Joi.number().port().default(5432),
        DB_PASSWORD: Joi.string().required(),
        JWT_SECRET: Joi.string().min(32).required(),
      }),
      validationOptions: { abortEarly: false }, // 에러를 한 번에 모두 보여줌
    }),
  ],
})
export class AppModule {}
```

Joi 대신 class-validator를 쓰고 싶다면 `validate` 함수를 넘긴다.

```ts
// config/env.validation.ts
import { plainToInstance } from 'class-transformer';
import { IsEnum, IsNumber, IsString, MinLength, validateSync } from 'class-validator';

enum Environment {
  Development = 'development',
  Production = 'production',
  Test = 'test',
}

class EnvironmentVariables {
  @IsEnum(Environment)
  NODE_ENV: Environment;

  @IsString()
  DB_HOST: string;

  @IsNumber()
  DB_PORT: number;

  @IsString()
  @MinLength(32)
  JWT_SECRET: string;
}

export function validate(config: Record<string, unknown>) {
  const validated = plainToInstance(EnvironmentVariables, config, {
    enableImplicitConversion: true, // '5432' → 5432
  });
  const errors = validateSync(validated, { skipMissingProperties: false });
  if (errors.length > 0) {
    throw new Error(errors.toString());
  }
  return validated;
}

// ConfigModule.forRoot({ isGlobal: true, load: [databaseConfig], validate })
```

> **포인트**: 검증은 **앱 시작 시점에 실패**하게 만드는 것이 핵심이다. 잘못된 설정으로 뜬 뒤 첫 요청에서 터지는 것보다 배포 단계에서 바로 죽는 게 훨씬 낫다.

> **주의**: `validationSchema`와 `validate`는 `.env`/`process.env`의 **원본 환경변수**를 검증한다. `registerAs`가 반환하는 가공된 객체를 검증하는 것이 아니다.

### 3단계: ConfigType + KEY로 타입 안전 주입

```ts
import { Inject, Injectable } from '@nestjs/common';
import { ConfigType } from '@nestjs/config';
import databaseConfig from '../config/database.config';

@Injectable()
export class DatabaseHealthService {
  constructor(
    @Inject(databaseConfig.KEY)
    private readonly dbConfig: ConfigType<typeof databaseConfig>,
  ) {}

  describe() {
    // dbConfig.host: string, dbConfig.port: number 로 자동 추론
    return `${this.dbConfig.host}:${this.dbConfig.port}`;
  }
}
```

`registerAs`가 반환한 팩토리에는 `KEY` 프로퍼티가 붙어 있어 DI 토큰으로 쓸 수 있다. `ConfigType<typeof databaseConfig>`는 팩토리 함수의 반환 타입을 뽑아준다.

다른 모듈의 async 설정에서도 바로 쓸 수 있다.

```ts
TypeOrmModule.forRootAsync({
  inject: [databaseConfig.KEY],
  useFactory: (db: ConfigType<typeof databaseConfig>) => ({
    type: 'postgres',
    host: db.host,
    port: db.port,
    username: db.username,
    password: db.password,
    database: db.name,
    ssl: db.ssl,
    autoLoadEntities: true,
  }),
}),
```

또는 `imports: [ConfigModule.forFeature(databaseConfig)]`를 함께 쓰면 해당 네임스페이스를 그 모듈 범위에서 로드할 수 있고, `TypeOrmModule.forRootAsync(databaseConfig.asProvider())` 같은 축약형도 제공된다.

### forFeature: 기능 모듈 전용 설정

```ts
// payment/payment.config.ts
export default registerAs('payment', () => ({
  apiKey: process.env.PG_API_KEY,
  webhookSecret: process.env.PG_WEBHOOK_SECRET,
}));

// payment/payment.module.ts
@Module({
  imports: [ConfigModule.forFeature(paymentConfig)],
  providers: [PaymentService],
})
export class PaymentModule {}
```

설정 파일이 해당 기능 폴더 안에 함께 있어서 응집도가 높아진다.

### ConfigService.get과 infer

`ConfigService`에 제네릭을 주면 점(.) 경로 키와 반환 타입을 추론할 수 있다.

```ts
interface AppConfig {
  database: { host: string; port: number };
  jwt: { secret: string; expiresIn: string };
}

@Injectable()
export class SomeService {
  constructor(private readonly config: ConfigService<AppConfig, true>) {}

  connect() {
    const host = this.config.get('database.host', { infer: true }); // string
    const port = this.config.get('database.port', { infer: true }); // number
    const db = this.config.get('database', { infer: true });       // { host, port }
  }
}
```

두 번째 제네릭 `true`는 "검증을 거쳤으니 값이 항상 있다"는 의미로, 반환 타입에서 `undefined`를 제거한다. 값이 없으면 바로 예외를 던지게 하려면 `getOrThrow()`를 쓴다.

| 방식 | 타입 안전성 | 편의성 | 추천 상황 |
| --- | --- | --- | --- |
| `config.get('DB_HOST')` | 낮음 | 높음 | 프로토타입 |
| `get('database.host', { infer: true })` | 높음 | 중간 | ConfigService를 이미 쓰는 코드 |
| `@Inject(databaseConfig.KEY)` + `ConfigType` | 매우 높음 | 높음 | 서비스/모듈 단위 설정 주입 |

## 그 외 꿀팁

> **비유**: 새 차를 사면 해두는 기본 세팅들 — 시트 위치, 사이드미러, 블랙박스. 한 번만 해두면 계속 편하다.

### enableShutdownHooks

```ts
const app = await NestFactory.create(AppModule);
app.enableShutdownHooks(); // SIGTERM 등 수신 시 onModuleDestroy, onApplicationShutdown 호출
await app.listen(3000);
```

```ts
@Injectable()
export class QueueWorker implements OnApplicationShutdown {
  async onApplicationShutdown(signal?: string) {
    console.log(`shutdown by ${signal}`);
    await this.drainJobs(); // 진행 중 작업 마무리, 커넥션 정리
  }
}
```

> **주의**: 기본값은 꺼져 있다. K8s 롤링 배포 시 SIGTERM을 받고도 커넥션 정리 없이 죽는 원인이 된다. 다만 리스너를 등록하므로 테스트에서 앱을 여러 번 만들면 `MaxListenersExceededWarning`이 날 수 있다.

### ValidationPipe whitelist / transform

```ts
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true,             // DTO에 없는 속성 제거
    forbidNonWhitelisted: true,  // 없는 속성이 오면 400 에러
    transform: true,             // plain object → DTO 인스턴스, '1' → 1 (타입 기반)
    transformOptions: { enableImplicitConversion: true },
  }),
);
```

| 옵션 | 효과 | 막아주는 것 |
| --- | --- | --- |
| `whitelist` | 데코레이터 없는 속성 제거 | `isAdmin: true` 같은 mass assignment |
| `forbidNonWhitelisted` | 제거 대신 에러 | 클라이언트 오타를 조용히 무시하는 문제 |
| `transform` | DTO 인스턴스로 변환, 파라미터 타입 변환 | `@Param('id') id: number`가 문자열로 오는 문제 |

### Swagger CLI plugin

DTO마다 `@ApiProperty()`를 일일이 붙이지 않아도, 빌드 시 TypeScript 타입과 class-validator 데코레이터를 읽어 자동으로 메타데이터를 추가해준다.

```json
{
  "collection": "@nestjs/schematics",
  "sourceRoot": "src",
  "compilerOptions": {
    "plugins": [
      {
        "name": "@nestjs/swagger",
        "options": {
          "classValidatorShim": true,
          "introspectComments": true
        }
      }
    ]
  }
}
```

`nest-cli.json`에 위처럼 설정한다. 기본적으로 `*.dto.ts`, `*.entity.ts` 파일명만 대상이다. `introspectComments`를 켜면 JSDoc 주석이 description으로 들어간다.

> **주의**: `nest build`/`nest start`로 빌드할 때만 적용된다. `ts-node`나 SWC, Jest(ts-jest)로 직접 실행하면 플러그인이 동작하지 않아 문서가 비어 보일 수 있다(별도 설정 필요).

### API Versioning

```ts
import { VersioningType } from '@nestjs/common';

app.enableVersioning({
  type: VersioningType.URI, // /v1/users, /v2/users
  defaultVersion: '1',
});
```

```ts
@Controller({ path: 'users', version: '1' })
export class UsersV1Controller {
  @Get()
  findAll() { return 'v1 list'; }
}

@Controller('users')
export class UsersV2Controller {
  @Version('2')
  @Get()
  findAll() { return 'v2 list'; }

  @Version(['1', '2'])
  @Get(':id')
  findOne(@Param('id') id: string) { return id; }
}
```

| 타입 | 예시 | 특징 |
| --- | --- | --- |
| `URI` | `/v1/users` | 가장 직관적, 캐시/로그 구분 쉬움 |
| `HEADER` | `X-API-Version: 2` | URL 깔끔, 브라우저에서 테스트 불편 |
| `MEDIA_TYPE` | `Accept: application/json;v=2` | REST 원칙에 가깝지만 복잡 |
| `CUSTOM` | extractor 함수 | 자유롭게 정의 |

## 셀프 체크

**Q1. Fastify 어댑터로 바꾼 뒤 Docker 컨테이너에서 외부 접속이 안 된다. 원인과 해결책은?**

**A.** Fastify는 기본적으로 `127.0.0.1`에만 바인딩한다. `app.listen(3000, '0.0.0.0')`처럼 호스트를 명시해 모든 인터페이스에서 수신하게 해야 한다.

**Q2. LazyModuleLoader로 로드하는 모듈에 컨트롤러를 넣을 수 없는 이유는?**

**A.** 라우트는 앱 부트스트랩 시점에 HTTP 어댑터에 등록된다. lazy 모듈은 그 이후에 로드되므로 라우트를 추가할 수 없다. 게이트웨이, 마이크로서비스 핸들러, GraphQL resolver도 같은 이유로 불가능하다.

**Q3. 운영 환경에서 압축을 앱의 `compression` 미들웨어보다 nginx에 맡기는 게 나은 이유는?**

**A.** 압축은 CPU 작업이라 Node.js의 싱글 스레드 이벤트 루프를 점유해 다른 요청 처리를 늦춘다. nginx는 압축을 효율적으로 처리하므로 앱은 비즈니스 로직에만 집중할 수 있다.

**Q4. 실제로는 순환 관계가 아닌데 `Nest can't resolve dependencies ... (?)` 에러가 났다. 무엇을 먼저 의심해야 하나?**

**A.** barrel(`index.ts`) 경유 import로 인한 모듈 로딩 순환이다. 평가 순서 때문에 클래스가 `undefined`인 상태로 `design:paramtypes`에 기록된 것이다. 파일 경로로 직접 import하도록 바꾸는 게 우선이고, `forwardRef`는 진짜 순환일 때만 쓴다.

**Q5. `registerAs('database', ...)`로 만든 설정을 타입 안전하게 주입하는 방법은?**

**A.** `@Inject(databaseConfig.KEY)`로 토큰을 지정하고, 타입을 `ConfigType<typeof databaseConfig>`로 선언한다. 그러면 `host`, `port` 등의 타입이 팩토리 반환값에서 자동 추론된다.

## 핵심 정리

- Fastify 어댑터는 성능 이득이 있지만 Express 전용 미들웨어/`@Res()` 코드 호환성을 확인해야 하고, `listen(3000, '0.0.0.0')`을 잊지 말자.
- `LazyModuleLoader`는 서버리스 콜드스타트 최적화용이다. 컨트롤러/게이트웨이/resolver는 lazy 모듈에 둘 수 없다.
- 압축은 개발/단순 환경에선 `compression` 또는 `@fastify/compress`, 운영에선 nginx/CDN에 맡기고 중복 압축은 피한다.
- barrel export는 public API 경계에만 쓰자. 앱 내부에서 남용하면 순환 의존 → `undefined` 주입 → 불필요한 `forwardRef`로 이어진다.
- `registerAs` + `ConfigModule.forRoot({ isGlobal, load, validationSchema / validate })` + `ConfigType` / `KEY` 주입 조합이 가장 안전한 설정 관리법이다. `get(..., { infer: true })`와 `getOrThrow()`도 활용하자.
- `enableShutdownHooks`, `ValidationPipe`의 `whitelist` / `transform`, Swagger CLI plugin, API versioning은 새 프로젝트를 만들면 바로 세팅해두자.

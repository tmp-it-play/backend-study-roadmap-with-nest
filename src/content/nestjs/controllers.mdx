## 한눈에 보기

- Controller는 **라우팅 테이블 + 요청 파라미터 매핑**을 선언적으로 표현한다. 실제 라우트 등록은 부트스트랩 때 Nest가 메타데이터를 읽어 Express/Fastify에 한다.
- 핸들러는 **값을 반환**하는 것이 기본(standard 모드)이다. `@Res()`를 주입하는 순간 Nest의 응답 처리(Interceptor 응답 매핑, 직렬화)가 꺼진다. 필요하면 `passthrough: true`.
- 요청 바디의 타입은 **class DTO**로 선언한다. interface는 런타임에 사라져서 `ValidationPipe`와 Swagger가 쓸 수 없다.
- 라우트는 **선언 순서대로 등록**되므로 `/users/me`를 `/users/:id`보다 위에 둔다.
- 버저닝(URI/Header/Media type), `RouterModule`, `setGlobalPrefix`로 URL 구조를 코드 수정 없이 조직할 수 있다.

## Controller의 역할

> **비유**: Controller는 호텔 **프런트 데스크**다. 손님(요청)의 용건을 듣고 필요한 정보(파라미터)를 정리해 담당 부서(Service)에 넘긴 뒤, 결과를 손님에게 전달한다. 프런트가 직접 요리하거나 객실 청소를 하지는 않는다.

```ts
@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get()
  findAll(@Query() query: ListUsersQueryDto) {
    return this.usersService.findAll(query);
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.usersService.findOne(id);
  }

  @Post()
  create(@Body() dto: CreateUserDto) {
    return this.usersService.create(dto);
  }
}
```

### 라우트가 등록되는 과정

1. `@Controller('users')`가 클래스에 `path = 'users'` 메타데이터를 저장한다.
2. `@Get(':id')`가 메서드 함수에 `path = ':id'`, `method = GET`을 저장한다.
3. 부트스트랩 시 **RouterExplorer**가 컨트롤러의 prototype 메서드를 순회하며 메타데이터를 읽는다.
4. global prefix, `RouterModule` 경로, 버전, 컨트롤러 prefix, 메서드 경로를 합쳐 최종 경로를 만든다.
5. HTTP 어댑터(Express 또는 Fastify)에 `router.get('/users/:id', handler)` 형태로 등록한다. 이때 handler는 Guard → Interceptor → Pipe → 메서드 → Filter 체인이 감싸진 함수다(순서는 Request Lifecycle 문서 참고).

> **포인트**: Nest 라우팅은 결국 **Express/Fastify 라우터 위에 얹힌 선언적 레이어**다. 그래서 경로 문법(와일드카드 등)은 하위 어댑터와 `path-to-regexp` 버전의 영향을 받는다.

## HTTP 메서드 데코레이터

`@Get`, `@Post`, `@Put`, `@Patch`, `@Delete`, `@Options`, `@Head`, `@All`이 있다. `@All`은 모든 메서드를 받는다.

| 데코레이터 | 기본 상태 코드 | 비고 |
| --- | --- | --- |
| `@Get()` | 200 | |
| `@Post()` | **201** | Nest만의 기본값. 조회성 POST면 `@HttpCode(200)` |
| `@Put()` / `@Patch()` | 200 | |
| `@Delete()` | 200 | 바디 없이 응답하려면 `@HttpCode(204)` |
| `@All()` | 200 | 프록시, 헬스체크 등 |

```ts
@Controller('auth')
export class AuthController {
  @Post('login')
  @HttpCode(HttpStatus.OK) // 로그인은 리소스 생성이 아니므로 200
  login(@Body() dto: LoginDto) {
    return this.authService.login(dto);
  }
}
```

## 요청 파라미터 추출

> **비유**: 택배 송장에서 필요한 칸만 오려 내는 **가위**들이다. `@Param`은 주소 칸, `@Query`는 요청 사항 칸, `@Body`는 상자 내용물, `@Headers`는 송장 상단의 메타 정보다.

| 데코레이터 | 가져오는 값 | Express 대응 |
| --- | --- | --- |
| `@Param(key?)` | 경로 파라미터 | `req.params` |
| `@Query(key?)` | 쿼리 스트링 | `req.query` |
| `@Body(key?)` | 요청 바디 | `req.body` |
| `@Headers(name?)` | 헤더(이름은 소문자) | `req.headers` |
| `@Ip()` | 클라이언트 IP | `req.ip` |
| `@HostParam(key?)` | 서브도메인 파라미터 | `req.hosts` |
| `@Session()` | 세션 객체 | `req.session` |
| `@Req()` / `@Res()` | 원본 request / response | `req` / `res` |

```ts
@Get(':orgId/members')
listMembers(
  @Param('orgId', ParseUUIDPipe) orgId: string,
  @Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number,
  @Headers('accept-language') lang: string | undefined,
  @Ip() ip: string,
) {
  return this.orgService.listMembers(orgId, { page, lang, ip });
}
```

> **주의**: `@Ip()`는 `req.ip`를 읽는다. 로드밸런서 뒤에 있다면 Express의 `trust proxy` 설정(`app.set('trust proxy', 1)`, `NestExpressApplication` 필요)을 하지 않으면 LB의 IP가 찍힌다.

> **주의**: `@Query()`와 `@Param()`의 값은 **항상 문자열**(또는 문자열 배열)이다. TS 타입을 `number`로 적어도 자동 변환되지 않는다. 변환은 Pipe의 역할이며 Pipe와 Validation 문서에서 다룬다.

## DTO는 왜 class인가

> **비유**: interface는 **설계도 사진**이라 공사가 끝나면(컴파일) 버려진다. class는 **실물 견본**이라 현장(런타임)에 남아 있어서 검수원(ValidationPipe)이 직접 대조할 수 있다.

```ts
// X interface: 컴파일 후 사라짐
export interface CreateUserInput {
  email: string;
  name: string;
}

// O class: 런타임에 존재하고 데코레이터를 붙일 수 있음
export class CreateUserDto {
  @IsEmail()
  email!: string;

  @IsString()
  @Length(2, 30)
  name!: string;
}
```

| 비교 | interface | class |
| --- | --- | --- |
| 런타임 존재 | X | O |
| 메서드 `design:paramtypes`에 남는 값 | `Object` | `CreateUserDto` |
| class-validator 데코레이터 | X | O |
| Swagger 스키마 자동 생성 | X | O |
| `PartialType` 등 Mapped types | X | O |

`ValidationPipe`는 `ArgumentMetadata.metatype`(즉 `design:paramtypes`에서 꺼낸 클래스)을 보고 검증 대상을 결정한다. interface면 `Object`가 오므로 **아무 검증도 하지 않고 통과**시킨다. 이 부분이 조용히 실패한다는 점이 위험하다.

## 응답 처리: standard vs @Res

> **비유**: standard 모드는 **자동 포장 라인**이다. 핸들러가 물건만 올려 두면 포장(JSON 직렬화), 송장(상태 코드), 검수(Interceptor)가 알아서 된다. `@Res()`는 **수작업 포장**이다. 자유롭지만 자동 라인의 모든 기능을 포기한다.

### standard 모드

핸들러가 값을 반환하면 Nest가 처리한다.

- 객체/배열 → JSON 직렬화
- 원시값(string, number) → 그대로 전송
- `Promise` → resolve된 값
- `Observable` → **complete 시점의 마지막 값**
- `undefined` → 빈 바디

### library-specific 모드 (@Res)

```ts
@Get('legacy')
legacy(@Res() res: Response) {
  res.status(200).json({ ok: true }); // 직접 응답해야 함
}
```

`@Res()`를 주입하면 Nest는 "이 핸들러는 응답을 직접 처리한다"고 판단하고, **반환값을 무시**한다. 결과적으로 다음이 동작하지 않는다.

- Interceptor의 `map()`으로 응답 변환
- `ClassSerializerInterceptor`
- `@HttpCode()`, `@Header()` (직접 설정해야 함)

> **주의**: `@Res()`를 주입해 놓고 `res.send()`를 호출하지 않으면 요청이 **영원히 응답하지 않고 매달린다**.

### passthrough: true

쿠키나 헤더만 만지고 응답 본문은 Nest에 맡기고 싶을 때 쓴다.

```ts
@Post('login')
@HttpCode(200)
async login(
  @Body() dto: LoginDto,
  @Res({ passthrough: true }) res: Response,
) {
  const { accessToken, refreshToken } = await this.authService.login(dto);
  res.cookie('refresh_token', refreshToken, { httpOnly: true, secure: true, sameSite: 'strict' });
  return { accessToken }; // 반환값은 standard 모드처럼 처리됨
}
```

| 방식 | 반환값 사용 | Interceptor 응답 매핑 | 직접 `res` 조작 |
| --- | --- | --- | --- |
| standard | O | O | X |
| `@Res()` | X | X | O (필수) |
| `@Res({ passthrough: true })` | O | O | O (헤더/쿠키 등) |

> **포인트**: `@Res()`는 마지막 수단이다. 대부분은 standard 모드 + `@Header` / `@HttpCode` / `passthrough`로 해결된다.

## @HttpCode, @Header, @Redirect

```ts
@Controller('files')
export class FilesController {
  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)
  remove(@Param('id') id: string) {
    return this.filesService.remove(id);
  }

  @Get('report.csv')
  @Header('Content-Type', 'text/csv; charset=utf-8')
  @Header('Cache-Control', 'no-store')
  report() {
    return this.filesService.buildCsv();
  }

  @Get('docs')
  @Redirect('https://docs.example.com', 302)
  docs(@Query('version') version?: string) {
    if (version) {
      // 반환값이 있으면 데코레이터 인자를 덮어씀
      return { url: `https://docs.example.com/${version}`, statusCode: 301 };
    }
  }
}
```

> **포인트**: `@Header()`는 **정적 값**만 가능하다. 요청마다 달라지는 헤더는 `passthrough` 모드의 `res.setHeader()`나 Interceptor로 처리한다.

## 와일드카드 라우트

v11(Express 5, `path-to-regexp` v8)부터 와일드카드 문법이 바뀌었다.

| 패턴 | v10 (Express 4) | v11 (Express 5) |
| --- | --- | --- |
| 이후 모든 경로 | `@Get('files/*')` | `@Get('files/*splat')` (이름 필수) |
| 루트 포함 매칭 | `@Get('files*')` 형태 혼용 | `@Get('files/{*splat}')` |
| 선택적 파라미터 | `@Get(':id?')` | `@Get('{:id}')` 형태 |
| 정규식 문자 | 일부 허용 | 지원 안 됨 |

```ts
// v11
@Get('assets/*path')
serve(@Param('path') path: string[]) {
  // 'assets/img/logo.png' → ['img', 'logo.png']
  return this.assetsService.read(path.join('/'));
}
```

> **주의**: v10 → v11 업그레이드 시 `forRoutes('*')` 같은 미들웨어 경로와 `setGlobalPrefix`의 `exclude` 경로도 새 문법(`'*splat'` 또는 `'{*splat}'`)으로 바꿔야 한다. Nest는 일부 구버전 패턴을 자동 변환하면서 경고를 출력한다.

## 라우트 순서 함정

> **비유**: 우체국 직원이 분류함을 **위에서부터 차례로** 확인한다. 맨 위 분류함이 "아무 이름이나(`:id`)"라면, "관리자 앞(`me`)" 우편물도 거기로 들어가 버린다.

```ts
// X 잘못된 순서
@Controller('users')
export class UsersController {
  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {}

  @Get('me') // 절대 도달하지 않음
  me(@CurrentUser() user: AuthUser) {}
}
```

`GET /users/me` 요청은 `:id` 라우트에 먼저 매칭되고, `ParseIntPipe`가 `'me'`를 숫자로 바꾸지 못해 **400 Bad Request**가 난다. 에러 메시지만 보면 원인을 찾기 어렵다.

```ts
// O 고정 경로를 먼저 선언
@Controller('users')
export class UsersController {
  @Get('me')
  me(@CurrentUser() user: AuthUser) {}

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {}
}
```

> **포인트**: Nest는 컨트롤러 안에서는 **메서드 선언 순서**, 컨트롤러 간에는 **모듈/컨트롤러 등록 순서**대로 라우트를 등록한다. 고정 경로가 동적 경로보다 위에 오도록 하자. 다른 컨트롤러에 흩어진 겹치는 경로는 특히 찾기 어렵다.

## Sub-domain routing

`@Controller`에 `host` 옵션을 주면 Host 헤더로 라우팅한다.

```ts
@Controller({ host: 'admin.example.com' })
export class AdminController {
  @Get()
  index() {
    return 'admin dashboard';
  }
}

@Controller({ host: ':tenant.example.com' })
export class TenantController {
  @Get()
  home(@HostParam('tenant') tenant: string) {
    return this.tenantService.home(tenant);
  }
}
```

> **주의**: Fastify는 중첩 라우터를 지원하지 않아서 sub-domain routing은 **Express 어댑터**에서 쓰는 것이 공식 권장이다.

## Versioning

> **비유**: 같은 건물의 **1층(v1)과 2층(v2)** 매장이다. 손님이 어느 층으로 갈지는 입구 표지판(URI), 출입증(Header), 주문서 양식(Media type) 중 하나로 정한다.

```ts
// main.ts
app.enableVersioning({
  type: VersioningType.URI,
  defaultVersion: '1',
});
```

| 타입 | 요청 예시 | 설정 |
| --- | --- | --- |
| `URI` | `GET /v2/users` | `prefix` 기본값 `'v'` |
| `HEADER` | `X-API-Version: 2` | `header: 'X-API-Version'` |
| `MEDIA_TYPE` | `Accept: application/json;v=2` | `key: 'v='` |
| `CUSTOM` | 자유 | `extractor: (req) → 버전 또는 버전 배열` |

```ts
@Controller({ path: 'users', version: '1' })
export class UsersV1Controller {
  @Get()
  findAll() {
    return this.usersService.findAllLegacy();
  }
}

@Controller('users')
export class UsersV2Controller {
  @Get()
  @Version('2')
  findAll() {
    return this.usersService.findAll();
  }

  @Get('health')
  @Version(VERSION_NEUTRAL) // 버전과 무관하게 매칭
  health() {
    return { ok: true };
  }
}
```

> **포인트**: 메서드의 `@Version()`이 컨트롤러 버전보다 우선한다. `@Version(['1', '2'])`처럼 여러 버전을 한 핸들러에 매핑할 수도 있다.

## RouterModule로 경로 구성

여러 모듈의 컨트롤러에 공통 prefix를 붙이고 싶을 때, 컨트롤러 코드를 고치지 않고 **모듈 단위로** 경로 트리를 선언할 수 있다.

```ts
@Module({
  imports: [
    AdminModule,
    DashboardModule,
    MetricsModule,
    RouterModule.register([
      {
        path: 'admin',
        module: AdminModule,
        children: [
          { path: 'dashboard', module: DashboardModule },
          { path: 'metrics', module: MetricsModule },
        ],
      },
    ]),
  ],
})
export class AppModule {}
```

`MetricsModule` 안의 `@Controller('cpu')`에 있는 `@Get()`은 최종적으로 `/admin/metrics/cpu`가 된다.

### 최종 경로 조립 순서

1. global prefix (`setGlobalPrefix('api')`)
2. 버전 (URI 버저닝일 때 `v1`)
3. `RouterModule` 경로 (`admin/metrics`)
4. 컨트롤러 prefix (`cpu`)
5. 메서드 경로

→ `GET /api/v1/admin/metrics/cpu`

> **주의**: `RouterModule`은 **모듈 단위**로 동작한다. 한 모듈에 여러 컨트롤러가 있으면 모두 같은 prefix를 받는다. 컨트롤러별로 다른 prefix가 필요하면 모듈을 나누자.

## global prefix

```ts
// main.ts
const app = await NestFactory.create(AppModule);
app.setGlobalPrefix('api', {
  exclude: [
    { path: 'health', method: RequestMethod.GET },
    'metrics', // 모든 메서드 제외
  ],
});
await app.listen(3000);
```

> **포인트**: 헬스체크나 Prometheus metrics처럼 인프라가 고정 경로로 호출하는 엔드포인트는 `exclude`로 prefix에서 빼 두면 편하다.

## 비동기 핸들러

핸들러는 동기 값, `Promise`, `Observable` 무엇이든 반환할 수 있다.

```ts
@Get(':id')
async findOne(@Param('id', ParseIntPipe) id: number): Promise<UserResponse> {
  const user = await this.usersService.findOne(id);
  if (!user) throw new NotFoundException(`User ${id} not found`);
  return user;
}

@Get('stats')
stats(): Observable<Stats> {
  return this.http.get<Stats>('https://stats.internal/users').pipe(map((res) => res.data));
}
```

| 반환 타입 | Nest의 처리 |
| --- | --- |
| 일반 값 | 즉시 직렬화 |
| `Promise` | await 후 직렬화. reject → Exception Filter |
| `Observable` | complete까지 기다린 뒤 **마지막 값** 전송. error → Exception Filter |

> **주의**: complete되지 않는 Observable(예: `interval()`)을 일반 핸들러에서 반환하면 응답이 끝나지 않는다. 지속 스트림은 `@Sse()`를 쓰자.

## StreamableFile

파일이나 스트림을 응답할 때 `@Res()`로 `pipe`하지 않고도 standard 모드를 유지할 수 있다.

```ts
@Get('exports/:id')
async download(@Param('id') id: string): Promise<StreamableFile> {
  const { path, filename } = await this.exportsService.find(id);
  const stream = createReadStream(path);
  return new StreamableFile(stream, {
    type: 'text/csv',
    disposition: `attachment; filename="${filename}"`,
  });
}
```

`StreamableFile`은 Express/Fastify 양쪽에서 동작하고, Interceptor도 그대로 적용된다. 반면 `ClassSerializerInterceptor`는 `StreamableFile`을 감지해 건드리지 않는다.

> **포인트**: 대용량 파일은 `readFile`로 Buffer를 만들지 말고 **스트림**을 넘기자. 메모리 사용량이 파일 크기와 무관해진다.

## Server-Sent Events (@Sse)

```ts
interface MessageEvent {
  data: string | object;
  id?: string;
  type?: string;
  retry?: number;
}

@Controller('notifications')
export class NotificationsController {
  constructor(private readonly events: NotificationEventsService) {}

  @Sse('stream')
  stream(@CurrentUser('id') userId: string): Observable<MessageEvent> {
    return this.events.forUser(userId).pipe(
      map((n) => ({ data: n, type: 'notification', id: n.id })),
    );
  }
}
```

- `@Sse()` 핸들러는 **`Observable`을 반환**해야 한다.
- 각 emit이 SSE 이벤트 하나가 되고, Nest가 `Content-Type: text/event-stream` 헤더와 연결 유지를 처리한다.
- 클라이언트 연결이 끊기면 구독이 해제된다.

> **주의**: SSE는 서버 인스턴스와 연결이 묶인다. 수평 확장 환경에서는 Redis Pub/Sub 같은 브로커로 이벤트를 모든 인스턴스에 전파해야 한다.

## 직렬화: ClassSerializerInterceptor

> **비유**: 응답 직전에 서류에서 **민감 정보를 검은 펜으로 지우는 검수원**이다. 어떤 칸을 지울지는 엔티티 클래스에 붙은 스티커(`@Exclude`)로 판단한다.

```ts
export class UserEntity {
  id!: number;
  email!: string;

  @Exclude()
  passwordHash!: string;

  @Expose({ groups: ['admin'] })
  lastLoginIp!: string;

  @Expose()
  get displayName(): string {
    return `${this.firstName} ${this.lastName}`;
  }

  @Exclude()
  firstName!: string;

  @Exclude()
  lastName!: string;

  constructor(partial: Partial<UserEntity>) {
    Object.assign(this, partial);
  }
}
```

```ts
@Controller('users')
@UseInterceptors(ClassSerializerInterceptor)
export class UsersController {
  @Get(':id')
  async findOne(@Param('id', ParseIntPipe) id: number) {
    const row = await this.usersService.findOne(id);
    return new UserEntity(row); // 반드시 클래스 인스턴스로 반환
  }

  @Get(':id/admin')
  @SerializeOptions({ groups: ['admin'] })
  async findOneForAdmin(@Param('id', ParseIntPipe) id: number) {
    return new UserEntity(await this.usersService.findOne(id));
  }
}
```

### 동작 원리

1. 핸들러가 값을 반환한다.
2. Interceptor의 `map()`에서 반환값이 객체(또는 배열)인지 확인한다.
3. `class-transformer`의 `instanceToPlain(value, options)`을 호출한다.
4. 이 과정에서 `@Exclude`, `@Expose`, `@Transform` 메타데이터가 적용된 plain object가 만들어진다.
5. 이후 일반 JSON 직렬화.

> **주의**: Prisma/TypeORM raw 쿼리 결과 같은 **plain object**를 그대로 반환하면 클래스 메타데이터가 없으므로 `@Exclude`가 **적용되지 않는다**. v10부터는 `@SerializeOptions({ type: UserEntity })`로 plain object를 해당 클래스로 변환하게 할 수도 있다.

| 옵션 | 효과 |
| --- | --- |
| `strategy: 'excludeAll'` | 기본 전부 제외, `@Expose`만 노출(화이트리스트) |
| `groups` | 그룹별 노출 제어 |
| `excludePrefixes: ['_']` | `_`로 시작하는 필드 제외 |
| `type` | plain object를 지정 클래스로 변환 후 직렬화 |

전역 적용은 다음처럼 한다.

```ts
// app.module.ts
providers: [
  { provide: APP_INTERCEPTOR, useClass: ClassSerializerInterceptor },
],
```

## 셀프 체크

**Q1. `@Res()`를 주입한 핸들러에서 `return { ok: true }`를 했는데 응답이 오지 않는다. 이유와 해결책은?**

**A.** `@Res()`를 주입하면 Nest는 library-specific 모드로 전환해 반환값을 무시하므로 응답이 전송되지 않는다. `res.json()`을 직접 호출하거나, 반환값을 쓰고 싶다면 `@Res({ passthrough: true })`로 바꾼다.

**Q2. `GET /users/me`가 400 Bad Request를 반환한다. `ParseIntPipe` 에러 메시지가 보인다. 무엇을 의심해야 하는가?**

**A.** 라우트 순서 문제다. `@Get(':id')`가 `@Get('me')`보다 먼저 선언되어 `'me'`가 `:id`로 매칭된 뒤 숫자 변환에 실패한 것이다. 고정 경로 핸들러를 동적 경로보다 위로 옮긴다.

**Q3. 요청 바디 타입을 interface로 선언했을 때 전역 `ValidationPipe`는 어떻게 동작하는가?**

**A.** interface는 런타임에 없으므로 메서드의 `design:paramtypes`에 `Object`가 기록된다. `ValidationPipe`는 `Object` 같은 기본 타입은 검증 대상이 아니라고 판단해 아무 검증 없이 값을 통과시킨다. 에러도 나지 않아 문제를 알아채기 어렵다.

**Q4. `setGlobalPrefix('api')`, URI 버저닝 `defaultVersion: '1'`, `RouterModule`의 `admin`, `@Controller('reports')`, `@Get('daily')`가 있을 때 최종 경로는?**

**A.** `GET /api/v1/admin/reports/daily`. global prefix → 버전 → RouterModule 경로 → 컨트롤러 prefix → 메서드 경로 순서로 조립된다.

**Q5. `ClassSerializerInterceptor`를 전역 등록했는데 `passwordHash`가 응답에 그대로 나온다. 가능한 원인은?**

**A.** 핸들러가 엔티티 클래스 인스턴스가 아니라 ORM이 돌려준 plain object를 반환했기 때문일 가능성이 높다. 클래스 인스턴스가 아니면 `@Exclude` 메타데이터를 찾을 수 없다. `new UserEntity(row)`로 감싸거나 `@SerializeOptions({ type: UserEntity })`를 사용한다.

## 핵심 정리

- Controller 데코레이터는 경로와 메서드 메타데이터를 저장하고, RouterExplorer가 부트스트랩 때 이를 읽어 Express/Fastify 라우트로 등록한다.
- 파라미터 데코레이터로 필요한 값만 추출하고, 바디 타입은 런타임에 남는 class DTO로 선언한다.
- 기본은 값을 반환하는 standard 모드다. `@Res()`는 Interceptor/직렬화를 무력화하므로 `passthrough: true`를 우선 고려한다.
- 라우트는 선언 순서대로 매칭되므로 고정 경로를 동적 경로보다 먼저 선언한다. v11에서는 와일드카드에 이름이 필요하다.
- URL 구조는 global prefix, versioning, `RouterModule`, sub-domain routing으로 코드 변경 없이 조직한다.
- `Promise`와 `Observable`(complete 시 마지막 값)을 그대로 반환할 수 있고, 파일은 `StreamableFile`, 실시간 푸시는 `@Sse()`로 처리한다.
- `ClassSerializerInterceptor`는 클래스 인스턴스에 대해 `instanceToPlain`을 실행해 `@Exclude`/`@Expose`를 적용한다.

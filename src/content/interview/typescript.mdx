## 기본 개념

**Q. (단골) TypeScript를 사용하는 이유는 무엇인가요?**

**A.** TypeScript는 JavaScript에 **정적 타입 시스템**을 더한 superset 언어로, 컴파일 시점에 타입 오류를 잡아 **런타임 버그를 사전에 줄여줍니다**. 타입이 곧 문서 역할을 해서 **자동 완성, 리팩터링, 코드 탐색** 같은 IDE 지원이 강력해지고, 협업과 대규모 코드베이스 유지보수가 쉬워집니다. 다만 타입은 **컴파일 후 모두 제거(type erasure)** 되므로, 외부 입력 같은 런타임 데이터의 검증은 별도로 필요합니다.

> **꼬리 질문**: 타입이 런타임에 사라진다면 API 응답은 어떻게 검증하나요? (zod, class-validator)

**Q. (단골) interface와 type alias의 차이는 무엇인가요?**

**A.** 둘 다 객체 타입을 정의할 수 있지만, `interface`는 같은 이름으로 여러 번 선언하면 **선언 병합(declaration merging)** 이 되고 `extends`로 확장합니다. `type`은 병합이 안 되지만 **유니온, 튜플, 원시 타입 별칭, 매핑 타입, 조건부 타입** 등 더 넓은 타입 표현이 가능하고 `&`(교차 타입)로 확장합니다. 일반적으로 객체의 형태나 라이브러리 공개 API처럼 **확장 가능성이 있는 곳은 interface**, 유니온이나 복잡한 타입 조합은 **type**을 사용합니다. 중요한 건 팀 컨벤션을 정하고 일관되게 쓰는 것입니다.

```ts
interface User { name: string }
interface User { age: number } // 병합 → name, age

type Status = 'idle' | 'loading' | 'done'; // 유니온은 type만 가능
```

**Q. (단골) any, unknown, never의 차이는 무엇인가요?**

**A.** `any`는 **타입 검사를 완전히 끄는** 타입으로, 어떤 연산도 허용되고 다른 타입으로 전염되어 타입 안정성을 무너뜨립니다. `unknown`은 **어떤 값이든 할당할 수 있지만 사용하기 전에 반드시 타입을 좁혀야** 하는 안전한 top 타입이라, 외부 입력이나 `catch`의 에러 처리에 적합합니다. `never`는 **절대 발생할 수 없는 값**의 타입(bottom 타입)으로, 항상 throw하는 함수의 반환 타입이나 switch 문의 **완전성 검사(exhaustive check)** 에 씁니다.

```ts
function assertNever(x: never): never {
  throw new Error(`Unexpected: ${x}`);
}
```

**Q. 타입 추론(Type Inference)이란 무엇인가요?**

**A.** 타입 추론은 개발자가 타입을 명시하지 않아도 **컴파일러가 할당된 값이나 문맥으로 타입을 자동으로 결정**하는 기능입니다. 변수 초기값, 함수 반환값, 콜백 매개변수(문맥적 타이핑) 등에서 동작합니다. `let`은 넓은 타입(`string`)으로, `const`는 리터럴 타입(`'hello'`)으로 추론되는 **타입 넓히기(widening)** 차이가 있습니다. 실무에서는 추론이 가능한 곳은 맡기고, **함수의 매개변수와 공개 API의 반환 타입은 명시**하는 편이 좋습니다.

**Q. 구조적 타이핑(Structural Typing)이란 무엇인가요?**

**A.** TypeScript는 타입의 이름이 아니라 **구조(가지고 있는 프로퍼티)가 호환되면 같은 타입으로 취급**하는 구조적 타이핑, 일명 **덕 타이핑**을 사용합니다. 그래서 명시적으로 implements하지 않아도 필요한 프로퍼티를 모두 가진 객체는 할당이 가능합니다. 반면 Java 같은 **명목적 타이핑(nominal typing)** 은 이름이 같아야 호환됩니다. 명목적 구분이 필요하면 **브랜드 타입(branded type)** 기법을 사용합니다.

> **꼬리 질문**: 객체 리터럴을 직접 넘길 때만 초과 프로퍼티 에러가 나는 이유는? (excess property checking)

## 타입 시스템 심화

**Q. (단골) 제네릭(Generic)이란 무엇이고 왜 사용하나요?**

**A.** 제네릭은 **타입을 매개변수처럼 받아** 함수, 클래스, 인터페이스를 여러 타입에 재사용할 수 있게 하는 기능입니다. `any`를 쓰면 입력과 출력의 타입 관계가 사라지지만, 제네릭은 **타입 안정성을 유지하면서 재사용성**을 얻을 수 있습니다. `extends`로 **타입 제약(constraint)** 을 걸어 특정 프로퍼티를 가진 타입만 받도록 제한할 수도 있습니다.

```ts
function getProp<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
getProp({ id: 1 }, 'id'); // number
```

**Q. (단골) 유니온 타입과 인터섹션 타입의 차이는?**

**A.** **유니온 타입**(`A | B`)은 "A **또는** B"로, 값이 둘 중 하나일 수 있으므로 사용 전에 타입을 좁혀야 하고 **공통 멤버만 바로 접근**할 수 있습니다. **인터섹션 타입**(`A & B`)은 "A **그리고** B"로, 두 타입의 **모든 프로퍼티를 동시에 만족**하는 타입이 됩니다. 집합 관점에서 보면 유니온은 값의 집합이 넓어지고, 인터섹션은 좁아지는 것입니다.

**Q. (단골) 타입 좁히기(Type Narrowing)와 타입 가드는 무엇인가요?**

**A.** 타입 좁히기는 유니온처럼 넓은 타입을 **조건문을 통해 더 구체적인 타입으로 좁히는 것**입니다. `typeof`, `instanceof`, `in` 연산자, 동등 비교, 그리고 `value is Type` 형태의 **사용자 정의 타입 가드** 함수를 사용합니다. 실무에서는 공통 리터럴 필드를 둔 **판별 유니온(Discriminated Union)** 을 switch로 분기하는 패턴을 많이 씁니다.

```ts
type Shape = { kind: 'circle'; r: number } | { kind: 'rect'; w: number; h: number };
function area(s: Shape) {
  switch (s.kind) {
    case 'circle': return Math.PI * s.r ** 2;
    case 'rect': return s.w * s.h;
  }
}
```

**Q. 타입 단언(as)과 타입 선언의 차이는? non-null assertion은?**

**A.** **타입 선언**(`const a: User = ...`)은 값이 타입을 만족하는지 **컴파일러가 검사**하지만, **타입 단언**(`as User`)은 "내가 더 잘 안다"고 컴파일러에게 **검사를 우회하도록 지시**하는 것이라 잘못 쓰면 런타임 에러로 이어집니다. `!`(non-null assertion)은 값이 `null`/`undefined`가 아님을 단언합니다. 둘 다 타입 시스템을 속이는 것이므로 **가능하면 타입 가드로 좁히는 방식**을 우선해야 합니다. 최근에는 타입을 넓히지 않고 검사만 하는 `satisfies` 연산자도 자주 쓰입니다.

**Q. (단골) 자주 쓰는 유틸리티 타입을 설명해주세요.**

**A.** `Partial`은 모든 프로퍼티를 **선택적**으로, `Required`는 **필수**로, `Readonly`는 **읽기 전용**으로 만듭니다. `Pick`은 **일부 키만 선택**하고 `Omit`은 **일부 키를 제외**하며, `Record`는 키와 값 타입으로 객체 타입을 만듭니다. 이 밖에 `ReturnType`, `Parameters`, `Awaited`, `NonNullable`, `Exclude`, `Extract`가 있습니다. 예를 들어 수정 DTO를 `Partial`로, 응답 DTO를 `Omit`으로 비밀번호를 뺀 형태로 정의하는 식으로 활용합니다.

**Q. keyof와 typeof 연산자는 무엇인가요?**

**A.** `keyof`는 객체 타입의 **키들을 문자열 리터럴 유니온 타입**으로 추출합니다. 타입 레벨의 `typeof`는 **값(변수)으로부터 타입을 추출**합니다. 둘을 조합한 `keyof typeof obj` 패턴은 상수 객체의 키 목록을 타입으로 만들 때 자주 쓰이며, `as const`와 함께 enum 대체 패턴으로도 활용됩니다.

**Q. 매핑 타입(Mapped Type)과 조건부 타입(Conditional Type)이란?**

**A.** **매핑 타입**은 기존 타입의 키를 순회하며 **각 프로퍼티를 변환해 새 타입을 만드는** 문법으로, `Partial`과 `Readonly`가 이 방식으로 구현되어 있습니다. **조건부 타입**은 `T extends U ? X : Y` 형태로 **타입 수준의 삼항 연산**을 하며, 유니온에 대해서는 각 멤버에 분배되는 **분배 조건부 타입**으로 동작합니다. `infer` 키워드로 조건 안에서 타입을 추출할 수 있고, `ReturnType`이 대표적인 예입니다.

```ts
type MyPartial<T> = { [K in keyof T]?: T[K] };
type MyReturn<T> = T extends (...args: any[]) => infer R ? R : never;
```

**Q. 공변성(Covariance)과 반공변성(Contravariance)이란 무엇인가요?**

**A.** **공변성**은 `Dog`가 `Animal`의 서브타입일 때 `Dog[]`도 `Animal[]`의 서브타입이 되는 것처럼 **관계가 같은 방향으로 유지**되는 성질입니다. **반공변성**은 함수 매개변수처럼 **관계가 반대로 뒤집히는** 성질로, `Animal`을 받는 함수는 `Dog`를 받는 함수 자리에 안전하게 쓸 수 있습니다. TypeScript는 `strictFunctionTypes` 옵션에서 함수 타입 매개변수를 반공변으로 검사하지만, **메서드 문법으로 선언한 매개변수는 이변성(bivariant)** 으로 검사하는 예외가 있습니다.

## 클래스와 enum

**Q. (단골) enum의 문제점과 대안은 무엇인가요?**

**A.** 일반 `enum`은 타입만이 아니라 **런타임 객체(IIFE 코드)를 생성**해 번들 크기가 늘고 트리 셰이킹이 어렵습니다. 숫자 enum은 **아무 숫자나 할당 가능**해 타입 안정성이 약하고, 구조적 타이핑과 달리 명목적으로 동작하는 등 일관성도 떨어집니다. `const enum`은 인라인되지만 `isolatedModules` 환경에서 문제가 생길 수 있어, 실무에서는 **문자열 리터럴 유니온**이나 **`as const` 객체**를 대안으로 많이 씁니다.

```ts
const Role = { ADMIN: 'ADMIN', USER: 'USER' } as const;
type Role = (typeof Role)[keyof typeof Role]; // 'ADMIN' | 'USER'
```

**Q. 접근 제어자 private과 JavaScript의 # private 필드의 차이는?**

**A.** TypeScript의 `private`, `protected`, `public`은 **컴파일 타임에만 검사**되고, 컴파일 후에는 일반 프로퍼티가 되어 런타임에서는 접근이 가능합니다. 반면 `#field`는 **ECMAScript 표준의 진짜 private 필드**로 런타임에서도 외부 접근이 차단됩니다. 또 TypeScript는 생성자 매개변수에 접근 제어자를 붙이면 프로퍼티 선언과 할당을 한 번에 하는 **매개변수 프로퍼티** 문법을 제공하며, NestJS의 의존성 주입에서 자주 쓰입니다.

**Q. abstract class와 interface의 차이는?**

**A.** `interface`는 **구현 없이 형태(계약)만 정의**하고 컴파일 후 사라지므로 런타임에 존재하지 않습니다. `abstract class`는 **일부 메서드의 구현과 상태를 가질 수 있고** 런타임에도 클래스로 남아 `instanceof` 검사가 가능하지만, 직접 인스턴스화할 수는 없습니다. 클래스는 여러 interface를 implements할 수 있지만 상속은 하나만 가능합니다. NestJS에서 interface는 런타임 토큰이 될 수 없어서 **DI 토큰으로 abstract class를 쓰는 패턴**이 나오는 이유이기도 합니다.

## 설정과 생태계

**Q. (단골) 데코레이터(Decorator)란 무엇인가요?**

**A.** 데코레이터는 클래스, 메서드, 프로퍼티, 매개변수에 붙여 **선언을 수정하거나 메타데이터를 추가하는 특수 함수**로, `@` 문법을 사용합니다. 선언이 평가될 때 실행되며, 대상의 정보(클래스 생성자, 프로퍼티 키, 디스크립터 등)를 인자로 받습니다. NestJS, TypeORM, class-validator가 레거시 **`experimentalDecorators`** 와 **`emitDecoratorMetadata`** 옵션 기반으로 동작하며, TypeScript 5.0부터는 TC39 표준 데코레이터도 지원하지만 매개변수 데코레이터가 없어 두 방식의 차이를 아는 것이 좋습니다.

> **꼬리 질문**: 여러 데코레이터가 붙으면 실행 순서는? (평가는 위→아래, 적용은 아래→위)

**Q. tsconfig에서 중요한 옵션은 무엇인가요?**

**A.** 가장 중요한 것은 `strict`로, `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes` 등을 한 번에 켜서 **타입 안정성을 크게 높입니다**. 그 밖에 출력 문법 수준을 정하는 `target`, 모듈 형식을 정하는 `module`과 `moduleResolution`, 경로 별칭 `paths`, 그리고 NestJS에서 필수인 `experimentalDecorators`와 `emitDecoratorMetadata`가 있습니다. 실무에서는 `noUncheckedIndexedAccess`처럼 인덱스 접근의 `undefined` 가능성을 잡아주는 옵션도 고려합니다.

**Q. 선언 파일(.d.ts)은 무엇인가요?**

**A.** `.d.ts` 파일은 **구현 없이 타입 정보만 담은 선언 파일**로, JavaScript로 작성된 라이브러리에 타입을 제공합니다. 라이브러리가 자체 타입을 포함하지 않으면 DefinitelyTyped의 `@types` 패키지를 설치해 사용합니다. 전역 타입을 확장하거나 Express의 `Request`에 `user` 프로퍼티를 추가하는 것처럼 **모듈 보강(module augmentation)** 을 할 때도 선언 파일과 `declare` 키워드를 사용합니다.

## NestJS 기본

**Q. (단골) NestJS란 무엇이고, Express와 비교해 어떤 차이가 있나요?**

**A.** NestJS는 TypeScript 기반의 **Node.js 서버 프레임워크**로, 내부적으로 **Express(기본) 또는 Fastify를 HTTP 어댑터로 사용**합니다. Express는 최소한의 기능만 제공하는 **비의견적(unopinionated)** 라이브러리라 구조를 팀이 직접 정해야 하지만, NestJS는 **Module, Controller, Provider 구조와 DI 컨테이너**를 제공하는 **의견적(opinionated)** 프레임워크입니다. 그래서 일관된 아키텍처, 테스트 용이성, Guard·Pipe·Interceptor 같은 횡단 관심사 처리 도구를 기본으로 얻을 수 있습니다. 대신 학습 곡선과 보일러플레이트가 늘어나는 트레이드오프가 있습니다.

> **꼬리 질문**: 그럼 NestJS에서 Express 기능을 직접 쓸 수 있나요? (`@Req`, `@Res`, 미들웨어 호환)

**Q. Express 어댑터와 Fastify 어댑터의 차이는 무엇인가요?**

**A.** NestJS는 **플랫폼 독립적**으로 설계되어 HTTP 어댑터를 교체할 수 있습니다. **Express**는 기본값으로 생태계와 미들웨어가 풍부하고 호환성이 좋습니다. **Fastify**는 스키마 기반 직렬화와 효율적인 라우팅 덕분에 **처리량(throughput)이 더 높지만**, Express 전용 미들웨어나 라이브러리가 바로 호환되지 않을 수 있습니다. 성능이 중요한 서비스라면 Fastify, 생태계 호환성이 중요하면 Express를 선택합니다.

**Q. (단골) Module, Controller, Provider의 역할을 설명해주세요.**

**A.** **Controller**는 들어오는 요청을 **라우팅하고 응답을 반환**하는 계층으로 `@Controller`와 `@Get` 같은 데코레이터로 정의합니다. **Provider**는 `@Injectable`로 표시된 서비스, 레포지토리, 팩토리 등으로 **비즈니스 로직을 담당**하며 DI 컨테이너가 생성하고 주입합니다. **Module**은 `@Module`로 관련된 Controller와 Provider를 **하나의 응집된 단위로 묶고**, `imports`와 `exports`로 모듈 간 의존 관계와 공개 범위를 정의합니다. 애플리케이션은 루트 모듈(AppModule)에서 시작하는 **모듈 그래프**로 구성됩니다.

**Q. (단골) 모듈의 exports를 하지 않으면 어떻게 되나요? Global 모듈은 언제 쓰나요?**

**A.** NestJS에서 Provider는 기본적으로 **선언된 모듈 안에 캡슐화**되어, `exports`에 등록하지 않으면 다른 모듈에서 import해도 주입할 수 없고 "Nest can't resolve dependencies" 에러가 납니다. `@Global` 데코레이터를 붙이면 루트에서 한 번만 등록해 **어디서든 import 없이 주입**할 수 있습니다. 하지만 의존 관계가 숨겨지고 캡슐화가 깨지므로 설정(Config), 로거, DB 연결처럼 **정말 전역적인 것에만 제한적으로** 사용하는 것이 좋습니다.

**Q. Dynamic Module이란 무엇인가요?**

**A.** Dynamic Module은 `forRoot`, `forRootAsync`, `register` 같은 정적 메서드로 **런타임에 설정 값을 받아 Provider를 동적으로 구성하는 모듈**입니다. `TypeOrmModule.forRoot`나 `ConfigModule.forRoot`처럼 같은 모듈을 **환경마다 다른 옵션으로 재사용**할 때 씁니다. 관례상 `forRoot`는 앱 전체에 한 번 설정, `forFeature`는 특정 모듈 범위의 설정, `register`는 사용하는 곳마다 다른 설정을 의미합니다. `forRootAsync`의 `useFactory`와 `inject`로 다른 Provider(예: ConfigService)를 주입받아 설정할 수 있습니다.

## DI와 IoC

**Q. (단골) IoC(제어의 역전)와 DI(의존성 주입)란 무엇인가요?**

**A.** **IoC**는 객체의 생성과 생명주기 관리, 의존 관계 연결의 **제어권을 개발자 코드가 아닌 프레임워크(컨테이너)가 가지는 설계 원칙**입니다. **DI**는 IoC를 구현하는 방법 중 하나로, 클래스가 필요한 의존성을 **직접 `new`로 생성하지 않고 외부에서 주입받는 패턴**입니다. NestJS에서는 생성자에 타입을 선언하기만 하면 **IoC 컨테이너가 인스턴스를 만들어 주입**합니다. 이로써 결합도가 낮아지고, 테스트 시 Mock 객체로 쉽게 교체할 수 있습니다.

```ts
@Injectable()
export class UsersService {
  constructor(private readonly usersRepository: UsersRepository) {}
}
```

> **꼬리 질문**: DI가 없으면 테스트가 왜 어려워지나요? / 생성자 주입과 프로퍼티 주입의 차이는?

**Q. (단골) NestJS는 생성자 매개변수의 타입만 보고 어떻게 의존성을 찾아 주입하나요?**

**A.** TypeScript의 `emitDecoratorMetadata` 옵션을 켜면 컴파일러가 데코레이터가 붙은 클래스에 대해 **생성자 매개변수의 타입 정보를 `design:paramtypes` 메타데이터로 기록**합니다. NestJS는 **`reflect-metadata`** 라이브러리의 `Reflect.getMetadata`로 이 정보를 읽어 각 매개변수가 어떤 클래스(토큰)인지 파악하고, 컨테이너에서 해당 Provider 인스턴스를 찾아 주입합니다. 그래서 클래스에 `@Injectable` 같은 데코레이터가 있어야 메타데이터가 생성되며, **interface는 런타임에 사라지므로 토큰으로 쓸 수 없어** `@Inject` 데코레이터로 문자열이나 Symbol 토큰을 명시해야 합니다.

**Q. (단골) 데코레이터와 reflect-metadata는 NestJS에서 어떤 역할을 하나요?**

**A.** NestJS의 데코레이터는 대부분 **클래스나 메서드에 메타데이터를 붙이는 함수**입니다. 예를 들어 `@Controller('users')`는 경로 정보를, `@Get()`은 HTTP 메서드와 경로를, `@UseGuards()`는 적용할 가드 정보를 `Reflect.defineMetadata`로 저장합니다. 애플리케이션이 부트스트랩될 때 NestJS가 **이 메타데이터를 스캔해 라우트를 등록하고 DI 그래프를 구성**합니다. `SetMetadata`나 `Reflector.createDecorator`로 커스텀 메타데이터를 만들고, Guard에서 `Reflector`로 읽어 역할 기반 인가를 구현하는 것이 대표적인 활용입니다.

```ts
export const Roles = Reflector.createDecorator<string[]>();
// Guard 내부
const roles = this.reflector.get(Roles, context.getHandler());
```

**Q. 커스텀 프로바이더(useClass, useValue, useFactory, useExisting)는 언제 쓰나요?**

**A.** 기본 클래스 Provider 외에 **토큰과 생성 방식을 직접 지정**할 때 커스텀 프로바이더를 씁니다. `useValue`는 **상수나 Mock 객체**를 주입할 때, `useClass`는 환경에 따라 **다른 구현 클래스로 교체**할 때, `useFactory`는 **다른 Provider를 주입받아 동적으로 생성**하거나 비동기 초기화(DB 연결 등)가 필요할 때 씁니다. `useExisting`은 기존 Provider에 **별칭(alias)** 을 만듭니다. 문자열·Symbol 토큰을 쓸 때는 `@Inject(TOKEN)`으로 주입받습니다.

**Q. (단골) Provider의 Injection Scope(DEFAULT, REQUEST, TRANSIENT)를 설명해주세요.**

**A.** 기본값인 **DEFAULT(Singleton)** 는 애플리케이션 전체에서 **인스턴스 하나를 공유**하며 앱 시작 시 생성됩니다. **REQUEST** 스코프는 **요청마다 새 인스턴스**를 만들고 요청이 끝나면 GC 대상이 되어, 요청별 상태(테넌트 정보 등)를 다룰 때 씁니다. **TRANSIENT**는 **주입받는 소비자마다 별도의 인스턴스**를 생성합니다. 주의할 점은 REQUEST 스코프가 **의존 체인을 타고 상위로 전파(scope bubbling)** 되어 이를 주입받는 컨트롤러와 서비스까지 요청마다 생성되므로 **성능 비용**이 생긴다는 것입니다. 그래서 가능하면 싱글톤을 유지하고, 요청 컨텍스트가 필요하면 AsyncLocalStorage(nestjs-cls 등)를 대안으로 고려합니다.

**Q. (단골) 순환 의존성(Circular Dependency)은 왜 생기고 어떻게 해결하나요?**

**A.** 순환 의존성은 A가 B를, B가 다시 A를 의존해 **DI 컨테이너가 어느 쪽을 먼저 생성할지 결정할 수 없을 때** 발생합니다. Provider 간에는 양쪽에서 `@Inject(forwardRef(() => B))`로, 모듈 간에는 `imports: [forwardRef(() => BModule)]`로 **아직 정의되지 않은 참조를 지연 해석**하게 해 해결할 수 있습니다. 다만 공식 문서도 권장하듯 forwardRef는 임시방편이고, 근본적으로는 **공통 로직을 별도 서비스·모듈로 분리**하거나 **이벤트 기반으로 결합을 끊는** 등 설계를 개선하는 것이 좋습니다. 또 REQUEST 스코프 Provider가 순환에 끼면 의존성이 `undefined`가 될 수 있고, 배럴 파일(index.ts) import가 순환을 유발하기도 합니다.

## 요청 라이프사이클

**Q. (단골) NestJS의 요청 라이프사이클 순서를 설명해주세요.**

**A.** 요청은 **Middleware → Guard → Interceptor(전처리) → Pipe → Controller(Route Handler) → Service → Interceptor(후처리) → 응답** 순으로 흐릅니다. 각 단계에서 예외가 발생하면 **Exception Filter**가 잡아 응답을 만듭니다. 같은 종류끼리는 Guard·Interceptor·Pipe가 **전역 → 컨트롤러 → 라우트** 순으로 실행되고, 필터는 반대로 **라우트 → 컨트롤러 → 전역** 순으로 가장 가까운 것이 먼저 예외를 처리합니다.

```text
Request
 → Middleware → Guard → Interceptor(before) → Pipe
 → Controller → Service
 → Interceptor(after) → Response
(예외 발생 시 → Exception Filter)
```

**Q. (단골) Middleware, Guard, Interceptor의 차이는 무엇인가요?**

**A.** **Middleware**는 라우트 핸들러 이전에 실행되는 Express 스타일 함수로 `req`, `res`, `next`에 접근하지만, **다음에 어떤 핸들러가 실행될지는 모릅니다**. 로깅, CORS, body 파싱처럼 범용적인 처리에 적합합니다. **Guard**는 `ExecutionContext`를 통해 **실행될 핸들러와 메타데이터를 알 수 있어** 인증·인가처럼 "이 요청을 처리할지 말지"를 boolean으로 결정하는 데 씁니다. **Interceptor**는 RxJS `Observable`을 이용해 **핸들러 실행 전후를 모두 감싸** 응답 변환, 로깅·실행 시간 측정, 캐싱, 타임아웃 처리 등 AOP 스타일 로직에 적합합니다.

> **꼬리 질문**: 인증을 미들웨어가 아닌 Guard로 구현하는 이유는? / Guard에서 false를 반환하면 어떤 응답이 나가나요? (`ForbiddenException`, 403)

**Q. ExecutionContext란 무엇인가요?**

**A.** `ExecutionContext`는 `ArgumentsHost`를 확장한 객체로, **현재 실행 중인 요청의 컨텍스트 정보**를 제공합니다. `getClass`와 `getHandler`로 **실행될 컨트롤러 클래스와 핸들러 메서드**를 얻을 수 있어 `Reflector`로 메타데이터를 읽을 수 있습니다. 또 `switchToHttp`, `switchToRpc`, `switchToWs`로 전환해 HTTP, 마이크로서비스, WebSocket 등 **전송 계층에 관계없이 같은 Guard·Interceptor를 재사용**할 수 있게 해줍니다.

**Q. (단골) Pipe는 무엇이고 ValidationPipe는 어떻게 동작하나요?**

**A.** Pipe는 컨트롤러 핸들러가 실행되기 직전에 인자를 가로채 **변환(transformation)** 하거나 **유효성 검사(validation)** 를 수행합니다. `ParseIntPipe`, `ParseUUIDPipe` 같은 내장 파이프가 있고, `ValidationPipe`는 **class-transformer로 plain 객체를 DTO 클래스 인스턴스로 변환한 뒤 class-validator 데코레이터 규칙으로 검증**합니다. 검증에 실패하면 `BadRequestException`(400)을 던집니다. 실무에서는 `whitelist`(DTO에 없는 속성 제거), `forbidNonWhitelisted`, `transform` 옵션을 함께 전역 설정합니다.

```ts
app.useGlobalPipes(
  new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true }),
);
```

**Q. DTO는 왜 interface가 아니라 class로 정의하나요?**

**A.** TypeScript의 interface는 **컴파일 후 사라지기 때문에** 런타임에 정보가 남지 않습니다. ValidationPipe는 런타임에 `design:paramtypes` 메타데이터로 **DTO 클래스 타입을 알아내고**, 그 클래스에 붙은 class-validator 데코레이터로 검증하므로 반드시 **class**여야 합니다. Swagger 문서 자동 생성(`@nestjs/swagger`)도 같은 이유로 클래스가 필요합니다. 또 `PartialType`, `PickType`, `OmitType` 같은 Mapped Types로 DTO를 재사용할 수 있습니다.

**Q. (단골) Exception Filter는 무엇이고 어떻게 활용하나요?**

**A.** NestJS에는 처리되지 않은 예외를 잡아 **적절한 응답으로 변환하는 내장 예외 레이어**가 있으며, `HttpException`과 그 하위 클래스(`NotFoundException` 등)를 던지면 자동으로 상태 코드와 메시지가 응답됩니다. **Exception Filter**는 `@Catch` 데코레이터와 `ExceptionFilter` 인터페이스로 이 동작을 커스터마이즈해 **응답 포맷을 통일**하거나, 로깅·모니터링(Sentry 등)을 붙이거나, 도메인 예외와 DB 예외를 HTTP 예외로 매핑합니다. 전역 필터로 등록할 때 DI가 필요하면 `useGlobalFilters` 대신 `APP_FILTER` 토큰으로 모듈에 등록합니다.

> **꼬리 질문**: `useGlobalGuards`와 `APP_GUARD` 등록 방식의 차이는? (DI 컨테이너 밖 vs 안)

**Q. 커스텀 데코레이터는 어떻게 만들고 언제 쓰나요?**

**A.** `createParamDecorator`로 **요청 객체에서 원하는 값을 꺼내는 매개변수 데코레이터**를 만들 수 있습니다. 예를 들어 Guard에서 인증 후 `request.user`에 넣은 사용자 정보를 `@CurrentUser()`로 바로 주입받는 패턴이 대표적입니다. 또 `applyDecorators`로 `@UseGuards`, `@Roles`, `@ApiBearerAuth` 같은 여러 데코레이터를 **하나로 합성**해 중복을 줄일 수 있습니다.

## 라이프사이클 훅과 설정

**Q. NestJS의 라이프사이클 훅에는 무엇이 있나요?**

**A.** 애플리케이션 시작 시 `onModuleInit`(모듈 의존성 해결 후) → `onApplicationBootstrap`(모든 모듈 초기화 후, 연결 수신 전) 순으로 호출됩니다. 종료 시에는 `onModuleDestroy` → `beforeApplicationShutdown` → `onApplicationShutdown` 순으로 호출되는데, 종료 훅은 **`app.enableShutdownHooks()`를 호출해야** SIGTERM 같은 시그널에 반응합니다. 초기 데이터 로딩, 커넥션 생성과 **graceful shutdown 시 커넥션 정리**에 활용합니다. 단, REQUEST 스코프 Provider에서는 라이프사이클 훅이 호출되지 않습니다.

**Q. 환경 변수와 설정은 어떻게 관리하나요?**

**A.** `@nestjs/config`의 `ConfigModule.forRoot`로 `.env` 파일을 로드하고, `ConfigService`를 주입받아 값을 읽습니다. `validationSchema`(Joi)나 `validate` 함수로 **앱 시작 시점에 환경 변수를 검증**해 잘못된 설정으로 서버가 뜨는 것을 막는 것이 좋습니다. `registerAs`로 설정을 네임스페이스별로 나누고 타입을 붙이면 관리가 쉬워지며, 다른 모듈 설정에는 `forRootAsync`와 `useFactory`로 ConfigService를 주입해 사용합니다.

## 테스트

**Q. (단골) NestJS에서 단위 테스트와 E2E 테스트는 어떻게 작성하나요?**

**A.** NestJS는 기본으로 **Jest**를 사용하며, `@nestjs/testing`의 `Test.createTestingModule`로 **테스트용 DI 컨테이너**를 구성합니다. **단위 테스트**에서는 의존하는 Provider를 `useValue`로 Mock 객체로 교체하거나 `overrideProvider`로 바꿔 대상 클래스의 로직만 검증합니다. **E2E 테스트**에서는 실제 모듈로 `INestApplication`을 띄우고 **supertest**로 HTTP 요청을 보내 Guard, Pipe, Filter까지 포함한 전체 흐름을 검증합니다. DI 구조 덕분에 테스트 대상과 의존성을 쉽게 분리할 수 있다는 것이 NestJS의 큰 장점입니다.

```ts
const module = await Test.createTestingModule({
  providers: [UsersService, { provide: UsersRepository, useValue: mockRepo }],
}).compile();
const service = module.get(UsersService);
```

## 데이터베이스와 아키텍처

**Q. NestJS에서 트랜잭션은 어떻게 처리하나요?**

**A.** TypeORM 기준으로 `DataSource.transaction` 콜백이나 `QueryRunner`로 **connect → startTransaction → commit/rollback → release**를 직접 제어할 수 있습니다. 하지만 서비스 코드에 트랜잭션 관리 코드가 섞이고 여러 레포지토리에 같은 EntityManager를 전달해야 하는 문제가 있어, 실무에서는 **AsyncLocalStorage 기반의 `@Transactional` 데코레이터**(typeorm-transactional, nestjs-cls transactional 플러그인 등)를 많이 씁니다. Prisma는 `$transaction` API를 사용합니다. 중요한 점은 `release`를 반드시 `finally`에서 호출해 **커넥션 누수를 막는 것**입니다.

**Q. (단골) NestJS에서 마이크로서비스는 어떻게 구성하나요?**

**A.** `@nestjs/microservices` 패키지로 **TCP, Redis, NATS, RabbitMQ, Kafka, gRPC** 등 다양한 Transporter를 사용할 수 있습니다. 통신 방식은 응답을 기다리는 **요청-응답(`@MessagePattern`)** 과 응답이 없는 **이벤트 기반(`@EventPattern`)** 두 가지이며, 클라이언트 쪽은 `ClientProxy`의 `send`와 `emit`을 사용합니다. 하나의 앱을 HTTP 서버와 마이크로서비스로 동시에 띄우는 **하이브리드 애플리케이션**도 가능합니다. Guard, Pipe, Interceptor, Filter도 동일하게 쓸 수 있지만, 예외는 `RpcException`을 사용합니다.

**Q. CQRS 패턴이란 무엇이고 NestJS에서 어떻게 사용하나요?**

**A.** **CQRS(Command Query Responsibility Segregation)** 는 데이터를 **변경하는 명령(Command)과 조회하는 쿼리(Query)의 모델과 책임을 분리**하는 패턴입니다. `@nestjs/cqrs` 모듈은 `CommandBus`, `QueryBus`, `EventBus`와 각각의 Handler를 제공해, 컨트롤러는 Command나 Query 객체를 버스에 보내기만 하고 실제 로직은 Handler가 처리합니다. 도메인 이벤트와 **Saga**로 복잡한 비즈니스 흐름을 이벤트 기반으로 조합할 수 있습니다. 다만 구조가 복잡해지므로 **읽기·쓰기 요구사항이 크게 다르거나 도메인이 복잡한 경우**에 도입하는 것이 적절합니다.

**Q. NestJS 애플리케이션의 성능을 개선하려면 어떻게 하나요?**

**A.** 먼저 HTTP 어댑터를 **Fastify로 교체**해 처리량을 높일 수 있고, `CacheModule`과 Redis로 **응답이나 조회 결과를 캐싱**합니다. REQUEST 스코프 Provider 남용을 피해 **불필요한 인스턴스 생성을 줄이고**, DB 측면에서는 N+1 쿼리 제거, 인덱스, 커넥션 풀 튜닝을 합니다. CPU 집약 작업은 이벤트 루프를 막지 않도록 **BullMQ 같은 큐로 비동기 처리**하거나 Worker Threads로 분리하고, 수평 확장 시에는 PM2 cluster나 컨테이너 오케스트레이션을 사용합니다.
